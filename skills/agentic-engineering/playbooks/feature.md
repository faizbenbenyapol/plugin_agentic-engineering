# ฟีเจอร์

**เราเป็นเจ้าของดีไซน์ วางแผน ตรวจ พิสูจน์** หัวหน้าเขียนเองเป็นค่าเริ่มต้น ส่ง agent เฉพาะตาม SKILL.md ข้อ 3

## ขั้น

1. **สืบสวนส่วนที่จะแตะแบบแคบ** และค้นโค้ดเดิมที่ใช้ซ้ำได้ก่อนเขียนฟังก์ชันใหม่
2. **ตั้งโจทย์ร่วมตาม `playbooks/kickoff.md`:** ทวนความเข้าใจ ถามเรื่องที่ผู้ใช้ต้องตัดสิน (ขอบเขต พฤติกรรม กรณีขอบ เกณฑ์เสร็จ) พร้อมคำแนะนำ แล้วเขียนข้อตกลงงานและรอยืนยันหนึ่งครั้งก่อนแก้ไฟล์แรก ทุกระดับ ไม่ใช่เฉพาะระดับเต็ม (ข้ามเมื่อผู้ใช้สั่ง "ตัดสินใจเองได้" แต่ยังต้องเขียนไฟล์) เขียน `docs/requirements/<ชื่อ>.md` ทุกฟีเจอร์ คำถามที่ตอบได้ด้วยการรัน ให้ทำ prototype เล็ก ๆ แทนการถาม
3. **ตั้งชื่อรูปร่างข้อมูลและโครงสร้างที่จัดมัน** ก่อนเขียน logic: state machine แทน boolean กระจาย, ตาราง/registry แทน if-else ยาว, typed model แทนการเดารูปร่างซ้ำหลายไฟล์ ถ้าข้ามขอบฟังก์ชันให้ร่างแบบตาม `references/design.md` (ระดับเต็มต้องมีสองแบบที่ต่างกันทั้งรูป)
4. **ทำทีละ slice ที่ตรวจได้:** อ่านแถว REQ ของ slice → ทำ → ตรวจกับเกณฑ์ยอมรับ → commit → ชิ้นถัดไป (ด่านตรวจใน `playbooks/kickoff.md`) จะทำต่างจากไฟล์ให้ออกคำขอเปลี่ยนก่อน สร้างจากชั้นในออกนอก: logic/ข้อมูลก่อน แล้วค่อยต่อ UI หรือ API ตั้ง interface ตามสิ่งที่ผู้เรียกต้องการ test ใช้ fake ที่เขียนเองแทน mock library เมื่อทำได้ การปรับ shared primitive ต้องตามไปแก้ผู้ใช้ทุกตัวและตรวจทุกตัว ถ้ามีหลายสายงานจริง ให้ระบุในแผนว่าอะไรต้องทำก่อน สายไหนแยกขาด และ state ไหนเขียนร่วม
5. **อ่าน diff ทั้งหมดเอง** เทียบกับสเปก ถ้าระดับกลางเปลี่ยนข้ามโมดูล ให้เทียบ red flags ใน `references/design.md`
6. **ตรวจบน surface จริง** (SKILL.md ข้อ 4) "สรุปไม่ได้" หรือผิด surface ไม่ใช่ผ่าน
7. **ระดับเต็ม:** ทำ blast radius แล้วส่ง `reviewer` แบบโจมตี
8. **ทำ `playbooks/delivery.md`** commit เล็กเรียงลำดับ (scaffold ก่อนฟีเจอร์)
9. **ทำคู่มือส่งมอบตาม `playbooks/handoff.md`** ทุกครั้ง

**รายงาน:** สร้างอะไรให้ใคร เลือกแบบไหนเพราะอะไร หลักฐาน เกณฑ์เสร็จทีละข้อ ใครตัดสินอะไร และสิ่งที่ผู้ใช้ยังต้องตัดสิน
