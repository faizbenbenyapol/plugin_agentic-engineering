# สืบสวน

**เราเป็นเจ้าของคำตอบ** อ่านอย่างเดียว ไม่แก้โค้ด ผลงานคือคำอธิบายที่อ้างอิงได้ หรือคำแนะนำพร้อมตารางเปรียบเทียบ

ใช้กับ: "X ทำงานยังไง" "ควรวางโค้ดนี้ไว้ไหน" "ทำไมถึงทำแบบนี้" "แน่ใจเหรอ" "ควรเลือก A หรือ B" และการวินิจฉัยอาการ runtime (ค้าง กิน CPU memory รั่ว) ที่ผลงานคือการวินิจฉัย ไม่ใช่การแก้

## ขั้น

1. ประเมินขนาด: คำถามแคบ (ฟังก์ชันเดียว โมดูลเดียว) หัวหน้าอ่านเองรอบเดียว คำถามกว้าง (หลายไฟล์ หลาย service) ส่ง `scout` หนึ่งตัวพร้อมคำถามรวม เพิ่มตัวที่สองเฉพาะเมื่อ service แยกกันจริง แล้วหัวหน้าสังเคราะห์ ไม่แน่ใจให้เลือกแบบแคบ
2. ไล่โค้ดจริงตั้งแต่จุดเข้าจนจุดจบ ถ้าถาม "ทำไม" ให้ขุดประวัติ: `git log -L`, `git blame`, ข้อความ commit, PR, issue ที่อ้างถึง แยกให้ชัดว่าอะไรคือหลักฐาน อะไรคือการอนุมาน
3. ถ้าเป็นอาการ runtime ให้จับสัญญาณจากของที่รันอยู่จริง (CPU profile, heap snapshot, trace, log) ย่อให้เหลือ "หลักฐานชิ้นเด็ด" (ฟังก์ชันบน hot path, สายการยึด object ที่รั่ว, loop ที่ทำงานโดยไม่มี input) พิสูจน์กลไกด้วยการใส่ log หรือ instrument เพิ่มก่อนเชื่อ แล้วชี้กลับไปที่ไฟล์และบรรทัด artifact ใหญ่ให้ `scout` ย่อ
4. เขียนคำตอบตามโครง: ภาพรวม → แนวคิดหลัก → flow การทำงาน → ไฟล์อยู่ไหน → จุดที่ต้องระวัง (ตัดหัวข้อที่ไม่เกี่ยวทิ้ง) หรือถ้าเป็นคำถามเลือกทาง ให้ตารางเปรียบเทียบพร้อมคำแนะนำของเราเอง
5. ทุกข้อสรุปอ้าง `file:บรรทัด` ที่อ่านมาจริง ค้นแล้วไม่เจอก็เป็นคำตอบ ห้ามแต่ง caller หรือ API ขึ้นมา

ไม่มี PR ไม่มีการร่างแบบ ถ้าการสืบสวนนำไปสู่การแก้โค้ด ให้รายงานผลก่อน แล้วเปลี่ยนไป playbook แก้บั๊กหรือฟีเจอร์

**รายงาน:** ผลการสืบสวนตามโครงข้างบน คำถาม "แน่ใจเหรอ" ต้องมีความเห็นจริงของเราพร้อมเหตุผล ถ้าสมมติฐานของคำถามผิด ให้แย้ง งานวินิจฉัย runtime ให้บอกสัญญาณที่จับได้ หลักฐานที่ย่อแล้ว วิธีพิสูจน์กลไก ตำแหน่งในโค้ด และ path ของ artifact
