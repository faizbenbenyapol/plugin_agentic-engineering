# เปิด PR

เปิดเฉพาะเมื่อผู้ใช้ขอ หรือ `CLAUDE.md` ของโปรเจกต์บอกให้ทำ

## คำอธิบาย PR

PR body คือการบรีฟหนึ่งนาทีให้ผู้รีวิวที่มี diff อยู่แล้ว ไม่ใช่สมุดแล็บ บอกว่าทำไมต้องเปลี่ยน อะไรไม่ได้รวม อาจกระทบอะไร และพิสูจน์ยังไง ประโยคสั้น identifier น้อย ใช้หัวข้อ `##` ตามลำดับนี้ หัวข้อไหนไม่มีอะไรจะพูดให้ตัดทิ้ง:

- `## Why` ปัญหาและแนวทาง 1–3 ประโยค เปิดด้วยเป้าหมายของผู้ใช้
- `## What changed` 1–3 bullet ใส่ชื่อ symbol หรือ path เฉพาะที่เป็นแกน rename ให้บอกทั้งชื่อเก่าและใหม่
- `## Scope` ต้องมีเสมอ 1–3 ข้อ: ครอบคลุมอะไร ตั้งใจไม่รวมอะไร (งานต่อ ช่องว่างที่รู้)
- `## Tradeoffs` เฉพาะทางเลือกที่ทิ้งไปซึ่งผู้รีวิวจะถามแน่ ไม่มีทางเลือกจริงก็ตัดทิ้ง
- `## Blast radius` 1–2 ประโยค: กระทบใครหรืออะไร ทำไมปลอดภัยหรือเสี่ยง และ "ข้อเท็จจริงเดียวที่ทำให้ปลอดภัย" ถ้าทำ blast radius แล้ว
- `## Verification` 1–3 bullet แต่ละข้อคือการรันจริงและผล performance ใส่ตัวเลขหลักตัวเดียวพร้อมหน่วย `ก่อน → หลัง` รายละเอียดอื่นไว้ใน artifact ที่ลิงก์

หลังหัวข้อแนบ screenshot หรือวิดีโอเมื่อมันพิสูจน์ข้ออ้าง SHA เต็ม ตารางผลรายละเอียด checklist รายไฟล์ ไว้ใน artifact ที่ลิงก์ ไม่ใส่ใน body

## ขนาดและ stack

- PR แคบห้าตัวดีกว่า PR ใหญ่ตัวเดียว
- stack คือสายโซ่ base branch: PR ราก target trunk แต่ละลูก rebase บนปลายของแม่ และ target branch ของแม่ แตกจาก trunk เฉพาะงานที่อิสระ
- เมื่อผู้ใช้ขอให้เปิด PR: เปิดแล้วโพสต์ลิงก์ ทำงานต่อจน stack ครบ ไม่ต้องเฝ้าแต่ละ PR ทันที เฝ้า CI และรีวิวเมื่อผู้ใช้ขอ
- ใช้ `gh` เป็นค่าเริ่มต้น ตรวจสถานะด้วย `gh pr view` ก่อนพูดถึงสถานะ PR

## คอมเมนต์รีวิวจากบอต

บอตรีวิวจับบั๊กจริงได้ แต่ก็แจ้งเรื่องที่ไม่ใช่ปัญหาด้วย ประเมินทีละข้อ: แก้ / ปิดพร้อมเหตุผลที่เจาะจง / ถามผู้ใช้ อย่าแก้โค้ดวนตามทุกข้อ ถ้า feedback ออกนอกเป้าหมายให้แย้ง
