# เปิด PR

เปิดเฉพาะเมื่อผู้ใช้ขอ หรือ `CLAUDE.md` ของโปรเจกต์บอกให้ทำ

## ชื่อ PR: ภาษาอังกฤษ

รูปแบบเดียวกับหัวข้อ commit `type(scope): subject` (`playbooks/delivery.md`) PR ที่มี commit เดียว ใช้หัวข้อ commit นั้นได้เลย

## คำอธิบาย PR: ภาษาไทย

body เขียนเป็นภาษาไทยทั้งหมด ให้คนที่ไม่ได้ตามงานนี้ (ผู้รีวิว หรือตัวผู้ใช้เองในอีกหลายเดือน) อ่านแล้วรู้เรื่องว่าทำไมต้องเปลี่ยน เปลี่ยนจากอะไรเป็นอะไร อะไรไม่ได้รวม อาจกระทบอะไร และพิสูจน์ยังไง โดยไม่ต้องเปิด diff ก่อน ไม่ใช่สมุดแล็บ ประโยคเต็มแต่สั้น หนึ่งความคิดต่อประโยค ศัพท์เทคนิคที่อาจไม่คุ้นให้อธิบายสั้น ๆ ในวงเล็บครั้งแรก ชื่อ symbol path และคำสั่งเป็นภาษาอังกฤษตามจริง ใช้หัวข้อ `##` ตามลำดับนี้ หัวข้อไหนไม่มีอะไรจะพูดให้ตัดทิ้ง:

- `## ทำไมต้องแก้` ปัญหาที่ผู้ใช้ปลายทางเจอ ต้นเหตุ และแนวทางที่เลือก 2–4 ประโยค เปิดด้วยเป้าหมายของผู้ใช้
- `## เปลี่ยนอะไรบ้าง` 1–4 bullet แต่ละข้อบอก ก่อน → หลัง เป็นภาษาธรรมดา แล้วตามด้วยชื่อ symbol หรือ path ที่เป็นแกน rename ให้บอกทั้งชื่อเก่าและใหม่
- `## ขอบเขต` ต้องมีเสมอ 1–3 ข้อ: ครอบคลุมอะไร ตั้งใจไม่รวมอะไร (งานต่อ ช่องว่างที่รู้)
- `## ข้อแลกเปลี่ยน` เฉพาะทางเลือกที่ทิ้งไปซึ่งผู้รีวิวจะถามแน่ พร้อมเหตุผลที่ไม่เลือก ไม่มีทางเลือกจริงก็ตัดทิ้ง
- `## ผลกระทบ` 1–2 ประโยค: กระทบใครหรืออะไร ทำไมปลอดภัยหรือเสี่ยง และ "ข้อเท็จจริงเดียวที่ทำให้ปลอดภัย" ถ้าทำ blast radius แล้ว
- `## ตรวจยังไง` 1–3 bullet แต่ละข้อคือการรันจริง ผลที่เห็น และผลนั้นแปลว่าอะไร performance ใส่ตัวเลขหลักตัวเดียวพร้อมหน่วย `ก่อน → หลัง` รายละเอียดอื่นไว้ใน artifact ที่ลิงก์

**ด่าน anti-slop ก่อนเปิด:** PR ที่ agent เขียนแทบไม่มีต้นทุน แต่ต้นทุนของคนรีวิวยังเท่าเดิม ก่อนเปิดตอบให้ได้ว่า "คนรีวิวต้องเหนื่อยกว่าเราไหม" ถ้าใช่ ให้ผ่าเป็น PR เล็ก (ราว 100–200 บรรทัดต่อ PR หรือต่อ commit ที่อ่านแยกได้) ระบุใน `## ตรวจยังไง` ว่าส่วนไหน agent เขียน ส่วนไหนผู้ใช้อ่านแล้ว และชี้ 1–3 จุดที่คนรีวิวควรอ่านละเอียด

หลังหัวข้อแนบ screenshot หรือวิดีโอเมื่อมันพิสูจน์ข้ออ้าง SHA เต็ม ตารางผลรายละเอียด checklist รายไฟล์ ไว้ใน artifact ที่ลิงก์ ไม่ใส่ใน body บรรทัด attribution ท้าย body (เช่น `🤖 Generated with ...`) คงไว้ตามรูปแบบเดิม ไม่แปล

ส่ง body ด้วย `gh pr create --title "<อังกฤษ>" --body-file <ไฟล์>` เพื่อให้ภาษาไทยและบรรทัดว่างไม่เพี้ยน

ข้อยกเว้นเหมือน commit: repo กำหนดภาษาของ PR ไว้ชัด (`CLAUDE.md`, `CONTRIBUTING.md`, PR template ภาษาอังกฤษที่บังคับ) ให้ทำตาม repo แล้วบอกผู้ใช้หนึ่งบรรทัด PR template ที่มีอยู่ ให้คงหัวข้อของ template แล้วเขียนเนื้อหาเป็นภาษาไทย

**repo ของทีม:** ภาษา template และสิ่งที่ต้องแนบ (ลิงก์ ticket screenshot การบอกว่าใช้ AI) ตาม `docs/team-rules.md` ถ้าทีมเขียน PR เป็นอังกฤษ body ก็เป็นอังกฤษ ทำ "ก่อนขอรีวิว" ใน `playbooks/team-work.md` หัวข้อ 4 ให้ครบก่อนเปิด และคอมเมนต์รีวิวจากคนในทีมใช้หัวข้อ 5 ของไฟล์นั้น

## ขนาดและ stack

- PR แคบห้าตัวดีกว่า PR ใหญ่ตัวเดียว
- stack คือสายโซ่ base branch: PR ราก target trunk แต่ละลูก rebase บนปลายของแม่ และ target branch ของแม่ แตกจาก trunk เฉพาะงานที่อิสระ
- เมื่อผู้ใช้ขอให้เปิด PR: เปิดแล้วโพสต์ลิงก์ ทำงานต่อจน stack ครบ ไม่ต้องเฝ้าแต่ละ PR ทันที เฝ้า CI และรีวิวเมื่อผู้ใช้ขอ
- ใช้ `gh` เป็นค่าเริ่มต้น ตรวจสถานะด้วย `gh pr view` ก่อนพูดถึงสถานะ PR

## คอมเมนต์รีวิวจากบอต

บอตรีวิวจับบั๊กจริงได้ แต่ก็แจ้งเรื่องที่ไม่ใช่ปัญหาด้วย ประเมินทีละข้อ: แก้ / ปิดพร้อมเหตุผลที่เจาะจง / ถามผู้ใช้ อย่าแก้โค้ดวนตามทุกข้อ ถ้า feedback ออกนอกเป้าหมายให้แย้ง
