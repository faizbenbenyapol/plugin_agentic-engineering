# แก้บั๊ก

**เราเป็นเจ้าของงานนี้ วางแผน ตรวจ พิสูจน์** หัวหน้าสืบและแก้เองเป็นค่าเริ่มต้น ส่ง agent เฉพาะตาม SKILL.md ข้อ 3

ทำแบบนักวิทยาศาสตร์ ทุกบรรทัดที่ส่งโยงไปหาหลักฐานจาก runtime ได้ ของเสริม "เผื่อไว้" ที่ "น่าจะช่วย" คือสมมติฐาน ไม่ส่ง หลักฐานหักล้างสมมติฐานไหน ให้ถอยโค้ดที่มันพาเขียนออก ส่งแค่การเปลี่ยนที่เล็กที่สุดที่หลักฐานรองรับ

## ขั้น

1. **ทำให้เกิดซ้ำเอง บน surface เดียวกับที่ผู้ใช้เจอ** (CLI รันคำสั่ง UI เปิดหน้าจอ API เรียกจริง) ยังไม่เกิด ให้สังเคราะห์ตัวกระตุ้น บีบเงื่อนไข หรือใส่ log จนเกิด ขอให้ผู้ใช้ทำซ้ำได้เฉพาะเมื่อเข้าถึงจุดนั้นไม่ได้จริง โดยบอกเหตุผลเจาะจงและหลังจากไปไกลที่สุดเท่าที่ไปได้แล้ว ถ้า "พฤติกรรมที่ถูก" ไม่ชัด (ไม่มี test สเปก หรือเอกสารบอก และตีความได้หลายแบบ) ให้ถามผู้ใช้ตาม `playbooks/kickoff.md` ก่อนแก้ ห้ามเลือกเอง เพราะการแก้บั๊กผิดทิศคือการสร้างบั๊กใหม่
2. **หาต้นเหตุแบบตัดทีละครึ่ง** ตั้งสมมติฐานหลายข้อ (ใช้ `playbooks/investigation.md` กับ subsystem ที่เกี่ยว และ `git log` หา regression) แต่ละรอบเลือกการทดลองที่ตัดพื้นที่ปัญหาได้มากที่สุด เก็บหลักฐานจาก runtime แล้วตัดทิ้ง state ไม่ชัดให้ใส่ log แล้วอ่านค่าตอนรัน ห้ามเดา ยืนยัน *กลไก* ที่รอดด้วยหลักฐาน runtime ก่อนวางแผนแก้ ถ้าต้นเหตุเห็นชัดตั้งแต่อ่านโค้ด ไม่ต้องทำพิธีตั้งหลายสมมติฐาน ให้ยืนยันสมมติฐานเดียวนั้นด้วยการรันหนึ่งครั้ง (เช่น พิมพ์ค่าที่พิสูจน์กลไก) แล้วไปต่อ
3. **ถาม "ทำไม" จนเจอจุดแรกที่โค้ดตัดสินใจผิด** แล้วถามต่อว่า state ที่ทำให้พังนั้นถูกต้องตามระบบไหม ถ้าระบบอยู่ใน state นั้นได้จริง โค้ดที่พังคือต้นเหตุ ให้รองรับตรงนั้น ถ้า state นั้นไม่ควรเกิด guard ตรงที่พังคือการซ่อนบั๊ก ให้หาว่าใครสร้าง state นั้น (guard, retry, กลืน error, clamp ค่า, ทิ้ง state คือวิธีซ่อนบั๊กที่พบบ่อย) พังเฉพาะหลัง restart ให้สงสัย state ที่บันทึกไว้ก่อน: config, cache, lock file
4. **วางแผนแก้** ถ้าข้ามขอบฟังก์ชันให้ร่างแบบก่อน (`references/design.md`) แล้วแก้ในขอบเขตที่แคบที่สุด
5. **ค้นหารูปแบบเดียวกัน** จุดอื่นที่ผิดแบบเดียวกันให้แก้ให้หมด ไม่นับว่าทำเกินโจทย์ ถ้าข้อเท็จจริงที่ชี้ขาดต้องขุดลึกกว่าจะเจอ ให้เสนอสัญญาณที่เปิดตลอดและถูก (log, assert, metric) ที่จะทำให้เห็นตั้งแต่แรก
6. **ตรวจบน surface เดิม** ขั้นตอนทำซ้ำของข้อ 1 ต้องผ่าน "สรุปไม่ได้" หรือผิด surface ไม่ใช่ผ่าน ต้องบอก unit test บอกพฤติกรรมของ branch ไม่ได้พิสูจน์ว่าบั๊กหาย
7. **เรียง commit ให้ test ที่ fail มาก่อนการแก้** (commit แรกคือ test ที่แดง commit ถัดไปคือการแก้ที่ทำให้เขียว) ทำเมื่อบั๊กมีทาง test ในเครื่องที่ถูก ถ้า test จะแพง ต้องตั้ง harness ใหญ่ mock เยอะ หรือไม่ชัด ให้ใช้การตรวจที่ใกล้ที่สุดแทน (script ทำซ้ำ, browser automation, log assertion) ไม่มี test ดีกว่ามี test แย่ (test ที่ทดสอบ mock, ผูกกับไส้ใน, พึ่งเวลา)
8. ทำ `playbooks/delivery.md`

**รายงาน:** อะไรพัง ต้นเหตุ แก้ยังไง ตรวจยังไง แปะ output ตอนพังแล้วตามด้วยตอนผ่านแบบตรงตัว และจุดอื่นที่แก้รูปแบบเดียวกัน
