# ทำงานในทีม (repo บริษัท ฝึกงาน หรือ repo ที่มีคนอื่นทำร่วม)

ใช้ควบคู่กับ playbook หลักของงาน ไม่ได้ใช้แทน เปิดไฟล์นี้เมื่อเจอสัญญาณใดสัญญาณหนึ่ง: ผู้ใช้บอกว่าเป็นงานบริษัท งานฝึกงาน หรืองานทีม, `git shortlog -sn | head` มีคนอื่นนอกจากผู้ใช้, remote เป็น org ของบริษัท หรือมี `CONTRIBUTING.md`, `CODEOWNERS`, `.github/pull_request_template.md` เจอแล้วบอกผู้ใช้หนึ่งบรรทัดว่า "repo นี้เป็นงานทีม จะใช้กติกาทีม"

## หลักใหญ่ 4 ข้อ

1. **กติกาทีมชนะค่าเริ่มต้นของสกิล** ภาษาและความถี่ของคอมเมนต์ในโค้ด รูปแบบ commit และ PR ชื่อ branch style และ process ทั้งหมดให้ตามทีม สิ่งที่ไม่เปลี่ยนคือการคุยกับผู้ใช้ การสอน และรายงานในแชท ซึ่งยังเป็นภาษาไทยตามเดิม
2. **ผู้ใช้คือคนที่ต้องตอบคำถามรีวิว ไม่ใช่ AI** ทุกบรรทัดที่ส่งต้องเป็นสิ่งที่ผู้ใช้อธิบายเองได้ต่อหน้าพี่เลี้ยง (mentor) กฎเหล็กข้อ 2 จึงเข้มขึ้น ดูหัวข้อ 4 "ซ้อมรีวิว"
3. **ของบริษัทเป็นความลับ** ไม่อ่านหรือแสดง `.env` กุญแจ token และข้อมูลลูกค้า ไม่ส่งโค้ดหรือข้อมูลบริษัทไปเว็บหรือเครื่องมือภายนอก
4. **งานคนอื่นห้ามพัง** ไม่เขียนทับ ไม่ลบ ไม่ฟอร์แมตโค้ดของคนอื่นที่งานนี้ไม่ได้แตะ ไม่เปลี่ยนของที่ใช้ร่วมกันโดยไม่ถาม

## 1. ครั้งแรกใน repo (ทำครั้งเดียวต่อ repo)

1. **ถามเรื่องนโยบาย AI ก่อนอย่างอื่น** ถามผู้ใช้ว่าบริษัทอนุญาตให้ใช้ AI กับโค้ดนี้ไหม ใช้เครื่องมือไหนได้ และห้ามส่งอะไร ถ้าผู้ใช้ยังไม่รู้ ให้ร่างคำถามสั้น ๆ ให้ผู้ใช้ไปถาม mentor ระหว่างรอคำตอบ ให้อ่านและอธิบายโค้ดได้ แต่ไม่แตะไฟล์ความลับ ถามรวมไปด้วยว่าเก็บแผนผังระบบไว้ในบอร์ด Whiteboard ของ Claude ได้ไหม (`playbooks/board.md`) ถ้าไม่ได้หรือยังไม่รู้ ใช้ทางสำรองที่เป็นไฟล์ในเครื่อง
2. **สำรวจกติกาใน turn เดียว** (ls และ grep ก่อน อ่านเฉพาะช่วงที่ใช้): `README`, `CONTRIBUTING.md`, `CODEOWNERS`, PR template, `.github/workflows/` (CI รันอะไร), config ของ lint/format/commitlint, `git log --oneline -20` (รูปแบบและภาษา commit), `git branch -r | head` (ชื่อ branch) และภาษาของคอมเมนต์ในไฟล์ใกล้งาน
3. **สรุป "กติกาทีม" ไม่เกิน 10 บรรทัด** ให้ผู้ใช้ยืนยัน: ชื่อ branch, รูปแบบและภาษาของ commit, PR template และภาษา, ภาษาคอมเมนต์, คำสั่ง test/lint/build, ใครรีวิว, ระบบ ticket ข้อที่หาไม่เจอให้ใส่เป็น "คำถามสำหรับ mentor" แทนการเดา
4. **เก็บไฟล์ส่วนตัวไม่ให้หลุดเข้า repo ทีม** ไฟล์ของสกิลนี้ (`docs/requirements/`, `docs/handoff/`, `docs/progress.md`, `docs/board.md`, `docs/system-map.md`, `.learning/`) และโน้ตกติกาทีม `docs/team-rules.md` เป็นของผู้ใช้คนเดียว
   - เช็กก่อนว่าทีมไม่ได้ใช้ path พวกนี้อยู่แล้ว: `git ls-files docs/requirements docs/handoff docs/progress.md docs/team-rules.md docs/board.md docs/system-map.md .learning | head` ถ้าชน ให้ใช้ `.personal/` แทน `docs/` ทุกที่ในงานนี้
   - เพิ่ม path ลงใน `.git/info/exclude` (ignore เฉพาะเครื่องนี้ ไม่ถูก commit) **ห้ามแก้ `.gitignore` ของทีม** เพราะเป็นไฟล์ที่ใช้ร่วมกัน
   - ทีมอยากได้เอกสารแบบนี้ใน repo (เช่นมี `docs/adr/` อยู่แล้ว) ให้เขียนตามรูปแบบของทีมแทน
   - บนคลาวด์ (`CLAUDE_CODE_REMOTE=true`) ไฟล์ที่ exclude จะไม่ถูก push ให้ส่งไฟล์ให้ผู้ใช้ก่อนจบเซสชัน
5. จดกติกาที่ยืนยันแล้วลง `docs/team-rules.md` เซสชันหลังอ่านไฟล์นี้แทนการสำรวจใหม่

## 2. รับงาน

- **งานมาจาก ticket หรือ mentor** ใส่รหัส ticket ในไฟล์รีไควร์เมนต์และชื่อ branch (ถ้าทีมทำแบบนั้น)
- **คำถามตอน kickoff ที่ผู้ใช้ตอบไม่ได้** เช่น กฎธุรกิจ พฤติกรรมที่ถูก หรือขอบเขต ห้ามเดา ให้รวมเป็นข้อความเดียวสั้น ๆ ในภาษาที่ทีมใช้ให้ผู้ใช้ส่งถามเจ้าของ ticket หรือ mentor ด้วยตัวเอง แล้วรอคำตอบก่อนทำส่วนนั้น
- **ประเมินขนาดงาน** บอกผู้ใช้คร่าว ๆ ว่างานใหญ่แค่ไหน ถ้าใหญ่กว่าที่ ticket ดูเหมือน (เกิน 1–2 วัน หรือต้องแตะหลายโมดูล) ให้แนะนำบอก mentor ตั้งแต่ต้น ไม่ใช่ตอนใกล้ส่ง
- **กำหนดเวลาติด** ติดเรื่องเดียวเกิน 45 นาทีโดยไม่คืบ ให้เสนอว่าถึงเวลาถามคนในทีม แล้วช่วยเขียนคำถาม: อยากทำอะไร ลองอะไรไปแล้ว เห็นผลอะไร (log หรือ error สั้น ๆ) และสงสัยว่าเป็นที่ไหน ถามแบบนี้คนตอบช่วยได้เร็ว และเป็นนิสัยที่ทีมชอบ

## 3. ระหว่างทำ

- **แตก branch จาก main ล่าสุด** `git fetch` แล้วแตกจาก `origin/<branch หลัก>` ตั้งชื่อตามกติกาทีม
- **ตาม main ให้ทันอย่างน้อยวันละครั้ง** ใช้ rebase หรือ merge ตามที่ทีมทำ ห้ามเขียนประวัติใหม่บน branch ที่คนอื่นดึงไปแล้ว
- **conflict (โค้ดสองคนแก้ที่เดียวกัน)** ห้ามเลือก "ของเรา" หรือ "ของเขา" ทั้งก้อน อ่านทั้งสองฝั่งให้เข้าใจว่าแต่ละฝั่งตั้งใจทำอะไร แล้วรวมให้ได้ทั้งสองอย่าง ถ้าไม่แน่ใจว่าฝั่งคนอื่นตั้งใจอะไร ให้ผู้ใช้ถามเจ้าของ commit นั้น (`git log -1 <sha>`) รันทดสอบหลังแก้ conflict ทุกครั้ง
- **ขอบเขตเท่ากับ ticket** ไม่รีแฟกเตอร์ไปด้วย ไม่รัน formatter ทั้งไฟล์ ไม่แก้ typo ไฟล์อื่น เจอปัญหาที่ไม่เกี่ยว ให้จดไว้เสนอผู้ใช้เปิด ticket แยก diff เล็กทำให้รีวิวง่ายและผ่านไว
- **โค้ดตามบ้านเดิม** pattern ชื่อ โครงสร้าง error handling และ test ให้เลียนแบบโค้ดข้างเคียงใน repo ก่อน `references/code-quality.md` ถ้าขัดกัน ให้ตามทีมแล้วบอกผู้ใช้ว่าต่างจากที่สกิลแนะนำตรงไหน
- **คอมเมนต์ในโค้ด** ใช้ภาษาและความถี่ตามทีม ถ้าทีมเขียนอังกฤษ คอมเมนต์ก็เป็นอังกฤษ และไม่ใส่ทุกฟังก์ชันถ้าทีมไม่ทำ คำอธิบายภาษาไทยเพื่อการเรียนให้ไปอยู่ในแชทและ `.learning/` แทน ไม่รู้ว่าทีมใช้แบบไหนให้ดูไฟล์ข้างเคียง แล้วใส่ไว้ในคำถามสำหรับ mentor
- **ของที่ใช้ร่วมกันต้องถามก่อนแตะ** เพิ่มหรืออัปเกรด dependency, CI, config กลาง, env ที่ใช้ร่วมกัน, migration, API ที่ทีมอื่นเรียก, ไฟล์ใน `CODEOWNERS` ของทีมอื่น ให้หยุดแล้วร่างข้อความขออนุมัติให้ผู้ใช้ส่ง

## 4. ก่อนขอรีวิว

1. **รันให้เหมือน CI** รันชุด lint, typecheck และ test ที่ CI รัน (ดูจาก workflow) ให้ผ่านในเครื่องก่อน
2. **รีวิวตัวเอง** อ่าน diff ทั้งหมดเหมือนเป็นคนรีวิว: ลบโค้ดดีบักและ `console.log` ลบไฟล์ที่ไม่ได้ตั้งใจ ตรวจว่าไม่มีความลับหรือข้อมูลจริงใน diff (`git diff origin/<branch หลัก> | grep -iE "key|secret|token|password"`)
3. **ขนาด PR** ราวไม่เกิน 400 บรรทัด และหนึ่ง ticket ต่อหนึ่ง PR งานใหญ่ให้แบ่งตาม `playbooks/large-task.md` หรือเปิด draft PR (PR ที่ยังไม่พร้อม merge) ตั้งแต่เนิ่น ๆ เพื่อให้ทีมช่วยดูทิศทาง
4. **ซ้อมรีวิว (บังคับในงานทีม)** ก่อนเปิด PR ให้ถามผู้ใช้ 3 ข้อแบบที่คนรีวิวจะถามจริง เช่น ทำไมเลือกวิธีนี้ ถ้า X พังจะเกิดอะไร ทดสอบยังไง ให้ผู้ใช้ตอบด้วยคำพูดตัวเอง ข้อไหนตอบไม่ได้ ให้อธิบายจนเข้าใจหรือเขียนโค้ดส่วนนั้นใหม่ให้ง่ายลง ห้ามเปิด PR ที่ผู้ใช้ยังอธิบายไม่ได้ ผู้ใช้สั่งข้ามได้ แต่ให้เตือนหนึ่งบรรทัด
5. **คำอธิบาย PR** ใช้ template และภาษาของทีม ลิงก์ ticket บอกวิธีทดสอบ และแนบ screenshot ถ้าเป็นงาน UI ถ้านโยบายทีมให้บอกว่าใช้ AI ช่วย ให้ใส่ตามนั้น

## 5. รับคอมเมนต์รีวิว

- **ทีละข้อ** แต่ละข้อทำหนึ่งในสามอย่าง: แก้ตามนั้น / อธิบายเหตุผลพร้อมหลักฐาน / ถามกลับเมื่อไม่เข้าใจ ไม่ข้ามข้อไหน
- **รสนิยมของทีมให้รับไว้** เช่น ชื่อตัวแปร หรือการแบ่งไฟล์ แย้งเฉพาะเรื่องที่มีหลักฐานว่าจะเกิดบั๊กหรือช้า และแย้งอย่างสุภาพ คอมเมนต์รีวิวคือการติโค้ด ไม่ใช่การติตัวคน
- **ร่างคำตอบให้ผู้ใช้โพสต์เอง** AI ไม่ตอบคอมเมนต์ในนามผู้ใช้ เว้นแต่ผู้ใช้สั่งชัด
- **แก้เป็น commit ใหม่** ระหว่างรีวิวห้าม force-push เว้นแต่ทีมทำแบบนั้น จะได้ให้คนรีวิวเห็นว่าแก้อะไร แล้วตอบว่า "แก้แล้วใน `<sha สั้น>`"
- **คอมเมนต์แบบเดิมโดนซ้ำ** เพิ่มเป็นกฎใน `docs/team-rules.md` ตาม `playbooks/correct.md` จะได้ไม่โดนครั้งที่สาม

## 6. สื่อสารกับทีม

- **standup (อัปเดตงานประจำวัน)** ผู้ใช้ขอเมื่อไร ให้ร่างจาก `git log` และ `docs/progress.md` สามหัวข้อ: เมื่อวานทำอะไร วันนี้จะทำอะไร ติดอะไร สั้น ภาษาธรรมดา ภาษาเดียวกับที่ทีมใช้
- **บอกเรื่องติดและเลื่อนตั้งแต่เนิ่น ๆ** งานจะช้ากว่าที่บอกไว้ ให้เตือนผู้ใช้ให้แจ้ง mentor ทันทีที่รู้ ไม่ใช่วันส่ง
- **ข้อความถึงคนอื่นทุกชนิดเป็นแค่ร่าง** แชท อีเมล ticket คอมเมนต์ PR ให้ผู้ใช้เป็นคนส่ง (รายการหยุดรอยืนยันใน SKILL.md ข้อ 5)

## 7. ปิดงาน

- ในงานทีม **คำอธิบาย PR คือคู่มือส่งมอบที่ทีมเห็น** ไฟล์ `docs/handoff/` ยังเขียนตาม `playbooks/handoff.md` แต่เก็บไว้ส่วนตัวตามหัวข้อ 1 ข้อ 4
- หลัง merge: อัปเดตสถานะ ticket และลบ branch ตามกติกาทีม แล้วจดบทเรียนจากรีวิวลง `.learning/`
