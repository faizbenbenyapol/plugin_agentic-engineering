# คู่มือส่งมอบ (handoff manual)

**ทุกงานที่แก้โค้ดระดับกลางและเต็มต้องจบด้วยคู่มือส่งมอบเป็นไฟล์ `.md` ใน repo** ผู้ใช้จะนำไฟล์นี้ไปทำเป็นเอกสารส่งมอบจริงเอง จึงต้องเขียนให้คนที่ไม่ได้อยู่ในแชทอ่านแล้วติดตั้ง ใช้งาน ดูแล และตรวจย้อนได้ ทำหลัง `playbooks/delivery.md` และก่อนรายงานจบงาน งานที่ยังไม่มีคู่มือยังไม่นับว่าเสร็จ

| งาน | ทำอะไร | ไฟล์ |
| --- | --- | --- |
| ผ่าน kickoff (ฟีเจอร์ งานใหญ่ รันยาว prototype ที่จะใช้จริง) | ฉบับเต็ม | `docs/handoff/<ชื่องาน>.md` ชื่อเดียวกับไฟล์รีไควร์เมนต์ |
| ระดับกลางที่ไม่ผ่าน kickoff (แก้บั๊ก รีแฟกเตอร์ performance) | ส่วนที่แก้มีคู่มือแล้ว: แก้หัวข้อที่กระทบในคู่มือนั้น และเพิ่มแถวในประวัติเวอร์ชัน ยังไม่มี: เพิ่มหนึ่งรายการ (วันที่ อาการหรือเป้าหมาย สาเหตุ แก้อะไร ตรวจยังไง ย้อนยังไง) | คู่มือเดิม หรือ `docs/handoff/CHANGELOG.md` ไฟล์เดียว ไม่สร้างไฟล์ใหม่ทุกครั้ง |
| ระดับเบา | ไม่ต้องทำ ถ้าส่วนที่แก้มีคู่มืออยู่แล้ว เพิ่มหนึ่งแถวใน "ประวัติเวอร์ชัน" ของคู่มือนั้น | — |
| งานอ่านอย่างเดียว | ไม่ต้องทำ | — |

ผู้ใช้สั่ง "ไม่ต้องทำคู่มือ" ในงานนั้นให้ข้ามได้ งานต่อเนื่องหลายเฟส ให้อัปเดตไฟล์เดิม เพิ่มแถวในประวัติเวอร์ชัน ไม่สร้างไฟล์ใหม่ทุกเฟส

## เขียนแบบประหยัดโควตา

คู่มือประกอบจากหลักฐานที่มีอยู่แล้ว **ห้ามอ่านโค้ดทั้ง repo ใหม่เพื่อเขียนคู่มือ**

1. รวบรวมใน turn เดียว: ไฟล์รีไควร์เมนต์ (ถ้ามี), `git log --oneline <base>..HEAD`, `git diff --stat <base>..HEAD`, decision log หรือ `docs/progress.md` (ถ้ามี), `.env.example` / ไฟล์ config ที่ diff แตะ และ output ของ test/build ที่รันไปแล้วใน session
2. ส่วนที่ต้องอ่านโค้ด (โครงสร้างระบบ ตัวแปร env) ให้ grep เฉพาะจุด
3. คำสั่งติดตั้งและรันที่เขียนในคู่มือต้องเคยรันผ่านจริงใน session นี้ ถ้ายังไม่เคย ให้รันหนึ่งครั้ง รันไม่ได้ (เช่น deploy จริง) ให้ติดป้าย *ยังไม่ได้รัน*
4. งานใหญ่ที่บริบทใกล้เต็ม ให้ส่ง `scout` ย่อ git log และ diff stat แทนการอ่านเอง

## กฎการเขียน

- ภาษาไทยธรรมดา ศัพท์เทคนิคใส่ภาษาอังกฤษในวงเล็บครั้งแรก เขียนให้คนนอกทีมเข้าใจ
- Markdown ล้วน หัวข้อมีเลขกำกับ ตารางธรรมดา ไม่ใช้ HTML ไม่ใช้ emoji ในหัวข้อ เพื่อให้แปลงเป็น Word/PDF ได้ตรง
- ทุกข้ออ้างสำคัญมีป้าย *รันแล้ว* *อนุมาน* หรือ *ยังไม่ได้รัน* ห้ามเขียนสิ่งที่ไม่ได้เห็นจริงใน session
- **ห้ามใส่ความลับ** (API key รหัสผ่าน token ข้อมูลส่วนบุคคล) ใส่แค่ชื่อตัวแปรและบอกว่าเอาค่ามาจากไหน
- อ้างไฟล์อื่นด้วย path แทนการคัดลอกเนื้อหาซ้ำ (รีไควร์เมนต์ ADR decision log)
- ใช้คำเดียวกับที่ใช้ในไฟล์รีไควร์เมนต์และหน้าจอจริง

## แม่แบบ

```markdown

| รายการ | ค่า |

| เวอร์ชัน | <เช่น 1.0 หรือ tag> |

## 1. สรุปสิ่งที่ส่งมอบ
ย่อหน้าเดียวจากมุมผู้ใช้ปลายทาง: ตอนนี้ทำอะไรได้ที่เมื่อก่อนทำไม่ได้

## 2. ตารางตรวจย้อนรีไควร์เมนต์ (traceability)
| รหัส | รีไควร์เมนต์ | ทำที่ไหน | ตรวจยังไง | ผล |
| --- | --- | --- | --- | --- |
| REQ-1 | | <โมดูล หรือ file> | <คำสั่ง / ขั้นที่กด> | ผ่าน (รันแล้ว) |

## 3. การเปลี่ยนจากรีไควร์เมนต์เดิม
| CR | เปลี่ยนอะไร | เพราะอะไร | อนุมัติโดย |
| --- | --- | --- | --- |

## 4. ความต้องการของระบบและการติดตั้ง
- สิ่งที่ต้องมีก่อน: <runtime + เวอร์ชัน, ฐานข้อมูล, บัญชีบริการภายนอก>
- ขั้นติดตั้ง (คำสั่งคัดลอกไปรันได้):
- ตัวแปรสภาพแวดล้อม:

| ชื่อ | ใช้ทำอะไร | ตัวอย่าง | ความลับ? | เอาค่ามาจากไหน |
| --- | --- | --- | --- | --- |

## 5. การรันและการนำขึ้นระบบ (deploy)
คำสั่งรันในเครื่อง, คำสั่ง build, ขั้น deploy (ถ้ามี) และวิธีเช็กว่าขึ้นแล้วทำงาน

## 6. คู่มือการใช้งาน
ทีละงานที่ผู้ใช้ทำ (ตาม user story): ขั้น 1, 2, 3 ... สิ่งที่ควรเห็น
ข้อความผิดพลาดที่อาจเจอ → แปลว่าอะไร → แก้ยังไง

## 7. โครงสร้างระบบสำหรับผู้ดูแล
- ภาพรวม: ส่วนหลักและข้อมูลไหลยังไง (ข้อความหรือ ASCII diagram)
- ไฟล์/โมดูลสำคัญ: path → หน้าที่หนึ่งบรรทัด
- ข้อมูลและ schema ที่เปลี่ยน, migration และลำดับการรัน
- จุดที่ต้องระวังเวลาแก้ต่อ

## 8. การทดสอบ
- คำสั่งรัน test ทั้งหมด:
- ผลล่าสุด: <บรรทัดสรุปจริง เช่น 42 passed>
- ตรวจบนหน้าจอ/API จริงแล้ว: <...>
- ยังไม่ได้ทดสอบ: <...>

## 9. ข้อจำกัด ความเสี่ยง และหนี้เทคนิค
สิ่งที่ยังไม่ทำ (อ้าง "ไม่ทำรอบนี้"), สมมติฐานที่ยังรอยืนยัน, จุดเปราะ

## 10. การย้อนกลับ (rollback)
ย้อนโค้ด ย้อน migration ปิด feature flag ข้อมูลที่ย้อนไม่ได้ต้องบอกชัด

## 11. สิ่งที่ผู้ใช้ต้องทำเอง
ขั้นที่ agent ทำแทนไม่ได้: สมัครบัญชี ตั้งค่า secret ใน CI ชี้ DNS กดอนุมัติ deploy จ่ายเงิน แต่ละขั้นบอก URL หรือเมนูที่ต้องเข้า สิ่งที่ต้องคัดลอก และใส่ค่าไว้ที่ไหน

งานต่อยอด, หนี้ที่ควรใช้คืน และข้อเสนอเพิ่มใน `CLAUDE.md` (ความผิดพลาดที่เกิดซ้ำในงานนี้ จะได้ไม่เกิดอีก)
```

## ปิดงาน

1. เปลี่ยนสถานะไฟล์รีไควร์เมนต์เป็น "ส่งมอบแล้ว"
2. commit คู่มือแยก: หัวข้อ `docs(handoff): <task name in English>` body ภาษาไทยหนึ่งบรรทัดบอกว่าคู่มือนี้ใช้ทำอะไร (`playbooks/delivery.md`)
3. รายงานจบงานบอก path คู่มือ ถ้าสภาพแวดล้อมมีเครื่องมือส่งไฟล์ให้ผู้ใช้ ให้ส่งไฟล์คู่มือด้วย
4. อ่านคู่มือทวนหนึ่งรอบก่อน commit: ทุก REQ อยู่ในหัวข้อ 2, ไม่มีความลับ, คำสั่งในหัวข้อ 4–5 ตรงกับที่รันจริง
