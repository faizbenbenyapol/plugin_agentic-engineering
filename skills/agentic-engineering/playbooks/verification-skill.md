# สร้างสกิลตรวจของโปรเจกต์

"พิสูจน์กับของจริง" ทำไม่ได้ถ้าไม่มีวิธีขับแอปจริง playbook นี้สร้างสกิลประจำโปรเจกต์ที่ `.claude/skills/verify-<app>/` ไว้เปิดแอป ใช้ฟีเจอร์แบบที่ผู้ใช้ใช้ และเก็บหลักฐาน คนอ่านคือ agent ตัวถัดไปที่ไม่เคยเห็นแอปนี้และอ่านกลางงาน ไม่ใช่มนุษย์

ใช้เมื่อ: โปรเจกต์ยังไม่มีวิธีพิสูจน์พฤติกรรม UI/CLI/service แบบ script หรือผู้ใช้ขอ "ทำสกิลตรวจให้ repo นี้"

## ขั้น

1. **สัมภาษณ์ repo ไม่ใช่ผู้ใช้** ตอบจาก codebase ถามผู้ใช้เฉพาะสิ่งที่สังเกตไม่ได้:
   - **Surface:** ผู้ใช้แตะอะไร: เว็บ, CLI/TUI, desktop, API, mobile, library ถ้ามีหลายอย่างเลือกตัวหลักแล้วจดตัวอื่นไว้
   - **รัน:** แอปเปิดในเครื่องยังไง ใช้คำสั่ง dev ที่ repo เขียนไว้ก่อน จด port, env, seed data, auth
   - **ขับ:** agent ควบคุมมันยังไง ใช้ harness ที่มีแล้วก่อน (Playwright/Cypress, expect script, endpoint ที่ curl ได้) ไม่มีค่อยใช้สูตรทั่วไป: browser/CDP สำหรับเว็บ, tmux/PTY สำหรับ CLI, HTTP สำหรับ service
   - **สังเกต:** เก็บหลักฐานอะไรได้: screenshot, transcript ของ terminal, response body, log, exit code, state ใน DB
   - **แยก instance:** เปิดสองตัวคู่กันได้ไหม (port, data dir, profile) ไม่ได้ให้เขียนบอกในสกิล ปฏิเสธการขับ instance ที่ผู้ใช้ใช้อยู่ ดีกว่าทำ session ของเขาเสีย
   ถ้า checkout build หรือเปิดไม่ได้ ให้แก้หรือรายงานให้ชัดก่อน สกิลที่เขียนบนฐานพังจะสอนขั้นตอนผิด
2. **เขียน `SKILL.md`** มี frontmatter (`name: verify-<app>` และ `description` ที่บอกชื่อแอป surface และเมื่อไรควรใช้ ไม่มี frontmatter สกิลจะไม่ถูกโหลด) และหัวข้อเหล่านี้ ทุกข้อมาจากสิ่งที่เจอจริง ห้ามเหลือ placeholder:
   - **เปิด:** คำสั่งที่เปิดแอปสำหรับตรวจ และวิธีรู้ว่าพร้อม "พร้อม" คือใช้งานได้ ไม่ใช่แค่ process ตอบ (health check ของ DB ผ่านได้ทั้งที่ init script ยังรันอยู่) ต้องเปิดได้จาก data dir ว่าง รวม migration และ seed พร้อมวิธีปิด
   - **ตรวจสุขภาพ:** การเช็กอ่านอย่างเดียวหนึ่งอย่างที่ตอบว่า "instance นี้ควรขับไหม": process ขึ้น, build ถูกตัว, port เป็นของเรา, auth ใช้ได้
   - **ขับ:** สูตรพร้อม selector หรือคำสั่งจริงจาก repo นี้ ใช้ตัวจับที่เสถียร (ARIA label, data attribute, prompt string, route) แทนพิกัดหรือลำดับ tab
   - **หลักฐาน:** เก็บอะไร เก็บที่ไหน มาตรฐาน: ใช้เส้นทางของผู้ใช้จริง ไม่ใช่ setter ภายในหรือ endpoint สำหรับ test, เก็บทั้งการกระทำและ state ที่ได้, ตรวจผลข้างเคียง (ไฟล์ที่เขียน แถวที่เพิ่ม ข้อความที่ส่ง) คู่กับสิ่งที่เห็น, mock เฉพาะตรงที่ production แยกระบบภายนอกอยู่แล้ว ถ้าใช้ dry-run ให้สังเกตว่ามันข้ามอะไรจริง อย่าเชื่อชื่อ
   - **เก็บกวาด:** ปิด instance ที่ตัวเองเปิด ห้าม kill ตามชื่อ process เก็บกวาดลบ instance และไฟล์ชั่วคราว ห้ามลบหลักฐาน หลักฐานต้องอยู่ต่อในที่ที่สกิลระบุ
   - **ตัวช่วย:** script ที่แนบต้องรันได้และมีตัวอย่างการเรียกในสกิล
3. **ทำแผนที่ฟีเจอร์** `features/README.md` เป็นสารบัญ และไฟล์ละฟีเจอร์ที่ผู้ใช้เห็น (เริ่ม 3–5 ตัวสำคัญจาก route คำสั่ง เมนู หรือเอกสาร) แต่ละไฟล์ตอบจากมุมผู้ใช้ด้วยหัวข้อ: ฟีเจอร์ย่อย, ไปถึงยังไง, ขับด้วย harness ยังไง, กับดัก ถ้า seed data ไม่มีเงื่อนไขที่ journey ต้องใช้ ให้ journey รายงานว่าไม่ผ่านและจดเหตุผลในกับดัก ห้ามลดความเข้มของ journey เพื่อให้ผ่าน
4. **พิสูจน์สกิลก่อนส่ง** รันตามคำสั่งในสกิลเองครบหนึ่งรอบ: เปิด → ตรวจสุขภาพ → ขับฟีเจอร์หนึ่งตัวในแผนที่ → เก็บหลักฐาน → เก็บกวาด แล้วยืนยันว่าหลักฐานยังอยู่ แก้สิ่งที่พังและรันเก็บกวาดทุกครั้งที่ล้ม สกิลที่ไม่เคยรันคือร่าง ไม่ใช่ผลงาน ถ้าพิสูจน์ในสภาพแวดล้อมแทน (container แทน VM จริง) ให้ระบุขั้นที่สภาพแวดล้อมแทนทำให้แต่ของจริงไม่ทำ ขั้นเหล่านั้นยังไม่ได้ตรวจ
5. **เพิ่มบรรทัดใน `CLAUDE.md`** ว่าการตรวจแอปจริงใช้สกิลนี้ และเสนอการดูแล: เมื่อแอปเปลี่ยน ให้รันทุกฟีเจอร์ในแผนที่ซ้ำและแก้สกิลให้ตรงกับของจริง ทำเป็น scheduled task ได้ถ้าผู้ใช้อยากได้

**รายงาน:** surface ที่เลือก path ของสกิล ฟีเจอร์ในแผนที่ ผลการรันพิสูจน์ (path หลักฐาน) และสิ่งที่ยังไม่ได้ตรวจ
