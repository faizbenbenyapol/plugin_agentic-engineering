# งานใหญ่ / ไม่เข้ากับ playbook ไหน

**ผลงานแรกก่อนโค้ดคือ workflow** ลำดับเฟสที่ปรับความเข้มงวดตามงาน ทำแบบวิทยาศาสตร์ และทิ้งร่องรอยการตัดสินใจที่ผู้ใช้กลับมาตรวจได้หลังปล่อยให้ทำ

ใช้กับ: migration ข้ามหลายจุด, การเปลี่ยนหลายส่วนที่ทะเยอทะยาน, งานหลายเฟสหรือหลาย PR, งานที่ผู้ใช้ปล่อยไว้แล้วจะกลับมาเชื่อผลทีหลัง แม้ playbook ฟีเจอร์จะพอเข้า หรือเมื่อไม่มี playbook ไหนเข้าเลย

## ขั้น

1. **บอกผู้ใช้ก่อนว่างานนี้ใช้โควตามาก** แบ่งเป็นหนึ่งเฟสต่อ session แล้วเพิ่มเฟส A–E ลง task list (เปิด `references/principles.md` เฉพาะข้อที่ใช้)
2. **A. ตั้งกรอบ** ทำความเข้าใจก่อนผูกมัด ห้ามเริ่มรันจนกว่าจะบอกได้ว่า:
   - "เสร็จ" คือเงื่อนไขที่ตรวจได้และพิสูจน์ว่าผิดได้
   - ขอบเขตเป็นตัวเลข: จำนวนหน่วยงานโดยประมาณ แรงงาน และสิ่งกีดขวางที่เจอตอนสำรวจ
   - ระดับความเข้มงวด เอียงไปทางสูง ทางเดียวย้อนไม่ได้หรือกระทบกว้างได้มากขึ้น ขั้นที่ย้อนได้และเสี่ยงต่ำได้น้อยลง ความเข้มงวดคือด่านและหลักฐาน ไม่ใช่ "พยายามมากขึ้น"
   ตั้งกรอบด้วย `playbooks/kickoff.md`: ถามเรื่องที่ผู้ใช้ต้องตัดสินให้ครบรอบเดียวตอนต้น เพื่อให้เฟสที่เหลือรันยาวได้ไม่ต้องหยุด และตกลง checkpoint ที่ผู้ใช้อยากเห็น นำเสนอกรอบและข้อแลกเปลี่ยนก่อนผูกมัดงานยาว ถ้าผู้ใช้อยู่ ให้รอยืนยันกรอบหนึ่งครั้งสำหรับงานหลายชั่วโมง ถ้าผู้ใช้ให้อิสระเต็มหรือไม่อยู่ ให้เขียนกรอบลง decision log เป็นแถวแรกแล้วเริ่มเลย ไม่ต้องรอ
3. **B. ออกแบบ workflow** แตกเป็นหน่วยที่ลงได้เอง เรียงจากสิ่งที่ไม่รู้และเสี่ยงที่สุดก่อน scaffold และการตรวจมาก่อนฟีเจอร์
   - สร้าง harness ตรวจก่อนลงมือ พร้อม baseline จาก state ก่อนเปลี่ยน ผลตรวจจะอ่านเป็น "ค่าเก่า vs ค่าใหม่"
   - การตัดสินใจทางเดียวย้อนไม่ได้ ให้ร่างแบบตาม `references/design.md` งาน mechanical ที่รูปชัดแล้วข้ามได้ ร่างแบบซ้ำบนดีไซน์ที่ตกลงแล้วคือ over-engineering
   - ตัดสินว่าอะไรแตกขนาน แตกเฉพาะตามรอยต่อจริง แต่ละ agent มี worktree ของตัวเอง อย่าแตกเกิน
   - งานที่ทำซ้ำหลายหน่วย ให้สร้างคานงัด (codemod, script) ก่อนแตกงาน
   - เขียนรายการเฟสที่ออกแบบลงไฟล์ (`docs/plans/<ชื่อ>.md`) นี่คือสิ่งที่ผู้ใช้รีวิว งานหลาย PR ให้แต่ละ PR มีหัวข้อของตัวเอง: ขึ้นกับอะไร ไฟล์ที่แตะ สิ่งที่สร้าง สิ่งที่จะเห็น และวิธีตรวจ
   แล้วใส่ขั้นที่ออกแบบลง task list ระหว่างเฟส C กับ D
4. **C. วนลูป** แต่ละหน่วยคือการทดลอง: บอกสมมติฐาน เปลี่ยนเล็กที่สุด วัดเทียบเงื่อนไขบนของจริง เดินหน้าก็เก็บ ไม่เดินก็ถอย ตรวจทีละหน่วยก่อนเริ่มหน่วยถัดไป ไม่รวมไปตรวจตอนท้าย
   - ตรวจจาก artifact เสมอ ไม่ใช่รายงานของ agent ผ่านง่ายเกินไปให้สงสัยวิธีตรวจก่อน
   - งานที่ส่ง agent ต้องมีคนตัดสิน agent ที่โกงด่าน ให้รีเซ็ตและทำ brief ให้รัดกุมขึ้น ถ้าด่านเองผิด ให้แก้ด่านเป็นงานแยก ไม่ใช่อ้อมมัน
   - คำตัดสิน: ผ่าน / ไม่ผ่าน / สรุปไม่ได้ ห้ามซ่อนผลลบ
5. **D. เก็บร่องรอย** decision log ตาม `references/decision-log.md` บันทึกทีละแถวเมื่อแต่ละขั้นเสร็จ ไม่ใช่เขียนทีเดียวตอนจบ งานระดับนี้ควร commit log ไว้ให้ผู้รีวิวอ่านใน PR
6. **E. ตรวจและส่งคืน** ตรวจทั้งก้อนเทียบเงื่อนไขของเฟส A บนผลิตภัณฑ์จริง ไม่ใช่แค่ harness การแก้ที่เกิดซ้ำระหว่างทางให้เปลี่ยนเป็นด่าน lint check หรือ script

**รายงาน:** workflow ที่ออกแบบ ระดับความเข้มงวดและเหตุผล path ของ plan และ decision log อะไรผ่านเงื่อนไขแล้ว อะไรยังค้าง และหัวข้อ "ควรดู"
