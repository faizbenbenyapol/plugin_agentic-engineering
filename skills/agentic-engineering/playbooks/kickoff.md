# ตั้งโจทย์ร่วม และถามกลับระหว่างทาง

**ผู้ใช้กับ agent ต้องเข้าใจงานตรงกันก่อนลงมือ** ทั้งข้างนอก (ผลที่ผู้ใช้จะเห็น) และข้างใน (โค้ดส่วนไหนจะเปลี่ยน อย่างไร ทำไม) งานจึงเป็นกล่องใส (white box) ไม่ใช่กล่องดำที่ผู้ใช้สั่งแล้วไม่รู้ว่า agent ทำอะไรลงไป เมื่อตกลงกันแล้ว agent ทำงานยาวได้โดยไม่ต้องหยุดถามเรื่องที่ตกลงไว้

ใช้กับ: ฟีเจอร์, งานใหญ่, งานรันยาว, รีแฟกเตอร์ที่เปลี่ยนสิ่งที่ผู้ใช้เห็น, บั๊กที่ "พฤติกรรมที่ถูก" ยังไม่ชัด และคำขอที่ตีความได้หลายแบบ

ข้ามได้: งานเบา, บั๊กที่พฤติกรรมที่ถูกชัดอยู่แล้ว (test หรือสเปกบอกไว้), งานอ่านอย่างเดียว และเมื่อผู้ใช้สั่ง "ตัดสินใจเองได้"

## ขั้น

1. **สำรวจก่อนถาม** อ่านโค้ดส่วนที่เกี่ยวแบบแคบ เพื่อถามเฉพาะสิ่งที่โค้ดตอบไม่ได้ ห้ามถามสิ่งที่หาเองได้ (ภาษา framework มี test ไหม ใครเรียกฟังก์ชันนี้)

2. **ทวนความเข้าใจ** เขียน "ผมเข้าใจว่า" ด้วยภาษาธรรมดา: ทำเพื่อใคร เสร็จแล้วผู้ใช้จะเห็นอะไร และส่วนของระบบที่จะแตะ (ไฟล์ละหนึ่งบรรทัดว่ามีหน้าที่อะไร) ส่วนนี้ใช้แทน "แผนที่งาน" ของ learn-while-building ได้

3. **ถามเป็นรอบ** เรียงตามต้นทุนถ้าเดาผิด เรื่องที่แก้ทีหลังแพงถามก่อน ครอบคลุมหมวดเหล่านี้เท่าที่งานมีเรื่องเปิด:
   - **เป้าหมายและผู้ใช้:** ใครใช้ ใช้ตอนไหน ปัญหาจริงคืออะไร
   - **ขอบเขต:** ทำอะไร ไม่ทำอะไรในรอบนี้ ฟีเจอร์ย่อยที่เราคิดว่าควรมีแต่ผู้ใช้ไม่ได้พูด ต้องถามว่า "อันนี้ทำด้วยไหม" ทุกข้อ
   - **พฤติกรรมและกรณีขอบ:** ค่าว่าง ค่าผิดรูป ข้อมูลซ้ำ ทำพร้อมกัน error แล้วผู้ใช้เห็นอะไร
   - **ข้อมูลและกฎธุรกิจ:** ตัวเลข การปัดเศษ สิทธิ์ เงิน เวลาและเขตเวลา
   - **ข้อจำกัด:** library ที่ห้ามหรือต้องใช้ ความเร็ว ความเข้ากันได้กับของเดิม
   - **เกณฑ์เสร็จ:** ผู้ใช้จะตรวจยังไงว่าเสร็จ (ขั้นตอนที่กดหรือคำสั่งที่รัน)
   - **วิธีทำงาน:** ให้ถามระหว่างทาง หรือทำยาวแล้วสรุปทีเดียว อยากเห็น checkpoint ตรงไหน

   ทุกคำถามมี 3 ส่วน ผู้ใช้จึงตอบได้เร็วและเรียนไปด้วย:
   - **ทำไมต้องถาม:** ถ้าเลือกผิด จะเกิดอะไร
   - **ตัวเลือก 2–4 ข้อ** พร้อมข้อแลกเปลี่ยนสั้น ๆ
   - **คำแนะนำของเรา** เป็นตัวเลือกแรก พร้อมเหตุผล

   มีเครื่องมือถามแบบตัวเลือก (เช่น AskUserQuestion) ให้ใช้ ครั้งละไม่เกิน 4 ข้อ เกินให้แบ่งรอบ ผู้ใช้ตอบ "ตามที่แนะนำ" แปลว่ารับค่าแนะนำทุกข้อที่ยังไม่ได้ตอบ

   **ถามเป็นต้นไม้การตัดสินใจ (design tree)** ผู้ใช้ต้องการให้เก็บรีไควร์เมนต์ละเอียดที่สุด: การตัดสินใจหนึ่งข้อแตกเป็นข้อย่อยที่ขึ้นกับมัน แต่ละรอบให้ถามเฉพาะ **แนวหน้า (frontier)** คือข้อที่ข้อก่อนหน้าตอบครบแล้ว ข้อที่คำตอบขึ้นกับข้อที่ยังเปิดในรอบเดียวกันให้รอรอบหลัง รวมคำถามทั้งแนวหน้าไว้ในข้อความเดียวต่อรอบ เพราะทุกรอบส่งบริบททั้งหมดซ้ำ ผู้ใช้ตอบแล้วคำนวณแนวหน้าใหม่ **ระดับกลางไม่เกิน 2 รอบ** เรื่องที่เหลือจดในหัวข้อ "คำถามที่ยังเปิด" พร้อมคำแนะนำให้ผู้ใช้แก้ในไฟล์ได้ **งานใหญ่หรือโปรเจกต์ใหม่** ถามต่อจนแนวหน้าว่าง คือทุกกิ่งถูกตัดสินหรือถูกจดเป็นสมมติฐานอย่างเปิดเผย ไม่มีข้อไหนถูกเดาเงียบ ๆ เรื่องที่เป็น **ข้อเท็จจริง** (โค้ดทำอะไร library รองรับไหม) เป็นหน้าที่เราหาเอง ส่วน **การตัดสินใจ** เป็นของผู้ใช้ ถ้าไม่ใช้ AskUserQuestion ให้ใช้รูปแบบนี้ และเขียนให้คำว่า "ใช่" แปลว่ารับคำแนะนำ:

   ```
   ❓ **Q1 – <หัวข้อ>**: <คำถาม ทำไมต้องถาม ตัวเลือก>
   ➡️ แนะนำ: <คำตอบที่แนะนำ + เหตุผลหนึ่งบรรทัด>
   ```

   **หยุดถาม** เมื่อแนวหน้าเหลือแต่เรื่องที่เดาผิดแล้วแก้ง่ายและไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น เรื่องพวกนั้นตัดสินเองแล้วจดเป็นสมมติฐาน ห้ามถามเพื่อโยนการตัดสินใจทางเทคนิคที่เราควรรู้ดีกว่า งานที่มีหน้าจอให้ถามหมวด UX ตาม `anti-ai-ui` ขั้น 0 ในรอบเดียวกันด้วย

4. **เขียนไฟล์รีไควร์เมนต์ลง repo** ทุกงานที่ผ่าน kickoff (ยกเว้นบั๊กที่ถามแค่ว่าพฤติกรรมที่ถูกคืออะไร และคำขอกำกวมที่ถามข้อเดียวแล้วชัด ซึ่งเขียนข้อตกลงในแชทพอ) ให้เขียน `docs/requirements/<ชื่องาน>.md` ตาม `references/requirements-template.md` (ระดับกลางใช้ฉบับย่อ งานใหญ่ใช้ฉบับเต็ม) สถานะ "ร่าง" แล้วส่งให้ผู้ใช้อ่าน ไฟล์นี้แทน `docs/specs/` เดิม (repo ที่มี `docs/specs/` อยู่แล้วให้ใช้ที่เดิม) และในแชทสรุปเป็นข้อตกลงงานสั้น ๆ ตามนี้:

   ```
   **ข้อตกลงงาน: <ชื่องาน>**
   - เป้าหมาย / ใครได้อะไร:
   - ทำ:
   - ไม่ทำรอบนี้:
   - พฤติกรรมและกรณีขอบ:
   - เกณฑ์เสร็จ (ตรวจยังไง):
   - แผน: ขั้น 1..n แต่ละขั้นแตะอะไร (ไฟล์หรือโมดูล) และพิสูจน์ยังไง
   - ผมตัดสินเองได้: <เรื่องเทคนิคที่ย้อนได้ และไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น>
   - จะกลับมาถามเมื่อ: <เรื่องที่ยังเปิด หรือสถานการณ์ที่ต้องให้ผู้ใช้ตัดสิน>
   - สมมติฐานที่ใช้: <...>
   ```

   ข้อตกลงในแชทเป็นแค่สรุป ตัวจริงคือไฟล์ ถ้าสองที่ขัดกันให้ยึดไฟล์

5. **วางแผนโมเดล** เติมคอลัมน์ "โมเดลที่แนะนำ" ในตารางแผนตาม `references/model-routing.md` แล้วบอกผู้ใช้หนึ่งบรรทัดว่าขั้นไหนควรสลับ `/model` และจุดไหน `/clear` ได้

6. **รอยืนยันหนึ่งครั้ง แล้วลงมือยาว** ผู้ใช้อยู่: รอคำตอบก่อนแก้ไฟล์แรก ได้ยืนยันแล้วเปลี่ยนสถานะไฟล์เป็น "ยืนยันแล้ว (<วันที่>)" และ commit ไฟล์นี้เป็น commit แรกของงาน ผู้ใช้ไม่อยู่ (scheduled task หรือบอกว่าจะกลับมาดู): ใช้ค่าแนะนำทุกข้อ คงสถานะ "ร่าง" ติดป้าย **รอยืนยัน** ไว้บนสุดของรายงาน แล้วทำต่อเฉพาะส่วนที่ย้อนได้

## ด่านตรวจรีไควร์เมนต์ (ระหว่างทำ)

ไฟล์รีไควร์เมนต์คือสิ่งที่ใช้เทียบตลอดงาน ไม่ใช่เอกสารที่เขียนแล้วทิ้ง ทำแบบประหยัด: grep เฉพาะแถว `REQ-`/`EDGE-` ที่ slice นี้ครอบคลุม ไม่อ่านไฟล์ทั้งไฟล์ซ้ำ

- **ก่อนเริ่มแต่ละ slice:** อ่านแถวที่ slice ครอบคลุมตามตารางแผน
- **หลังจบแต่ละ slice:** เทียบผลจริงกับเกณฑ์ยอมรับทีละข้อ ผ่าน / ไม่ผ่าน / สรุปไม่ได้ พร้อมหลักฐาน
- **ก่อนรายงานจบ:** เดินครบทุก REQ และ EDGE ข้อที่ไม่มีหลักฐานห้ามนับว่าเสร็จ
- **เจอว่าทำตามไฟล์ไม่ได้ ไม่ควรทำ หรือกำลังจะทำต่างจากไฟล์** (ทางเทคนิคไม่ไหว ข้อขัดกันเอง เจอทางที่ดีกว่า หรือผู้ใช้สั่งเพิ่มกลางทาง) **หยุดส่วนที่เกี่ยวแล้วถามก่อนเสมอ** ห้ามเปลี่ยนแล้วค่อยบอก ใช้รูปแบบคำขอเปลี่ยน:

  ```
  🔁 **คำขอเปลี่ยน CR-<เลข>** กระทบ: REQ-3
  - ไฟล์บอกว่า: <...>
  - เจออะไร: <หลักฐาน file:บรรทัด หรือผลที่รัน>
  - ทางเลือก: ก) <...> ข) <...> (พร้อมผลกระทบต่อเวลาและสิ่งที่ผู้ใช้เห็น)
  ➡️ แนะนำ: <...>
  ```

  งานส่วนที่ไม่ขึ้นกับคำตอบทำต่อได้ ผู้ใช้อนุมัติแล้วแก้ไฟล์ เพิ่มแถวใน "ประวัติการเปลี่ยน" และ commit พร้อมโค้ดที่เกี่ยว ผู้ใช้ไม่อยู่: ทำตามไฟล์เดิมถ้ายังทำได้ ไม่งั้นเลือกทางที่ย้อนได้แล้วจด CR เป็น "รอยืนยัน"
- **เรื่องเทคนิคที่ย้อนได้และไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น** (อยู่ในหัวข้อ "ผมตัดสินเองได้") ไม่ต้องออก CR แต่ถ้ามันทำให้ตารางแผนเปลี่ยน ให้แก้ตารางแผนใน commit เดียวกัน

## ระหว่างทำ: ถามกลับเมื่อไม่แน่ใจ

แยกความไม่แน่ใจเป็น 3 แบบก่อนตัดสินว่าจะถามไหม:

| แบบ | ตัวอย่าง | ทำ |
| --- | --- | --- |
| หาเองได้ | ฟังก์ชันนี้ใครเรียก library ทำแบบนี้จริงไหม | อ่านหรือรันเอง ห้ามถาม |
| เทคนิคที่ย้อนได้ และผู้ใช้ไม่เห็นความต่าง | ชื่อตัวแปร แยกไฟล์ไหน ใช้ Map หรือ object | ตัดสินเอง แล้วอธิบายเหตุผลในบล็อกสอน |
| ผู้ใช้ต้องตัดสิน | พฤติกรรมที่ข้อตกลงไม่ได้พูดถึง เพิ่มหรือตัดฟีเจอร์ กฎธุรกิจ หน้าตาและการใช้งาน สถาปัตยกรรม หรือเจอว่าข้อตกลงเดิมผิด | ถาม ห้ามเดา |

- **ถามแบบเดียวกับขั้น 3:** ทำไมต้องถาม ตัวเลือก และคำแนะนำ พร้อมบอกว่าเจออะไรถึงต้องถาม
- **ผู้ใช้อยู่:** ถามทันที งานส่วนที่ไม่ขึ้นกับคำตอบทำต่อได้ ส่วนที่ขึ้นกับคำตอบให้รอ
- **ผู้ใช้ไม่อยู่:** เลือกทางที่ปลอดภัยและย้อนได้ที่สุด จดเป็น "สมมติฐานรอยืนยัน" ลง decision log (`references/decision-log.md`) แล้วทำต่อ รายงานไว้บนสุดตอนจบ
- **เจองานที่น่าทำแต่อยู่นอกข้อตกลง** ห้ามทำเงียบ ๆ ถามว่า "อันนี้ทำด้วยไหม" ถ้าผู้ใช้อยู่ ไม่งั้นเขียนเป็นข้อเสนอท้ายรายงาน
- **ข้อตกลงเปลี่ยน** ผ่านคำขอเปลี่ยน (หัวข้อ "ด่านตรวจรีไควร์เมนต์") เสมอ ห้ามแก้ไฟล์รีไควร์เมนต์ก่อนผู้ใช้อนุมัติ
- **งานยาว** ส่ง checkpoint สั้น ๆ ตามจุดที่ตกลงไว้: ทำอะไรเสร็จ ตัดสินอะไรไปเอง ต่อไปจะทำอะไร

## ระดับการถาม

| ผู้ใช้พูด | ผล |
| --- | --- |
| "ถามละเอียด" (ค่าเริ่มต้น) | ตามไฟล์นี้ทั้งหมด |
| "ตัดสินใจเองได้" | ข้ามขั้น 3 ใช้ค่าแนะนำแล้วเขียนข้อตกลงให้อ่านก่อนเริ่ม ระหว่างทางถามเฉพาะรายการหยุดรอยืนยันใน SKILL.md ข้อ 5 และเรื่องที่ทำให้ข้อตกลงผิด ที่เหลือจดเป็นสมมติฐาน |

ถ้าผู้ใช้บอกให้จำ ให้บันทึกในโปรไฟล์ผู้เรียน (`ระดับการถาม:`)

## รายงานจบงาน

เพิ่มหัวข้อ **ใครตัดสินอะไร** ในรายงาน:
- ผู้ใช้ตัดสิน: <ข้อที่ตอบในขั้น 3 หรือระหว่างทาง>
- ผมตัดสินเอง: <เรื่อง + เหตุผลหนึ่งบรรทัด>
- ยังรอยืนยัน: <สมมติฐานที่ใช้ไป และผลถ้าคำตอบต่างออกไป>

และสรุป REQ/EDGE เป็นตัวเลข (ผ่าน x/y) พร้อมรายการข้อที่ไม่ผ่านหรือสรุปไม่ได้ ตารางทีละข้อเขียนในคู่มือส่งมอบหัวข้อ 2 ไม่ต้องพิมพ์ซ้ำในแชท แล้วเปลี่ยนสถานะไฟล์เป็น "ส่งมอบแล้ว" เมื่อทำคู่มือส่งมอบ (`playbooks/handoff.md`) เสร็จ
