# ส่งมอบ (commit และ PR)

ทำท้ายทุก playbook ที่แก้โค้ด playbook ที่อ่านอย่างเดียวไม่ต้องทำ ระดับเบาทำแค่หัวข้อ Commit **ระดับกลางและเต็ม ทำต่อด้วย `playbooks/handoff.md` (คู่มือส่งมอบ) เสมอ** ก่อนรายงานจบงาน

**ค่าเริ่มต้นคือ commit ในเครื่องบน branch งาน** push และเปิด PR เฉพาะเมื่อผู้ใช้ขอ หรือ `CLAUDE.md` ของโปรเจกต์บอกให้ทำ **บนคลาวด์ (`CLAUDE_CODE_REMOTE=true`) ให้ push branch งานก่อนจบ** เพราะ VM ถูกเรียกคืนได้ สิ่งที่ต้องหยุดรอยืนยันดูรายการเดียวใน SKILL.md ข้อ 5 เปิด PR ใช้ `playbooks/pull-request.md`

## Worktree และ branch

- ทำงานบน branch แยกจาก main ไม่แก้บน main ตรง ๆ (ยกเว้นผู้ใช้หรือ repo บอกให้ทำบน main) agent ที่ทำขนานได้ worktree คนละอัน
- branch สกปรกด้วยงานอื่นที่ไม่เกี่ยว: แยก patch ออก เปิด worktree ใหม่ แล้วค่อย apply
- worktree พันกันจนแก้ยาก: เริ่มใหม่จาก main แล้วทำซ้ำแบบน้อยที่สุด

## Commit

- commit บ่อย แต่ละ commit ควรลงได้เอง และอ่านเรียงแล้วเป็นเหตุผล: test ที่ fail ก่อนการแก้, commit ลบก่อนการปรับรูป, baseline ก่อนการเปลี่ยน, scaffold ก่อนฟีเจอร์ วางลำดับนี้ตั้งแต่ตอน commit จะได้ไม่ต้องจัดใหม่ทีหลัง
- การแก้ทีหลังให้เป็น commit ใหม่ ถ้าเป็นของ commit ก่อนหน้าให้ใช้ `git commit --fixup=<sha>` แล้วก่อนส่งค่อยรวมด้วย `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>` (ไม่ต้องโต้ตอบ) จัดลำดับใหม่ทั้งชุดเมื่อจำเป็นด้วย `git reset --soft <base>` แล้ว commit ใหม่ทีละกลุ่มไฟล์ ห้ามเขียนประวัติใหม่บน branch ที่ push ไปแล้วโดยผู้ใช้ไม่ได้ขอ
- stage เฉพาะไฟล์ที่ตั้งใจ (`git add <files>`)
- ก่อน commit อ่าน diff ทั้งหมดอีกรอบตาม "เช็กก่อนส่ง" ใน `references/code-quality.md`: ลบโค้ดดีบัก ของ "เผื่อไว้" ที่ไม่มีหลักฐาน และ import ที่ไม่ใช้ ตรวจว่าฟังก์ชันที่แก้มีคอมเมนต์ภาษาไทยที่ยังตรงกับโค้ด
- รัน lint และ typecheck ของ repo ก่อน push ห้ามข้าม hook คำเตือนที่มีอยู่ก่อนแล้วและไม่เกี่ยวกับงานนี้ ไม่ต้องแก้ (จะทำให้ diff บวม) ให้รายงานไว้บรรทัดเดียว repo ที่ไม่มี config lint ไม่ต้องเพิ่มเอง

## ข้อความ commit: หัวข้ออังกฤษ รายละเอียดไทย

**หัวข้อ (บรรทัดแรก) เป็นภาษาอังกฤษ** แบบ Conventional Commits `type(scope): subject` ไม่มีจุดท้าย ไม่เกินราว 72 ตัวอักษร type เช่น `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `perf` scope คือส่วนของระบบ subject เป็นคำสั่ง และใส่ชื่อ symbol จริงถ้ามันคือแกนของการเปลี่ยน เช่น `fix(cart): stop double charge when retrying checkout`

**รายละเอียด (body) เป็นภาษาไทย** เว้นหนึ่งบรรทัดหลังหัวข้อ เขียนให้คนที่เปิด `git log` อีกครึ่งปีข้างหน้ารู้เรื่องโดยไม่ต้องอ่าน diff ไม่ทวนหัวข้อ ใช้โครงนี้ ข้อไหนไม่มีให้ตัด:

```
fix(cart): stop double charge when retrying checkout

ปัญหา: ลูกค้ากดชำระเงินซ้ำตอนเน็ตช้า ระบบตัดเงินสองครั้ง
เพราะ retry ส่ง request ใหม่โดยไม่มีรหัสกันซ้ำ

แก้ยังไง: สร้าง idempotency key (รหัสกันทำซ้ำ) ครั้งเดียวต่อคำสั่งซื้อ
แล้วส่งรหัสเดิมทุกครั้งที่ retry ฝั่ง payment จึงรู้ว่าเป็นรายการเดิม

ตรวจยังไง: test ใหม่จำลองกดซ้ำ 3 ครั้ง เดิมตัดเงิน 3 ครั้ง ตอนนี้ 1 ครั้ง

Co-Authored-By: ...
```

- ศัพท์เทคนิคทับศัพท์ได้ ชื่อ symbol, path และคำสั่งเป็นภาษาอังกฤษตามจริง
- trailer ท้าย commit (`Co-Authored-By:`, `Claude-Session:`, `Fixes #12`) เป็นภาษาอังกฤษตามรูปแบบเดิม ห้ามแปล
- commit เล็กมาก (แก้ typo, import) body ภาษาไทยบรรทัดเดียวพอ
- ส่ง message หลายบรรทัดด้วย heredoc หรือ `git commit -F <ไฟล์>` ไม่ใช้ `-m` ซ้อนหลายอันจนบรรทัดว่างหาย
- **ข้อยกเว้น:** `CLAUDE.md`, `CONTRIBUTING.md` หรือ commitlint ของ repo กำหนดภาษาไว้ชัด ให้ทำตาม repo แล้วบอกผู้ใช้หนึ่งบรรทัด ไม่เดาจากประวัติ commit เก่าว่าเป็นภาษาอังกฤษ
