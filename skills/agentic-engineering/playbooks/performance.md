# Performance

**เราเป็นเจ้าของเรื่องราวของตัวเลข** ทุกการแก้ผูกกับการวัด ห้ามอ่าน source แทนการวัด

มีสองแบบ:
- **แก้ครั้งเดียว** มีความช้าที่วัดได้ ต้องหาและแก้เทียบ baseline
- **ไต่ตัวเลข (hillclimb)** ดันตัวชี้วัดเดียวให้ดีขึ้นต่อเนื่องจนถึงเป้า วนสมมติฐานทีละข้อ

## แก้ครั้งเดียว

1. **จับ baseline บน surface จริง** (trace, profile, เวลาของ flow ที่ผู้ใช้รอ) ตรวจ baseline และทุกตัวเลขหลังจากนี้ด้วย `references/benchmark.md`
2. **สืบสวนเพื่อตั้งสมมติฐาน** ห้ามอ้างเพดาน performance โดยไม่ได้รันก่อน ลองตามลำดับ ถูกสุดก่อน แล้วหยุดเมื่อข้อแรก ๆ ถึงเป้าแล้ว:
   1. ไม่ต้องทำ (หยุดงานที่ไม่มีใครใช้ผล ดีกว่าทำให้ถูกลง)
   2. ทำ แต่ไม่ทำซ้ำ (cache, memo)
   3. ทำให้น้อยลง
   4. ทำทีหลัง (lazy, defer)
   5. ทำตอนที่ผู้ใช้ไม่ได้รอ (background, prefetch)
   6. ทำพร้อมกัน
   7. ทำให้ถูกลง (อัลกอริทึม โครงสร้างข้อมูล)
3. **วางแผนแก้จาก trace** ถ้าข้ามขอบฟังก์ชันให้ร่างแบบก่อน แก้ ตรวจ diff จับ trace หลังแก้ ลองทีละอย่าง ตรวจก่อนลองอย่างถัดไป
4. **เทียบ artifact ด้วยเครื่องมือ** (แปลง JSON เข้า sqlite แล้ว query, diff) ไม่ใช่ดูด้วยตา "สรุปไม่ได้" หรือผิด surface ไม่ใช่ผ่าน
5. ใส่ตัวเลขใน PR แล้วทำ `playbooks/delivery.md`

**รายงาน:** baseline, ตัวเลขหลังแก้, ส่วนต่าง, ตัวจำกัด (ทำไมไม่ดีกว่านี้สองเท่า), path ของ artifact

## ไต่ตัวเลข (hillclimb)

แจ้งผู้ใช้ก่อนเริ่มว่า hillclimb ใช้โควตามาก และตกลงเพดานจำนวนรอบ วินัยแกน: เปลี่ยนหนึ่งอย่าง วัดหนึ่งครั้ง เก็บหรือถอย ห้ามซ้อนการเปลี่ยนที่ยังไม่ได้ทดสอบ ห้ามอ้างว่าชนะจากการอ่านโค้ด

1. **ทำความเข้าใจ workload ก่อนเลือกตัวชี้วัด** สืบสวนเป้าหมาย ระบุมิติของ workload ที่ขยับผลได้ (ขนาดข้อมูล ประวัติ state concurrency) เลือกเคสที่ทำให้อาการที่ผู้ใช้บ่นเกิดซ้ำ ถ้าไม่มีเคสไหนทำซ้ำได้ ให้แก้การทำซ้ำก่อน แล้วกำหนดตัวชี้วัดเดียว ทิศที่ถือว่าดีขึ้น และเงื่อนไขหยุดที่ตรวจได้ ซึ่งมีทั้งเป้าและจำนวนรอบขั้นต่ำ เช่น "ดีกว่า baseline อย่างน้อย 50% และลองอย่างน้อย 10 รอบ" (กันชนะเพราะโชคช่วงแรก)
2. **สร้าง harness วัด พิสูจน์ว่ามันไวพอ แล้วแช่แข็ง** รัน workload ที่ต่างกันให้เห็นว่าเคสเป้าหมายแสดงอาการ และเคสง่ายแยกออกตามคาด ตรวจ harness ด้วย `references/benchmark.md` ให้มันพิมพ์จำนวน error และปริมาณงานที่ทำจริง หลังแช่แข็ง คำสั่งเดียวต้องให้ตัวเลข (median ของ N รอบ) บันทึก baseline และ test ชุดที่ต้องเขียวเสมอก่อนเปลี่ยนอะไร
3. **เปิด decision log** (`references/decision-log.md`) แถวละการลอง ใช้ 6 คอลัมน์ปกติ: `phase` = รหัสการลอง (เช่น `h3`), `decision` = การเปลี่ยน, `why` = สมมติฐานและกลไก, `evidence` = `ก่อน → หลัง (ส่วนต่าง), test เขียว/แดง, commit`, `result` = `เก็บ` หรือ `ถอย` อ่าน log ก่อนลองทุกครั้ง ไม่ commit เข้า repo
4. **ทุกสมมติฐานต้องระบุกลไก** เช่น "เลื่อน X ออกจาก boot path เพราะมันบล็อก first paint" ไม่ใช่ "ลอง memo อะไรสักอย่าง" เรียงตามลำดับ 7 ข้อข้างบน
5. **วนทีละสมมติฐาน** แก้ในขอบเขตแคบ วัดก่อนและหลังด้วย harness ที่แช่แข็ง รัน test ชุดที่ต้องเขียว เก็บเฉพาะเมื่อตัวเลขขยับเกิน noise และ test เขียว ไม่งั้นถอยทั้งหมด commit ละหนึ่งการแก้ที่เก็บ stage เฉพาะไฟล์ที่แก้ (`git add <files>` ห้าม `-A`) บันทึก log ทุกครั้งทั้งเก็บและถอย ลองขนานเฉพาะเมื่อผู้ใช้สั่ง แต่ละตัวใน worktree ของตัวเอง
6. **ดันผ่านที่ราบแรก** ถอยติดกันหลายรอบ ให้เปลี่ยนหมวด รวมข้อที่เกือบได้ อ่าน source ใหม่ หรือลองอะไรที่แรงกว่า ความถูกต้องและความเรียบง่ายสำคัญกว่าตัวเลข ถอยการชนะที่ทำพฤติกรรมพัง เก็บการทำให้ง่ายที่ตัวเลขเท่าเดิม
7. **หยุดเมื่อถึงเงื่อนไข** หรือไอเดียที่เหลือได้น้อยไม่คุ้ม ห้ามลดเงื่อนไขเพื่อให้ถึง ห้ามเลิกขณะยังมีสมมติฐานถูก ๆ ที่ยังไม่ลอง ติดจริงให้บอก ไม่วนเปล่า
8. ทำ `playbooks/delivery.md` โดยเรียง commit ตามลำดับที่ชนะ

**รายงาน:** ตัวชี้วัดและเป้า baseline → ผลสุดท้ายพร้อม % จำนวนรอบ (เก็บ/ถอย) การแก้ที่เก็บบรรทัดละข้อ path ของ decision log และไอเดียที่ดีที่สุดถ้าจะไปต่อ
