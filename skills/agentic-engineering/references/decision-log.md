# Decision log

ร่องรอยการตัดสินใจที่ผู้ใช้กลับมาตรวจได้ ใช้กับงานยาว งานที่ปล่อยรัน งานหลายเฟส และงานที่ผู้ใช้จะกลับมาดูทีหลัง playbook อื่นที่ต้องมีร่องรอยให้ใช้ไฟล์นี้ ไม่คิดรูปแบบใหม่

## รูปแบบ

ไฟล์ TSV เดียว แถวละการตัดสินใจ ทุกช่องอยู่บรรทัดเดียว หลักฐานเป็นตัวชี้ ไม่ใช่ย่อหน้า

| คอลัมน์ | ความหมาย |
| --- | --- |
| `ts` | เวลา ISO8601 |
| `phase` | เฟสหรือสายงาน |
| `decision` | เลือกหรือทำอะไร หนึ่งบรรทัด |
| `why` | เหตุผลด้วยคำธรรมดา ถ้าหลักการไหนพาไป ให้พูดตรง ๆ ไม่ใช่แปะป้ายศัพท์ |
| `evidence` | ตัวชี้ที่พิสูจน์ได้: SHA, เลข PR, `file:บรรทัด`, path ของ artifact/trace/screenshot |
| `result` | ผล: `test เขียว`, `ถอย`, `pixel-diff 0`, `สรุปไม่ได้`, `ค้าง` |

ตัวอย่าง (เขียนแบบเล่าให้เพื่อนร่วมทีมฟัง):

```
ts	phase	decision	why	evidence	result
2026-10-24T09:02:00Z	frame	นับงานก่อน ประมาณ 100 component ราว 75 ชั่วโมง	อยากรู้ขนาดก่อนเริ่มงานยาว	commit 3a9f1c2	เจอ 5 เรื่องที่ต้องเคลียร์ก่อนเริ่ม
2026-10-24T09:40:00Z	harness	ถ่าย screenshot เวอร์ชันเดิมก่อนแก้อะไร	จะได้เทียบเก่ากับใหม่และจับการเปลี่ยนหน้าตาได้	scripts/snapshot.sh, baseline/	ได้ภาพอ้างอิง 120 ภาพ
2026-10-24T12:30:00Z	widget	ทิ้งงานของ agent ตัวหนึ่งเพราะ screenshot ว่างเปล่า	ตรวจไฟล์จริงแทนเชื่อสรุปของมัน	worktree reset	ถอย และรัด brief ให้แน่นขึ้น
```

## การบันทึก

ใช้ `scripts/log.sh` ในโฟลเดอร์ของสกิลนี้:

```bash
bash <path-ของสกิล>/scripts/log.sh decisions.tsv widget "ย้าย style ของ widget โดยหน้าตาเท่าเดิม" "เปลี่ยนน้อยและผลเหมือนเดิม" "commit 7c21e0a, pixel-diff 0" "เหมือนเดิม test ผ่าน"
```

script ใส่ `ts` ให้ เขียนหัวตารางตอนสร้างไฟล์ ลบ tab/ขึ้นบรรทัดใหม่ในช่อง และเติม `'` หน้าช่องที่ขึ้นต้นด้วย `= + - @` (กันสูตรทำงานเมื่อเปิดใน spreadsheet)

บันทึกจุดตัดสินใจและ checkpoint ไม่ใช่ทุกการกระทำ: ทางแยกที่เลือก หน่วยงานที่เสร็จพร้อมผลตรวจ การเปลี่ยนทิศหรือถอยพร้อมสาเหตุ สิ่งกีดขวาง ด่านที่แก้ งาน loop บันทึกรอบละแถว

## กฎ

- **เพิ่มอย่างเดียว** ตัดสินผิด ให้เพิ่มแถวใหม่ที่แทนที่ ห้ามแก้หรือลบประวัติ
- หลักฐานจาก script ที่ commit ไว้ ดีกว่าการทำมือครั้งเดียว
- ค่าเริ่มต้น: เก็บที่ `decisions.tsv` ใน work dir หรือ `.audit/<งาน>.tsv` เมื่อมีหลายงานพร้อมกัน ไม่ commit commit เฉพาะงานใหญ่ที่ผู้รีวิวต้องใช้ร่องรอยเพื่อเชื่อผล
- session ที่มาทำต่อ log ของคนอื่น ให้แถวแรกเป็น phase `start` และระบุช่วง `ts` ของแถวก่อนหน้าที่ไม่ได้เขียนเอง

## ตรวจ log ก่อนส่งคืน

1. **เทียบ log กับสิ่งที่เกิดจริง** ทุกแถวตรงกับการตัดสินใจหรือการกระทำจริง หลักฐานของทุกแถวเปิดได้และแสดงสิ่งที่แถวอ้าง ทางแยก การเปลี่ยนทิศ หรือแนวทางที่ทิ้งที่มีผลต่องานแต่ไม่ได้บันทึก คือช่องว่าง ให้เพิ่ม แก้ด้วยแถวใหม่ ไม่ใช่แก้แถวเดิม
2. **หาสิ่งที่ผู้ใช้ควรดู** หัวหน้าทำเองเป็นค่าเริ่มต้น งานระดับเต็มหรือเมื่อผู้ใช้ขอ ให้ส่ง log และสรุปงานให้ `reviewer` โดยไม่ทำงานใหม่ มองหา: การตัดสินใจที่หลักฐานอ่อนหรือไม่มี, การตรวจที่อ้างว่าทำแต่ไม่มีหลักฐาน, ทางเลือกที่ดูเสี่ยงเมื่อมองย้อน (เร็วเกินไป, ขยาย scope, ปิดอาการแทนต้นเหตุ), ช่องว่างที่อ่านผ่าน ๆ จะพลาด

รายงานของงานที่มี log ต้องปิดด้วยหัวข้อ **"ควรดู"** บรรทัดแรกคือ `ตรวจโดย <โมเดล>` หรือ `ตรวจโดยหัวหน้าเอง (ไม่อิสระ)` แล้วตามด้วยแต่ละประเด็นพร้อมชี้แถวหรือจังหวะที่เกี่ยว "ไม่มีประเด็น" เป็นคำตอบที่ใช้ได้

อ่าน log ในเทอร์มินัล: `column -s$'\t' -t decisions.tsv` บน GitHub TSV ที่ commit แล้วแสดงเป็นตาราง
