# การตรวจแบบละเอียด

**บันไดความมั่นใจ** ทุกข้ออ้างที่ความถูกต้องของงานพึ่งพา ให้ไต่ให้สูงที่สุดเท่าที่ทำได้ไม่แพง แล้วบอกว่าหยุดที่ขั้นไหน:

| ขั้น | ความหมาย | ป้าย |
| --- | --- | --- |
| 1 | พูดเอง ไม่มีอะไรรองรับ | เดา |
| 2 | ชี้ `file:บรรทัด` จริงได้ | อนุมาน |
| 3 | ไล่ทีละขั้นให้เห็นว่ากรณีเสียเกิดไม่ได้ | อนุมาน |
| 4 | เขียน script/test ที่เรียกโค้ดจริงและพังดังถ้าเราผิด แล้วรัน | รันแล้ว |
| 5 | ทำให้เกิดในแอปที่รันจริง | รันแล้ว |

**คำตัดสินมี 3 แบบ:** ผ่าน / ไม่ผ่าน / สรุปไม่ได้ "สรุปไม่ได้" หรือตรวจผิด surface ไม่ใช่ "ผ่าน" ห้ามซ่อนผลลบ

**ตรวจบน surface เดียวกับที่ปัญหาเกิด** ถ้าโค้ดเป็น library หรือโมดูลที่ไม่มีแอปใน repo surface คือการเรียก API สาธารณะของมันด้วย input จริง (ขั้น 4 นับเป็นผ่านได้ และให้บอกว่าแอปที่ใช้มันยังไม่ได้ตรวจ) CLI ต้องรันคำสั่งจริง UI ต้องเดิน flow ที่เปลี่ยน ใช้ screenshot กับสถานะหลักและมือถือ สถานะที่เหลือ assert ผ่าน Playwright หรือ DOM เพราะรูปกินโควตา API ต้องเรียกจริง migration ต้อง replay ข้อมูลจริง storage ต้องอ่านค่ากลับมาดู performance ต้องเทียบ trace unit test บอกพฤติกรรมของ branch ไม่ได้พิสูจน์ว่าบั๊กหาย

**สงสัยวิธีสังเกตก่อน** ตรวจแล้ว fail แปลก ๆ หรือผ่านง่ายเกินไป ให้สงสัยวิธีตรวจก่อนสงสัยระบบ อ่านค่าจริง exit code จริง ไม่ใช่ log ที่ตัดมาหรือสรุปของ agent test ที่ fail ต้อง fail ด้วยเหตุผลที่คาดไว้

**เขียน script ตรวจแทนการดูด้วยตา** script รันซ้ำได้และให้คนอื่นตรวจได้ เก็บ output ไว้เป็นหลักฐาน

**test พฤติกรรม ไม่ใช่ไส้ใน** ลองนึกการแก้สองแบบ: ทำพฤติกรรมพัง (test ต้องแดง) และเปลี่ยนไส้ในโดยผลเท่าเดิม (test ต้องยังเขียว) test ที่ไม่ผ่านทั้งสองข้อให้แก้หรือลบ

**รีวิวแยก (ระดับเต็ม หรือผู้ใช้ขอ)** ส่ง `reviewer` เฉพาะสเปกกับช่วง commit มันต้องพยายามทำให้พังและรายงานเฉพาะข้อที่มีคำสั่ง + output พิสูจน์ หัวหน้ารันคำสั่งของทุกข้อค้นพบซ้ำก่อนเชื่อ รีวิวตัวเองหรือ test ผ่านไม่นับเป็นรีวิวแยก

**โจมตีสมมติฐาน** เมื่อแก้ 2 ครั้งแล้วยังพังที่ด่านเดิม:
1. เขียนเป็นประโยคเดียวว่าการแก้ทั้งสองครั้ง "เชื่อ" อะไรร่วมกัน
2. หาการสังเกตที่ผลจะต่างออกไปถ้าความเชื่อนั้นผิด แล้วรัน ดูการกระจายของ failure ไม่ใช่แค่ขนาด ทำเป็น script รันซ้ำได้
3. ความเชื่อผิด ต้นเหตุอยู่ที่อื่น หาสิ่งที่ failure มีร่วมกันที่ความเชื่อเดิมไม่ได้ทำนาย ความเชื่อถูก ให้ถาม "ทำไม" ต่ออีกชั้น
4. แก้โดยลบเงื่อนไขที่ทำให้เกิด ไม่ใช่เพิ่มกลไกตามเก็บกวาด

ห้ามเริ่มแก้รอบใหม่ก่อนเขียนและทดสอบสมมติฐาน
