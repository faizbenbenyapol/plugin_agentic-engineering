# หลักการ

แต่ละข้อบอกว่าใช้เมื่อไร อ่านเฉพาะข้อที่ตรงกับสถานการณ์ เมื่อหลักการไหนเปลี่ยนการตัดสินใจ ให้บอกในรายงานว่าเปลี่ยนอะไรเพราะอะไรด้วยคำธรรมดา ไม่ต้องอ้างชื่อหลักการ

## แกน

### ขี้เกียจอย่างมีระบบ (Laziness Protocol)
ใช้เมื่อ: รีแฟกเตอร์ กำหนดขนาด diff หรืออยากเพิ่ม abstraction ชั้น หรือการส่งต่อค่า
- การเปลี่ยนที่เล็กที่สุดที่แก้ปัญหาได้ บรรทัดน้อยดีกว่า boilerplate ที่ "สวย"
- รวมการตัดสินใจไว้ที่เดียว อย่าตัดสินเรื่องเดียวกันซ้ำหลายจุด ให้มีแหล่งความจริงเดียวแล้วส่งผลเป็น flag ง่าย ๆ
- เอียงไปทางลบ

### คิดจากฐานราก (Foundational Thinking)
ใช้เมื่อ: ก่อนเขียน logic
- **ข้อมูลก่อน logic** นิยาม type หลักก่อน ไล่ทุกรูปแบบการเข้าถึง เลือกโครงสร้างที่ตรงกับเส้นทางที่ใช้บ่อย
- ระดับโค้ด DRY ที่โครงสร้าง ไม่ใช่ทุกบรรทัด statement คล้ายกันสามอันยังดีกว่า abstraction ก่อนเวลา ชัดดีกว่าฉลาด
- **ข้อพ่วงเรื่อง concurrency** ก่อนแชร์ state ให้ถาม "ถ้าอีกฝ่ายแก้พร้อมกันจะเกิดอะไร" ถ้าคำตอบไม่ใช่ "ไม่มีอะไร" ให้แยก
- **scaffold ก่อน** สิ่งที่ช่วยทุกเฟสหลังจากนี้ทำก่อน: CI, lint, โครง test, type กลาง ลำดับ: ลบโค้ดตาย → วางฐาน → ฟีเจอร์ test ก่อนแก้
- แต่ละรอบเพิ่มควรได้ abstraction ที่สมบูรณ์หนึ่งอันหรือทำของเดิมให้ลึกขึ้น อย่ากระจายความสามารถใหม่เป็นการประสานงานพิเศษตาม caller

### ออกแบบใหม่จากหลักแรก (Redesign from First Principles)
ใช้เมื่อ: ใส่ความต้องการใหม่เข้าไปในดีไซน์เดิม
- อ่านไฟล์ที่กระทบทั้งหมด แล้วถาม "ถ้าเขียนใหม่ตั้งแต่ต้องโดยมีความต้องการนี้ เราจะสร้างอะไร"
- ไล่การเปลี่ยนไปทุกที่ที่อ้างถึง: type เอกสาร ตัวอย่าง เหตุผล
- คิดการออกแบบใหม่ทั้งก้อน แต่ส่งทีละขั้น อย่าเอาไปแปะบนดีไซน์เดิม

### โจมตีสมมติฐาน (Attack the Premise)
ใช้เมื่อ: การแก้สองครั้งขึ้นไปที่เชื่อเรื่องเดียวกันตกด่านเดิม ดูขั้นตอนใน SKILL.md ข้อ 4 ต่างจากข้อก่อนหน้าตรงที่ข้อนี้ตั้งคำถามกับข้อเท็จจริงที่ดีไซน์ปัจจุบันเชื่อ ไม่ใช่สร้างดีไซน์ใหม่

### ลบก่อนเพิ่ม (Subtract Before You Add)
ใช้เมื่อ: วางลำดับการเพิ่ม รีแฟกเตอร์ หรือเขียนใหม่
- เอาความซับซ้อนออกก่อนแล้วค่อยสร้าง ตัดก่อนขัด ไปให้ถึงขั้นต่ำก่อนลงทุนเรื่องคุณภาพ
- ออกแบบตามการใช้งานที่เห็นจริง ไม่ใช่ edge case ที่คาดเดา ไม่มี validator parser หรือ guard เกินที่สเปกต้องการ
- ทิ้งระบบไว้ง่ายกว่าและทำได้มากกว่าตอนที่เจอ ภายใต้ผิวที่เท่าเดิมหรือเล็กกว่า
- ของที่ไม่มีเนื้อหาใหม่ ให้ลบ อย่าทิ้งไว้เป็นโครงเปล่า

### ลดภาระคนอ่าน (Minimize Reader Load)
ใช้เมื่อ: รีวิวหรือปรับโค้ดที่ไล่ยาก
- ความดูแลรักษาได้คือแรงที่คนอ่านต้องใช้ วัดสองแกน: **ชั้นที่ต้องไล่** และ **state ที่ต้องจำ** สองแกนนี้อิสระต่อกัน ไฟล์แบนที่มี global 50 ตัวก็อ่านยากพอ ๆ กับ adapter 6 ชั้น
- ยุบชั้นที่เสียมากกว่าได้: wrapper ที่มีผู้เรียกคนเดียว adapter ที่ไม่มี implementation ที่สอง ชั้นที่ส่งต่อ method และ argument เดิม
- interface ต้องบีบอัด interface กว้างที่ซ่อนได้น้อยทำให้คนอ่านต้องเรียนทั้งผิวและไส้
- หด scope ของ state: pure function > ตัวแปร local > field > state ระดับโมดูล > global คำนวณเอาแทนการซิงก์
- ประกาศ invariant ที่ขอบ คนอ่านเรียนครั้งเดียว
- **test:** คนอ่านใหม่ตอบได้ใน 30 วินาทีไหมว่า "X มาจากไหน" และ "อะไรเปลี่ยน X ได้" ถ้าไม่ได้ ให้ตัดชั้นหรือตัด state

### ยึดผลลัพธ์ปลายทาง (Outcome-Oriented Execution)
ใช้เมื่อ: การเขียนใหม่หรือ migration ที่วางแผนไว้และมีขอบเฟสชัด
- ความสมบูรณ์ของปลายทางสำคัญกว่าความเสถียรช่วงเปลี่ยน โค้ด compatibility ชั่วคราวมักกลายเป็นหนี้ถาวร
- การพังระหว่างทางยอมรับได้เมื่อวางแผนไว้ จำกัดขอบเขต และย้อนได้ ประกาศให้ชัดว่าพังได้ตรงไหน
- คงการตรวจที่ให้สัญญาณสูงในส่วนที่กำลังแตะ และตรวจเต็มทั้ง static และ runtime เมื่อจบแผน

### ประสบการณ์มาก่อน (Experience First)
ใช้เมื่อ: ตัดสินเรื่องผลิตภัณฑ์ UX หรือขอบเขตฟีเจอร์
- ความสะดวกของการ implement ขัดกับความพอใจของผู้ใช้ ให้เลือกผู้ใช้
- ทุกฟีเจอร์ ปุ่ม ตัวเลือกต้องมีเหตุผล ส่งน้อยแต่ดี (สามฟีเจอร์ที่เนี้ยบ ชนะสิบฟีเจอร์ที่หยาบ) ใส่ใจรายละเอียด: transition การจัดแนว ระยะ feedback สถานะ error
- "ผู้ใช้" คือใครก็ตามที่ใช้ผลงาน: คนใช้ UI, เพื่อนร่วมงานที่ import library, และวิศวกรที่จะดูแลโค้ดต่อ อธิบายผลกระทบจากมุมของพวกเขา

### สำรวจทางเลือกให้สุด (Exhaust the Design Space)
ใช้เมื่อ: interaction ใหม่หรือการตัดสินใจทางสถาปัตยกรรมที่ไม่มีตัวอย่างมาก่อน
- สร้าง prototype ที่แข่งกัน 2–3 แบบแล้วเทียบก่อนผูกมัด ใช้กับเรื่องที่ตัดสินด้วย "ความรู้สึก" ด้วย ไม่ใช่แค่ตรรกะ

### สร้างคานงัด (Build the Lever)
ใช้เมื่อ: งานใดก็ตามที่ไม่จิ๊บจ๊อย
- สร้างเครื่องมือที่ทำงานหรือพิสูจน์งาน (codemod, generator, script, query บน sqlite, check ที่รันซ้ำได้) แทนทำมือ เครื่องมือคือ artifact ที่ผู้รีวิวรันซ้ำได้ งานมือตรวจซ้ำได้แค่ทำใหม่
- ทำหน่วยแรกด้วยมือเพื่อเรียนสูตร แล้วสร้างเครื่องมือ พิสูจน์โดยรันกับหน่วยแรกแล้ว diff กับของที่ทำมือ ทำให้รันซ้ำได้ปลอดภัย
- เครื่องมือ deterministic ชนะการแตกงานให้ agent ถ้า script ทำทุกหน่วยได้ในรอบเดียว ให้รันเอง ไม่ต้องส่ง agent ไปทำมือ
- เมื่อแตกงานให้ agent ให้เขียนสูตร สัญญาการตรวจ และเขตห้ามแตะไว้ในไฟล์เดียวที่ทุกตัวอ่าน และอยู่นอกขอบเขตที่มันแก้ได้
- ใช้หลักการนี้แล้วต้องมีไฟล์ ถ้าอ้างแต่ใน diff ไม่มี script หรือเครื่องมือ แปลว่าไม่ได้ใช้
- เกณฑ์คือความจิ๊บจ๊อย ไม่ใช่การทำซ้ำ งานครั้งเดียวก็ควรมีคานงัดถ้ามันทำให้งานตรวจได้ แต่สร้าง script เล็กที่สุด ไม่ใช่ framework

## สถาปัตยกรรม

### Model the Domain
ใช้เมื่อ: เขียน logic ที่มี state, โค้ดที่แตก branch เยอะ หรือเดารูปร่างข้อมูลซ้ำหลายไฟล์
เข้ารหัส domain ไว้ในโครงสร้างข้อมูล แทนกระจายเป็นเงื่อนไข โครงสร้างที่ตรง domain ทำให้ state ผิดเกิดไม่ได้และลบ branch ได้ เลือกตอนเขียนถูก กู้ทีหลังแพง:
- state machine แทน boolean, phase, หรือ lifecycle check ที่กระจาย
- typed model แทน parameter หลวม ๆ
- map, registry, lookup table, discriminated union แทน branch ที่กระจายหลายไฟล์
- reducer หรือ command/event แทนการแก้ state แบบเฉพาะกิจ
- โมดูลที่จัดตามความรู้ของ domain หนึ่งก้อน แทนการจัดตามลำดับเวลา (load → validate → transform → save) ลำดับการทำงานไม่ใช่ความเป็นเจ้าของ
- queue, cache, index, graph, tree ตามรูปแบบการเข้าถึง
อย่าฝืนสร้าง abstraction โค้ดธรรมดาที่ชัด อยู่ที่เดียว และไม่น่าโต ให้คงไว้ สัญญาณว่าข้ามหลักการนี้: ฟีเจอร์ใหม่ทำให้ if/else เดิมยาวขึ้นอีกหนึ่ง branch หรือมี boolean ตัวที่สองที่ต้องซิงก์กับตัวแรก

### วินัยที่ขอบระบบ (Boundary Discipline)
ใช้เมื่อ: วาง validation, error handling, หรือ adapter ของ framework
- ที่ขอบ (CLI args, config, API ภายนอก, network): validate, คืน error, ป้องกันเต็มที่
- ข้างใน: ข้อมูลมี type, ส่ง error ต่อ, ไม่ validate ซ้ำ เชื่อ type
- ข้ามขอบ: เปิดเผยแนวคิดของ domain ไม่ใช่รูปแบบภายในของขอบ (ห้าม re-export type ของ transport storage framework หรือ wire)
- logic ธุรกิจเป็น pure function ไม่ผูก framework เปลือกบางและเป็นกลไก (แนว hexagonal: แกนคุยผ่าน interface แล้วต่อ adapter ทำให้ test แกนได้โดยไม่เปิด UI หรือ DB)
- **test:** "ข้อมูลนี้กำลังข้ามขอบระบบอยู่ไหม" ถ้าไม่ การ validate ซ้ำคือของเกิน "ส่วนนี้เป็น pure function ที่เปลือกแค่เรียกได้ไหม" ถ้าได้ ให้แยกออก

### วินัย type (Type System Discipline)
ใช้เมื่อ: ออกแบบ type หรือ signature ในภาษาที่มี type
- ให้ compiler ปฏิเสธ state ที่เป็นไปไม่ได้ primitive ที่สลับกัน และ variant ที่ไม่ได้จัดการ ลบ error และกรณีพิเศษให้หายไปด้วยดีไซน์ ดีกว่าเพิ่ม handler
- brand primitive ที่มีความหมาย: `UserId` กับ `OrderId` เป็น string ทั้งคู่แต่ต้องสลับกันไม่ได้ validate ครั้งเดียวตอนสร้าง
- ข้อมูลภายนอกไม่มี type จนกว่าจะ parse (JSON, RPC, IPC, CLI args, config, env, แถวจาก DB) ทุกขอบต้องมีฟังก์ชัน parse
- derive type จาก schema ที่เป็นแหล่งจริง (OpenAPI, protobuf, GraphQL, migration) อย่าเขียน type คู่ขนานด้วยมือ

### ทำซ้ำได้ผลเดิม (Make Operations Idempotent)
ใช้เมื่อ: ออกแบบคำสั่ง ขั้น lifecycle หรือ loop ที่ทำงานท่ามกลาง crash และ retry
- ทุกการแก้ state ต้องตอบได้: รันสองครั้งติดจะเกิดอะไร รอบก่อน crash กลางทางทุกจุดจะเกิดอะไร รันซ้ำแล้วไปจบที่ state เดียวกันไหม
- อ่าน state ที่มีอยู่ เทียบกับเป้า แล้วทำเฉพาะส่วนต่าง ไม่ใช่ทำตามสิ่งที่รอบก่อนตั้งใจ
- สิ่งที่รอบก่อนทิ้งไว้ (lock, ไฟล์ชั่วคราว, record ที่เขียนครึ่งเดียว, job ที่จองไว้) รอบถัดไปต้องรู้ได้ว่าค้าง เช่น เขียนลง path ชั่วคราวแล้ว rename เข้าที่ เทียบ artifact ด้วยเนื้อหา ไม่ใช่ลำดับการสร้าง
- ถ้าคำตอบคือ "ขึ้นกับว่ารอบก่อนทิ้งอะไรไว้" ต้องมีขั้น reconcile

### ย้าย caller แล้วลบ API เก่า (Migrate Callers Then Delete Legacy APIs)
ใช้เมื่อ: มี API ภายในใหม่ขณะที่ caller เก่ายังอยู่
- ย้ายทุก caller แล้วลบของเก่าในรอบเดียว ไม่มี shim ไม่ปล่อยสองทาง
- แก้ test ให้ยืนยันสัญญาใหม่ ลบ test ที่ปกป้องแค่ไส้ในก่อนรีแฟกเตอร์
- ใช้เมื่อไม่มีผู้ใช้ภายนอกที่พึ่ง backward compatibility และโปรเจกต์รับ breaking change แบบประสานกันได้

### แยกก่อนจะเรียงคิว state ที่ใช้ร่วม (Separate Before Serializing Shared State)
ใช้เมื่อ: actor หลายตัวอาจเขียนไฟล์ branch key หรือ object เดียวกัน
1. ระบุ state ที่เขียนร่วม (ไฟล์ที่ทั้งอ่านทั้งเขียน, branch ที่ push ทั้งคู่)
2. **ค่าเริ่มต้นคือกำจัดเป้าหมายการเขียนร่วม** ถามว่าต้องเป็น object เดียวจริง หรือแต่ละตัวแค่เผยแพร่ข้อเท็จจริงของตัวเอง ให้แต่ละตัวมีไฟล์ key branch ของตัวเอง แล้วรวมตอนอ่านหรือรายงาน (สอง worker เขียน field ของตัวเองลง `state.json` เดียวกันยังนับเป็นการเขียนร่วม)
3. ถ้าเป้าเดียวเป็น invariant จริง ค่อยเรียงคิวแบบมีโครงสร้าง: lockfile, เฟสตามลำดับ, writer คนเดียว, compare-and-swap คำสั่งและข้อตกลงไม่ใช่ concurrency control "ต้องใส่ lock" คือกลิ่นของดีไซน์ที่ต้องตรวจ ไม่ใช่คำตอบตั้งต้น

## การตรวจ

### พิสูจน์ว่าใช้ได้ (Prove It Works)
ใช้เมื่อ: หลังทำงาน ก่อนประกาศว่าเสร็จ
- ตรวจของจริงโดยตรง ไม่อนุมานจากตัวแทน (mtime ของไฟล์, ความสดของ output, รายงานของ agent, screenshot เก่า, "คอมไพล์ผ่าน")
- เช็ก process ว่ามีชีวิตโดยตรง อ่านค่าจริง ไม่ใช่ค่าที่ cache หรือคำนวณต่อ
- ตรวจแล้ว fail ให้สงสัยวิธีสังเกตก่อนสงสัยระบบ
- หลักฐานที่แข็งที่สุดคือ script ที่รันการเทียบเดิมซ้ำได้ เก็บ output ให้ผู้รีวิวรันเองได้

### แก้ที่ต้นเหตุ (Fix Root Causes)
ใช้เมื่อ: ดีบัก
- อาการคือที่ที่ state ผิดโผล่ให้เห็น ต้นเหตุคือที่แรกที่ระบบทำสิ่งที่ไม่ควรทำ หรือไม่รองรับ state ที่ควรรองรับ
- ทำให้เกิดซ้ำก่อน ถาม "ทำไม" จนคำตอบคือการตัดสินใจผิดในโค้ด ไม่ใช่ผลของอันก่อนหน้า ติดให้ instrument อ่าน error และ state จริง
- ถามว่า state ที่ทำให้พังถูกต้องไหม (ดู `playbooks/bug-fix.md` ขั้น 3)
- หาที่อื่นที่ผิดแบบเดียวกันแล้วแก้ให้หมด
- workaround ที่ต้องมีคอมเมนต์ยาวหนึ่งย่อหน้ามาอธิบาย แปลว่าโค้ดผิด แก้โค้ด ไม่ใช่แก้คอมเมนต์

### เรียงงานเป็นหน่วยที่ตรวจได้ (Sequence Work into Verifiable Units)
ใช้เมื่อ: งานหลายขั้น (sweep, migration, แก้คล้ายกันหลายจุด) และการเรียง commit/PR
- แตกเป็นหน่วยเล็ก แต่ละหน่วยจบที่ state ที่ตรวจได้ ห้ามไปต่อจนหน่วยปัจจุบันเขียว (state ดี → เปลี่ยนหนึ่งอย่าง → ตรวจ → ไปต่อ) rebase บน trunk สะอาดก่อนเพื่อให้ทุกการตรวจวัดเทียบฐานจริง
- เรียง commit ให้อ่านแล้วเป็นเหตุผล: test ที่ fail ก่อนการแก้, การลบก่อนการปรับรูป, baseline ก่อนการเปลี่ยน, scaffold ก่อนฟีเจอร์ ผู้รีวิว "ดูมันแดงแล้วเขียว" แทนที่จะต้องเชื่อเรา

### test พฤติกรรม ไม่ใช่ไส้ใน (Test Behavior, Not Implementation)
ใช้เมื่อ: เขียน แก้ หรือเก็บ test
- พฤติกรรมคือสิ่งที่ผู้ใช้โค้ดสังเกตได้ผ่าน interface: ค่าที่คืน error state ที่อ่านกลับได้ ผลต่อระบบภายนอก (request ที่ส่ง แถวที่เขียน ข้อความที่ปล่อย) ไส้ในคือสิ่งที่สังเกตไม่ได้: helper ส่วนตัว ลำดับการเรียกภายใน ข้อมูลระหว่างทาง
- ตรวจทุก test ด้วยการแก้สมมติสองแบบ: **ทำพฤติกรรมพัง** (คืนค่าผิด ข้ามผลข้างเคียง ทำซ้ำสองครั้ง) test ต้องแดง และ **เปลี่ยนไส้ใน** โดยผลเท่าเดิม test ต้องยังเขียว เก็บ test ที่ผ่านทั้งสองข้อ ที่เหลือแก้หรือลบ
- สาเหตุที่ test ไม่จับอะไร: assertion หลวมกว่าสัญญา, ค่าที่คาดคำนวณด้วยโค้ดที่ถูกทดสอบเอง, assert ข้อมูลที่ test สร้างเอง
- ค่าที่คาดต้องมาจากความต้องการ ไม่ใช่จากการรันโค้ด assert ตามที่สัญญาบอก ไม่มากไม่น้อยกว่านั้น
- สัญญาเป็นตัวตัดสิน: payload ที่ service ภายนอกที่ถูก mock ได้รับคือพฤติกรรม (service นั้นเห็น) การเรียก helper ภายในคือไส้ใน ข้อความ error ที่ไม่มี caller อ่านคือไส้ใน ชนิด error ที่ caller แตก branch ตามคือสัญญา

### อธิบายตัวเลขให้ได้ (Explain the Number)
ใช้เมื่อ: ก่อนวัด และก่อนเชื่อ รายงาน หรือตัดสินใจจากตัวเลขที่วัด (speedup, regression, throughput, latency, ผล eval)
- เขียนก่อนรันว่าผลแบบไหนจะเปลี่ยนการตัดสินใจ และระดับ noise หยุดเมื่อความต่างระหว่างรอบมากกว่าผลที่วัด
- ถาม "ทำไมไม่ดีกว่านี้สองเท่า" ระบุทรัพยากรที่จำกัด (core, lock, disk, network, หรือตัวสร้างโหลดเอง) จาก profile หรือตัวนับของระบบ แล้วชี้ไปที่ source การเดาจากการอ่านโค้ดไม่ใช่ตัวจำกัด
- ไล่ว่าตัวเลขอาจวัดอะไรอื่น แล้วตัดทิ้งด้วยหลักฐาน: error, งานที่ข้ามหรือ cache, โค้ดที่ไม่ได้รัน, ฝั่งที่ไม่ได้ tune, noise, ชิ้นที่เล็กเกินจะมีผลปลายทาง
- เก็บหลักฐานคู่ตัวเลข: จำนวนรอบ ช่วงกระจาย ตัวจำกัด ขั้นตอนเต็มใน `references/benchmark.md`

## การมอบงาน

### รักษา context (Guard the Context Window)
ใช้เมื่อ: context กำลังเต็ม: output ใหญ่ ไฟล์ยาว อ่านซ้ำ วางแผนแตกงาน
- ส่งงานกินเนื้อที่ให้ agent เก็บแค่สรุปไว้ในแชทหลัก
- กำหนดขนาดเฟสและเพดานขอบเขต (จำนวนไฟล์ต่อเฟส)
- context ล้นทำให้คิดแย่ลง สรุปเพี้ยน และงานหยุด

### ไม่หยุดรอมนุษย์ (Never Block on the Human)
ใช้เมื่อ: อยากถาม "ทำ X ดีไหม" กับเรื่องเทคนิคที่ย้อนได้ หลังตกลงโจทย์กันแล้ว
- ข้อนี้ไม่ใช่ข้ออ้างให้เดาความต้องการ ขอบเขต พฤติกรรม และกฎธุรกิจต้องถามให้ครบตอนตั้งโจทย์ (`playbooks/kickoff.md`) ถามตอนต้นครั้งเดียวคือสิ่งที่ทำให้ช่วงลงมือไม่ต้องหยุดรอ
- เรื่องเทคนิคที่ย้อนได้ ทำก่อนแล้วนำเสนอ อธิบายเหตุผล ให้มนุษย์ปรับทิศทีหลัง ความผิดพลาดที่ย้อนได้ถูกกว่าการหยุดรอ
- เห็นปัญหาให้จดและแก้รอบถัดไป
- ทิศทางผลิตภัณฑ์มาจากมนุษย์ การลงมือไม่ต้องรอ การกระทำที่ย้อนไม่ได้ยังต้องยืนยันเสมอ

## เมตา

### เปลี่ยนบทเรียนเป็นโครงสร้าง (Encode Lessons in Structure)
ใช้เมื่อ: เจอตัวเองเขียนคำสั่งเดิมเป็นครั้งที่สอง
- เปลี่ยนเป็น lint, metadata flag, runtime check หรือ script แทนเขียนข้อความเพิ่ม ขั้นตอนเต็มใน `playbooks/correct.md`
- ถ้าบทเรียนต้องใช้วิจารณญาณจนเข้ารหัสไม่ได้ ให้เขียนคำสั่งให้เด่นขึ้นและแนบตัวอย่างความผิดพลาดจริง
- ถ้าแก้เชิงโครงสร้างได้ ให้ใช้แค่การแก้เชิงโครงสร้าง คำสั่งคืออาการ
