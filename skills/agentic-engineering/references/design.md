# ร่างแบบก่อนเขียน

ร่าง type, signature, รูปของ class และขอบโมดูล ด้วย body ที่ยังว่าง (`throw new Error("not implemented")`, `todo!()`, `raise NotImplementedError`) และ pseudocode แล้วค่อยเติมโค้ดตามร่าง

ใช้เมื่อ: การเปลี่ยนข้ามขอบฟังก์ชันหรือโมดูล หรืองานที่ถ้ากระโดดไปเขียนโค้ดเลยจะล็อกรูปผิด

## A. ทำความเข้าใจระบบที่แตะ

สืบสวนทุก subsystem ที่โค้ดใหม่จะแตะ (`playbooks/investigation.md`) การรู้ชื่อไฟล์ไม่นับว่าเข้าใจ ถ้าดีไซน์เปลี่ยนความเป็นเจ้าของหรือการแบ่งชั้น ให้ขุด "ทำไม" ของรูปเดิมด้วย (`git log`, PR) เหตุผลเดิมจะกลายเป็นข้อจำกัด ไม่ใช่การเดา ข้ามได้เฉพาะงานใหม่ล้วนที่ไม่มีระบบรอบข้าง

## B. ร่าง

1. **เขียนฝั่งผู้เรียกก่อน** ตัวอย่างโค้ดที่ caller จะเขียน แล้วค่อย derive type และ signature จากมัน
2. **ออกแบบสองครั้ง** ระดับเต็มต้องมีอย่างน้อยสองร่างที่ต่างกันทั้งรูป ไม่ใช่ต่างแค่จุดเล็ก ๆ ในรูปเดียว แม้ร่างแรกจะดูพอแล้วก็ตาม หัวหน้าร่างเองสองแบบ (ใช้ agent ร่างแข่งเฉพาะเมื่อผู้ใช้สั่ง ตาม `references/parallel-and-review.md`)
3. **คัดกรองทุกร่างด้วย red flags ข้างล่าง** สมมติว่าคนที่จะแก้โค้ดต่อคือ agent ที่เห็นแค่ไฟล์ที่เปิด ก๊อปตัวอย่างที่ใกล้ที่สุด และเลือกทางสั้นที่สุดที่คอมไพล์ผ่าน เลือกร่างที่การเปลี่ยนซึ่งดูถูกจากไฟล์เดียว ถูกสำหรับทั้ง repo
4. **เทียบความลึกของ interface** เลือกร่างที่ซ่อนความซับซ้อนได้มากกว่าหลังผิวที่เล็กและง่ายกว่า interface ที่รวมความสามารถไว้ทำให้สายการเรียกสั้นได้ แทนที่จะกระจายไปหลายชั้น
5. **สังเคราะห์** เลือกฐาน แล้วยกจุดดีของร่างอื่นมาใส่ด้วยมือ (ไม่ใช่แปะ) ให้ผลยังอยู่ใต้แนวคิดเดียว

## C. ตกลง

ระดับกลาง: เดินหน้าต่อเลยด้วยร่างที่สังเคราะห์แล้ว ระดับเต็ม หรือผู้ใช้ขอ ("ให้ดูก่อน"): แสดงร่างแล้วรอยืนยัน ร่างจะ commit เป็น scaffold แยกก่อนก็ได้ ถ้าผู้ใช้ค้านรูป ให้ถือเป็นข้อมูลของขั้น A แล้วร่างใหม่ก่อนเขียนโค้ดต่อ ถ้าต้องการแรงกดดันก่อนลงมือ ส่งร่างให้ `reviewer` แบบโจมตี

## D. เติมโค้ดตามร่าง

ร่างคือสัญญา การเบี่ยงจากร่างคือสัญญาณที่ต้องบอก ไม่ใช่แรงเสียดทานที่กลืนเงียบ ๆ ถ้าฟังก์ชันต้องการ parameter ที่ร่างไม่ได้คาด ให้ถามว่าร่างผิด ความต้องการตกหล่น หรือ implementation เกินเลย

## E. ทิ้งร่างเมื่อสถาปัตยกรรมผิด

ถ้าการเติมโค้ดสร้างแรงเสียดทานที่ร่างรับไม่ไหวซ้ำ ๆ ให้ทิ้งร่าง อย่าแปะแก้บนดีไซน์ที่ผิด สัญญาณคือ *รูปแบบ* ไม่ใช่ครั้งเดียว:
- workaround รูปเดียวกันโผล่ซ้ำในโค้ดที่ไม่เกี่ยวกัน
- edge case หลายตัวที่ไม่เกี่ยวกันต้องการ branch พิเศษ
- type ต้องใช้ทางหนี (`any`, cast, field optional ที่ในทางปฏิบัติมีค่าเสมอ) จึงคอมไพล์ผ่าน
- อยาก "ใส่ lock" ทั้งที่ร่างบอกว่า state ไม่ได้แชร์
- caller ต้องรู้กฎภายในของ abstraction จึงใช้ได้
- การเบี่ยงจากร่างรูปเดียวกันสองครั้งขึ้นไป
ความซับซ้อนในข้อมูลไม่ใช่ความซับซ้อนในดีไซน์ edge case ไม่กี่ตัวไม่ได้ตัดสินสถาปัตยกรรม เมื่อทิ้ง: สืบสวนสิ่งที่สร้างไปแล้ว → ออกแบบใหม่ราวกับข้อจำกัดใหม่มีตั้งแต่วันแรก → ลบก่อนเพิ่ม ร่างใหม่ต้องเล็กกว่าร่างเก่าก่อนจะโต → กลับไปขั้น B

## ผลงาน

ตัวอย่างฝั่งผู้เรียก, ไฟล์ type/signature ใหม่ (งานเล็ก) หรือแผนที่โมดูล + type (งานใหญ่), และเหตุผลสั้น ๆ: ร่างที่พิจารณา, ฐานที่เลือกและทำไม, จุดที่ยกมาจากร่างอื่น, สิ่งที่ทิ้งและทำไม งานระดับเต็มบันทึกที่ `docs/decisions/`

## Red flags

**โมดูลตื้น** interface ใหญ่แต่ซ่อนได้น้อย สังเกต: caller ต้องเรียกหลาย method ประสานกันเพื่องานเดียว, option สาธารณะเปิดเผยขั้นภายใน, เรียน interface แล้วยังต้องเรียน implementation โมดูลลึกต่างจากสายการเรียกลึก สายการเรียกลึกกระจายความเข้าใจไปหลายชั้น

**ข้อมูลรั่ว** หลายโมดูลพึ่งการตัดสินใจภายในเดียวกัน (รูปแบบข้อมูล นโยบาย รายละเอียด protocol) จนเปลี่ยนแล้วต้องแก้ประสานหลายที่ การ re-export type ของ transport หรือ wire ก็นับ ให้ parse เป็น type ของ domain หลัง interface

**แบ่งตามลำดับเวลา** โมดูลจัดตามลำดับการทำงาน (load, validate, transform, save) แทนความรู้ที่เป็นเจ้าของ มักทำให้รูปแบบข้อมูลและ invariant เดียวกันซ้ำข้ามหลายขอบ

**method ส่งผ่าน** method ที่ส่ง argument เดิมไปหา method อื่นที่รูปเหมือนกัน เพิ่มชั้นโดยไม่ซ่อนอะไร ลบทิ้ง หรือย้ายหน้าที่ไปที่โมดูลที่ทำงานให้จบได้

**ความเป็นเจ้าของแตก** มากกว่าหนึ่งโมดูลเขียน state เดียวกันหรือเก็บสำเนาของตัวเอง agent ที่แก้ writer ตัวหนึ่งมองไม่เห็นตัวอื่น กฎจึงแยกทางกัน ให้ state แต่ละชิ้นมีเจ้าของเดียว

**สองทางทำงานเดียว** ดีไซน์รองรับหลายวิธีทำเรื่องเดียวกัน agent ก๊อปวิธีที่เจอก่อน ทุกวิธีจึงมี caller เพิ่มเรื่อย ๆ เก็บไว้ทางเดียว ย้าย caller แล้วลบทางอื่นในการเปลี่ยนเดียวกัน

**import ไส้ในได้** caller import ส่วนภายในของโมดูลได้ agent เลือกทางสั้นที่สุดจึง import ตรง แล้วไส้ในกลายเป็นส่วนของ interface ทำให้ import จากนอกโมดูลแล้ว build พัง

**รายการที่ซิงก์ด้วยมือ** รายการเดียวกันอยู่สองที่ขึ้นไป เพิ่มของต้องแก้ทุกที่ agent ที่เห็นที่เดียวแก้ที่เดียว เก็บรายการเดียวแล้ว derive ที่เหลือ ถ้า derive ไม่ได้ ให้ build พังเมื่อรายการไม่ตรงกัน
