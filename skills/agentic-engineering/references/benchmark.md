# Checklist ก่อนเชื่อตัวเลข performance

ใช้เมื่อได้ตัวเลข performance ที่วัดเอง: ก่อน/หลังของ PR, การอ้าง regression, harness ของ hillclimb, การเลือก library หรือ config ตอบทุกข้อด้วยหลักฐานจากการรัน ไม่ใช่การเดาจากโค้ด

ผู้ใช้ขอแค่ตัวเลขคร่าว ๆ: รันรอบเดียวพอ แต่ยังต้องเช็กข้อ 4 และ 7 และบอกว่ารอบเดียว การเลือกระหว่างตัวเลือกไม่ใช่ตัวเลขคร่าว ๆ

## ก่อนรัน

- เขียนประโยคที่จะรายงานไว้ก่อน เช่น "export เร็วขึ้น 30% ที่ p50 บนข้อมูล 60k แถว" คำถามข้างล่างทดสอบประโยคนี้
- อ่าน script ที่วัด จดว่ามันจับเวลา นับ และไม่สนใจอะไร
- เช็กโหลดเครื่อง (`uptime`) และจำนวน core (`nproc`) ถ้าเครื่องยุ่ง หาว่าอะไรรัน หยุดไม่ได้ให้สลับรันสองฝั่งให้เจอ noise เท่ากัน และบอกในรายงาน

## 7 คำถาม

1. **ทำไมไม่ดีกว่านี้สองเท่า** ระบุตัวจำกัด profile ในรอบที่ไม่ได้รายงาน (profiler ทำให้ช้าลง) ใช้ CPU ต่อ process, profiler ของ runtime (`node --cpu-prof`, `py-spy`, `perf`), I/O wait, จำนวน syscall แล้วชี้ไปที่ source ดูตัวสร้างโหลดด้วย ถ้ามันอิ่มก่อน แปลว่าวัดตัวสร้างโหลด ถ้าการเปลี่ยนไม่ขยับตัวเลข ตัวจำกัดคือคำอธิบาย หาให้เจอก่อนจะบอกว่าการเปลี่ยนไม่มีประโยชน์
2. **tune แล้วหรือยัง** รันทุกฝั่งแบบที่ production รัน: release build, flag และ env ของ production, batch และ transaction, connection pool, cache อุ่นหรือเย็นแบบ production, version และข้อมูลเดียวกัน ถ้าฝั่งหนึ่งใช้ค่าเริ่มต้น แปลว่าเทียบ config ไม่ใช่ implementation ตัวจำกัดที่เป็นการตั้งค่า (commit ทีละแถว, debug build, ขาด index) แปลว่าฝั่งนั้นยังไม่ tune tune แล้ววัดใหม่ก่อนตัดสิน
3. **เกินขีดจำกัดไหม** คิดเลข: byte ต่อวินาทีเทียบแบนด์วิดท์ disk/network, operation ต่อวินาที × ต้นทุนต่อ operation เทียบจำนวน core, เวลาที่ประหยัดเทียบเวลาที่ชิ้นที่เปลี่ยนใช้ ลบชิ้นที่กิน 10% ของเวลา ทำให้เร็วขึ้นได้มากสุดประมาณ 11% ผลที่เกินขีดจำกัดวัดอย่างอื่น เช่น cache, no-op, บั๊ก
4. **มี error ไหม** นับความล้มเหลวและ response ที่ไม่สำเร็จ เช็กว่า output ถูก ไม่ใช่แค่มี การปฏิเสธมักเร็ว timeout และ retry มักช้า ถ้า script ไม่นับ error ให้เพิ่ม
5. **ทำซ้ำได้ไหม** แต่ละฝั่งอย่างน้อย 5 รอบ สลับกัน (A B A B ...) ให้ warmup, lazy init, cache และ drift ไม่เข้าข้างฝั่งไหน รายงาน median และช่วง ความต่างที่เล็กกว่าความต่างระหว่างรอบคือ "ไม่ต่างอย่างวัดได้"
6. **มีผลจริงไหม** วัดเส้นทางปลายทางที่ผู้ใช้รอ ด้วยขนาดข้อมูลและ concurrency จริง คู่กับผลระดับย่อย แล้วรายงานผลย่อยเป็นสัดส่วนของทั้งหมด helper ที่กิน 1% ของ request ทำให้ request เร็วขึ้นได้มากสุด 1%
7. **งานเกิดขึ้นจริงไหม** ยืนยันว่างานรันในช่วงที่จับเวลา: request ถึง server, แถวถูกเขียน, byte ถูกอ่าน, โค้ดใช้ผลลัพธ์ โค้ด lazy (generator ที่ไม่มีใคร iterate, promise ที่ไม่มีใคร await, ผลที่ JIT ทิ้งได้) และ timeout ให้ตัวเลขของงานที่ไม่เคยเกิด

## รายงาน

- นำด้วยคำตัดสิน: เร็วขึ้น / ช้าลง / ไม่ต่างอย่างวัดได้ / สรุปไม่ได้
- ตัวเลขพร้อมหน่วย จำนวนรอบ ช่วง และตัวจำกัด เช่น "p50 41 ms → 33 ms, median ของ 7 รอบต่อฝั่ง, ช่วงหลังแก้ 32–35 ms, ถูกจำกัดด้วย JSON parsing บน core เดียว"
- ตัดสินว่า "สรุปไม่ได้" เมื่ออ้างความต่างแต่ระบุตัวจำกัดไม่ได้ ฝั่งหนึ่งไม่ได้ tune หรือเช็กข้อ 4 และ 7 ไม่ได้ บอกช่องว่างนั้น
- PR ใส่ตัวเลขหลักตัวเดียว รายละเอียดอื่นไว้ใน artifact
