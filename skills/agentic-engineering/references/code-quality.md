# คุณภาพโค้ด: สะอาด อ่านง่าย มีประสิทธิภาพ ดูแลต่อได้

อ่านไฟล์นี้ครั้งแรกที่จะเขียนโค้ดใน session แล้วใช้กับทุกบรรทัดที่เขียน รวมถึง diff ของ `implementer`

ข้อยกเว้น: โค้ดทิ้งของ `playbooks/prototype.md` และ script ชั่วคราวที่รันครั้งเดียวแล้วลบ ไม่ต้องทำหัวข้อ 1, 3 และ 4 (ยังเลี่ยงจุดช้าในหัวข้อ 2 ถ้าความเร็วคือสิ่งที่ prototype วัด) โค้ดจาก prototype ที่จะเก็บไว้ใช้จริง ต้องเขียนใหม่ตามไฟล์นี้

โค้ดที่ดีคือโค้ดที่คนถัดไป (รวมถึงผู้ใช้เองในอีก 6 เดือน) อ่านแล้วเข้าใจเร็ว แก้แล้วไม่พังที่อื่น และทำงานเร็วพอโดยไม่สิ้นเปลือง **ยาวไม่ได้แปลว่าดี** และสั้นจนต้องถอดรหัสก็ไม่ดี เป้าคือสั้นที่สุดที่ยังอ่านออกทันที

เมื่อเป้าหมายขัดกัน: **ถูกต้อง > อ่านง่ายและดูแลง่าย > เร็ว** ยกเว้นงานที่ความเร็วเป็นข้อกำหนด (hot path, ข้อมูลใหญ่) ซึ่งตัดสินด้วยตัวเลขที่วัดจริง

## 1. สะอาดและกระชับ

- **ทำเท่าที่ต้องทำ** ไม่มีโค้ด "เผื่อไว้" ไม่สร้าง wrapper หรือ abstraction ที่มี implementation เดียว ใช้ standard library และของเดิมในโปรเจกต์ก่อนเขียนใหม่
- **ฟังก์ชันทำเรื่องเดียว** ถ้าต้องใช้คำว่า "และ" อธิบายว่ามันทำอะไร ให้พิจารณาแยก ฟังก์ชันยาวเกินราว 40 บรรทัดหรือซ้อนเกิน 3 ชั้น คือสัญญาณให้แยก
- **early return แทน if ซ้อน** ตรวจกรณีผิดแล้วออกก่อน เส้นทางหลักจะได้อยู่ระดับซ้ายสุด
- **ชื่อบอกความหมาย** ไม่ย่อจนต้องเดา boolean ขึ้นต้นด้วย `is` `has` `can` ใส่หน่วยในชื่อเมื่อมีหน่วย (`timeoutMs`, `priceBaht`)
- **ไม่มีตัวเลขลอย** (magic number) ตั้งชื่อเป็นค่าคงที่ เช่น `MAX_RETRY = 3`
- **ไม่ฉลาดเกินไป** one-liner ที่ซ้อนหลายชั้นหรือ ternary ซ้อน ให้แยกเป็นตัวแปรที่มีชื่อ ชื่อตัวแปรกลางทางคือคำอธิบายที่ไม่มีวันเก่า
- **logic ซ้ำ** ที่งานนี้แตะ รวมเป็นที่เดียวเมื่อมันคือกฎเดียวกันที่ต้องเปลี่ยนพร้อมกัน (สูตรราคา เงื่อนไขสิทธิ์) โค้ดที่หน้าตาคล้ายกันแต่เปลี่ยนด้วยเหตุผลต่างกัน ปล่อยแยกได้ ซ้ำสามบรรทัดอ่านง่ายกว่า abstraction ที่เดาอนาคต
- **ลบซาก** โค้ดที่ไม่ถูกเรียก import ที่ไม่ใช้ โค้ดที่ comment ทิ้งไว้ log ดีบัก
- **ตาม style ของ repo** ใช้ formatter และ lint ที่มี ไม่ปรับรูปโค้ดที่ไม่เกี่ยวกับงาน (diff จะบวมและรีวิวยาก)

## 2. ประสิทธิภาพ

### ทำเสมอ ไม่ต้องวัด

ข้อเหล่านี้ไม่ทำให้อ่านยากขึ้น จึงเป็นค่าเริ่มต้น:
- **เลือกโครงสร้างข้อมูลตามการใช้** ค้นหาบ่อยใช้ `Set` `Map` `dict` แทนการไล่ list ใน loop
- **เลี่ยง O(n²) ที่เลี่ยงได้ง่าย** loop ซ้อนที่ค้นหากันเอง เปลี่ยนเป็นสร้าง map ครั้งเดียวแล้วค้น
- **ไม่ query DB หรือเรียก API ใน loop** (ปัญหา N+1) รวมเป็น batch, `IN (...)` หรือ join
- **ไม่ทำงานซ้ำใน loop** ยกค่าที่ไม่เปลี่ยนออกนอก loop ไม่อ่านไฟล์ ไม่ compile regex ไม่สร้าง connection ซ้ำ
- **IO ที่ไม่ขึ้นต่อกันทำพร้อมกัน** เช่น `Promise.all`, `asyncio.gather` เมื่อปลายทางรับไหว
- **ข้อมูลใหญ่** ใช้ stream หรือแบ่งหน้า แทนโหลดทั้งก้อนเข้าหน่วยความจำ คอลัมน์ที่ใช้ค้นหรือ join ต้องมี index
- **ปิด resource** ไฟล์ connection listener timer subscription
- **UI** ไม่คำนวณหนักหรือยิง request ทุกครั้งที่ render หรือกดปุ่ม

ใช้กับโค้ดที่เขียนใหม่และบรรทัดที่งานนี้แก้อยู่แล้ว จุดช้าในโค้ดเดิมที่งานนี้ไม่ได้แตะ (โดยเฉพาะในงานแก้บั๊กที่ต้อง diff เล็กที่สุด) ไม่ต้องแก้ ให้เขียนเสนอหนึ่งบรรทัดในรายงานพร้อม `file:บรรทัด`

### ทำเมื่อวัดแล้วเท่านั้น

cache, memoize, เขียน algorithm ใหม่ให้เร็ว, micro-optimization ทำเมื่อมีตัวเลขบอกว่าช้าจริง ใช้ `playbooks/performance.md` และ `references/benchmark.md` ถ้าการเร่งความเร็วทำให้อ่านยากขึ้น ต้องมีตัวเลขยืนยันในรายงาน และคอมเมนต์ในโค้ดบอกว่าทำไมต้องแบบนี้

## 3. คอมเมนต์ภาษาไทย

คอมเมนต์เป็นภาษาไทย ศัพท์เทคนิคทับศัพท์ได้ ชื่อตัวแปรและฟังก์ชันยังเป็นภาษาอังกฤษ เป้าหมายคือคนเปิดไฟล์ครั้งแรกรู้ทันทีว่าแต่ละส่วนทำอะไร โดยไม่ต้องอ่านโค้ดทุกบรรทัด

**ต้องมี:**
1. **หัวไฟล์** (ไฟล์ใหม่ หรือไฟล์ที่ยังไม่มี) 1–3 บรรทัด: ไฟล์นี้รับผิดชอบเรื่องอะไร และใครเรียกใช้
2. **ทุกฟังก์ชัน เมธอด และคลาส** ที่ export ออกไป หรือมี logic ไม่ตรงไปตรงมา ใช้รูปแบบ doc comment ของภาษานั้น (JSDoc, docstring, `///`, KDoc) บอก:
   - ทำอะไร: ผลลัพธ์ในหนึ่งประโยค ไม่ใช่วิธีทำ
   - รับอะไร คืนอะไร: ความหมาย หน่วย และค่าว่างได้ไหม (ข้ามส่วนที่ type บอกครบแล้ว)
   - ผลข้างเคียง: เขียน DB ส่ง request แก้ค่าที่รับเข้ามา และ error ที่โยนออกไป
   - ข้อควรระวังสำหรับคนแก้ต่อ (ถ้ามี)

   ไม่ต้องมี doc comment: getter/setter ธรรมดา ฟังก์ชันบรรทัดเดียวที่ชื่อบอกครบแล้ว callback สั้น ๆ แบบ inline ส่วน helper สั้นที่ชื่อบอกเกือบครบ (`formatDate` 3 บรรทัด) ใช้คอมเมนต์บรรทัดเดียวพอ คอมเมนต์ที่แค่แปลชื่อฟังก์ชันเป็นไทย (`// ฟังก์ชันคำนวณยอดรวม` เหนือ `calcTotal`) ไม่มีประโยชน์ ให้บอกสิ่งที่ชื่อไม่ได้บอกแทน
3. **หัวช่วง logic** ในฟังก์ชันที่มีหลายช่วง: คอมเมนต์หนึ่งบรรทัดก่อนแต่ละช่วงว่าช่วงนี้ทำอะไรในภาพรวม เช่น `// รวมสินค้าซ้ำในตะกร้าก่อนคิดส่วนลด` ถ้าฟังก์ชันต้องมีหัวช่วงหลายหัว ให้พิจารณาแยกแต่ละช่วงเป็นฟังก์ชันที่ชื่อตามหัวนั้น
4. **ทำไม** เมื่อโค้ดบอกเองไม่ได้: เงื่อนไขที่ดูแปลก ค่าคงที่ที่มาจากข้อกำหนด workaround ของ library ทางที่ไม่ชัดว่าทำไมเลือก ใส่ที่มา (ลิงก์ issue หรือเอกสาร) ถ้ามี
5. **ตัวอย่าง input → output** สำหรับ regex สูตร bit operation หรือ algorithm ที่คนทั่วไปไม่คุ้น

**ห้าม:**
- คอมเมนต์ทวนโค้ดทีละบรรทัด เช่น `i++ // เพิ่ม i` คอมเมนต์แบบนี้ไม่ช่วยใคร และกลายเป็นข้อมูลผิดทันทีที่โค้ดเปลี่ยน
- คอมเมนต์ที่ไม่ตรงกับโค้ด แก้โค้ดเมื่อไรต้องแก้คอมเมนต์ที่เกี่ยวใน commit เดียวกัน
- คอมเมนต์อธิบาย workaround ยาวเป็นย่อหน้า นั่นคือสัญญาณว่าโค้ดผิด ให้แก้โค้ด

**แก้ไฟล์เดิม:** ใส่หรืออัปเดตคอมเมนต์ของฟังก์ชันที่งานนี้แตะ ไม่ไล่ใส่ทั้งไฟล์ เว้นแต่ผู้ใช้ขอ ฟังก์ชันที่แตะมีคอมเมนต์ภาษาอังกฤษอยู่ ให้แทนด้วยภาษาไทย ไม่ทิ้งไว้สองภาษา

**ยังเป็นภาษาอังกฤษ:** ชื่อฟังก์ชัน ตัวแปร คลาส ไฟล์ ข้อความ log และ error message, string ที่ระบบอื่นอ่าน, คีย์ JSON, ชื่อคอลัมน์ และ endpoint เว้นแต่ repo หรือผู้ใช้กำหนดเป็นอย่างอื่น

**รูปแบบตามภาษา:** Python docstring `"""..."""` ใต้ `def`/`class` · JS/TS JSDoc `/** */` พร้อม `@param` `@returns` `@throws` · Java/C#/PHP doc comment มาตรฐาน · Go `//` เหนือฟังก์ชัน ขึ้นต้นด้วยชื่อฟังก์ชัน · Rust `///` · SQL/Shell `--` หรือ `#` เหนือบล็อก

ตัวอย่าง:

```ts
// คำนวณยอดชำระของตะกร้า ใช้ทั้งหน้า checkout และ API สร้างคำสั่งซื้อ

/**
 * คิดยอดรวมสุทธิของตะกร้าหลังหักส่วนลด
 * @param items สินค้าในตะกร้า ว่างได้ (คืน 0)
 * @param coupon คูปองที่ผ่านการตรวจแล้ว หรือ null ถ้าไม่ใช้
 * @returns ยอดสุทธิเป็นสตางค์ ไม่ติดลบ
 * @throws CouponExpiredError ถ้าคูปองหมดอายุระหว่างคิดเงิน
 */
export function calcTotalSatang(items: CartItem[], coupon: Coupon | null): number {
  // รวมสินค้าซ้ำก่อน เพราะส่วนลดขั้นบันไดคิดจากจำนวนต่อรายการ
  const merged = mergeDuplicates(items);
  ...
  // ใช้สตางค์ (จำนวนเต็ม) แทนบาททศนิยม กันปัดเศษเพี้ยนเมื่อบวกหลายรายการ
  return Math.max(0, subtotal - discount);
}
```

## 4. ดูแลต่อได้

- **แยก logic ธุรกิจออกจาก IO และ UI** ส่วนคำนวณจะได้ test ได้โดยไม่ต้องต่อ DB หรือเปิดหน้าจอ
- **ฟังก์ชัน pure เมื่อทำได้** รับค่าเข้า คืนค่าออก ไม่แก้ของข้างนอก state ที่ต้องมีให้มีเจ้าของที่เดียว
- **ตรวจข้อมูลที่ขอบ** input ของผู้ใช้และข้อมูลจาก API ภายนอก ตรวจตอนเข้าระบบ ข้างในเชื่อ type ได้
- **error ต้องมีความหมาย** จัดการ หรือส่งต่อพร้อมข้อความที่บอกว่าเกิดอะไรกับข้อมูลไหน ห้ามกลืน error เงียบ (`catch {}` เปล่า)
- **ไม่ hardcode** config, URL ของแต่ละ environment และ secret
- **ใช้ type** เมื่อ repo ใช้ TypeScript หรือ type hints อยู่แล้ว
- **dependency ใหม่ต้องคุ้ม** ถ้า standard library ทำได้ในราว 10 บรรทัด ไม่เพิ่ม library
- **test พฤติกรรมที่เปลี่ยน** ตาม `references/verification.md`

## 5. เช็กก่อนส่ง

อ่าน diff ของตัวเองทั้งหมดอีกรอบ แล้วตอบให้ได้ทุกข้อ:
- [ ] ตัดอะไรออกได้อีกโดยพฤติกรรมไม่เปลี่ยน (โค้ดเผื่อ ซาก import ที่ไม่ใช้ log ดีบัก)
- [ ] มี loop ที่ query/เรียก API หรือค้นหาซ้อนกันไหม
- [ ] ทุกฟังก์ชันใหม่หรือที่แก้ (ที่เข้าเกณฑ์) มีคอมเมนต์ภาษาไทยบอกว่าทำอะไร รับ/คืนอะไร และผลข้างเคียง ไม่ใช่แค่แปลชื่อ
- [ ] คอมเมนต์เดิมที่เกี่ยวกับโค้ดที่แก้ ยังตรงกับโค้ด
- [ ] ชื่อทุกตัวอ่านแล้วรู้ความหมายโดยไม่ต้องดูบริบท
- [ ] error ทุกทางมีคนจัดการ และไม่มี catch เปล่า
- [ ] lint และ formatter ของ repo ผ่าน

ข้อไหนตอบว่าไม่ ให้แก้ก่อนส่ง ข้อไหนตั้งใจเลือกต่างจากนี้ ให้บอกเหตุผลในรายงาน
