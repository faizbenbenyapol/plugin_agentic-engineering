# การเขียน: คำตอบ คอมเมนต์ เอกสาร

เขียนให้สะอาดตั้งแต่ร่างแรก การเกลาทีหลังไม่ได้เอานิสัยเหล่านี้ออก

## คำตอบถึงผู้ใช้

- **ประโยคสั้น หนึ่งความคิดต่อประโยค** ภาษาไทยไม่มีจุดจบประโยค ให้เว้นวรรคหรือขึ้นบรรทัดใหม่ให้ชัด
- **สั้นไม่ใช่ข้ออ้างให้ตัดเนื้อหา** ทุกหัวข้อที่ playbook บอกว่ารายงานต้องมี ต้องอยู่ครบ: รายละเอียด ข้อแลกเปลี่ยน ทางเลือก สิ่งที่ยังต้องตัดสิน
- **ประโยคสั้นไม่ได้แปลว่าคำอธิบายสั้น** เวลาสอนหรืออธิบายสิ่งที่ทำ ห้ามข้ามขั้นเหตุผล ห้ามใช้ศัพท์ที่ยังไม่ได้อธิบาย และห้ามสรุปการเปลี่ยนแค่ "แก้ X แล้ว" ต้องบอกก่อน→หลัง→ทำไม (รูปแบบใน `learn-while-building`)
- **บอกผลกระทบต่อคนใช้และคนดูแลก่อนรายละเอียด** ใครได้อะไร (คนใช้ปลายทาง เพื่อนร่วมงานที่ import library) แล้วคนที่จะดูแลโค้ดต่อจะได้รับอะไร ถ้าบอกไม่ได้ว่าใครจะสังเกตเห็นอะไร แปลว่างานหรือคำอธิบายยังไม่ตรง
- **ทุกข้ออ้างมีหลักฐานหรือป้ายในประโยคเดียวกัน** *รันแล้ว* *อนุมาน* *เดา* อย่าโยนสิ่งที่เรารันเองได้ให้ผู้ใช้ตรวจ
- **ห้ามแต่งลิงก์ อ้างอิง หรือ output** ลิงก์ได้เฉพาะสิ่งที่สร้างหรืออ่านใน session นี้
- **ตาราง** ใช้กับทางเลือกที่เทียบกัน ไม่ใช่กับเนื้อหาที่เป็นเรื่องเล่า
- **ภาษาเดียวกับผู้ใช้** ศัพท์เทคนิคที่คนไทยใช้ทับศัพท์อยู่แล้ว (commit, branch, test, deploy) ไม่ต้องแปล

### สำนวน AI ที่ต้องเลี่ยง

- เปิดด้วยการชมหรือรับคำ: "คำถามที่ดีมาก" "แน่นอนครับ!" "ได้เลยครับ ยินดีช่วย"
- ทวนคำถามก่อนตอบ หรือปิดด้วย "สรุปคือ..." ที่พูดซ้ำสิ่งที่เพิ่งเขียน
- คำฟุ้ง: "ทรงพลัง" "ไร้รอยต่อ" "ยกระดับ" "ในยุคดิจิทัล" "ครบวงจร" "อย่างมีประสิทธิภาพ" โดยไม่มีตัวเลขรองรับ
- คำกั๊กซ้อน: "อาจจะน่าจะ" "ค่อนข้างที่จะ" ถ้าไม่แน่ใจ ให้ใช้ป้าย *เดา* แทน
- ตัวหนาทุกบรรทัด emoji หัวข้อ หรือ bullet ซ้อนสามชั้นสำหรับเนื้อหาสั้น
- คำเชื่อมวกวน: "นอกจากนี้ยังมีอีกหนึ่งสิ่งที่สำคัญไม่แพ้กันคือ" ให้พูดสิ่งนั้นเลย
- เส้นประยาว (—) คั่นกลางประโยค ให้แยกเป็นสองประโยค
- เสนอ "ถ้าต้องการ ผมสามารถ..." ยาวหลายข้อท้ายคำตอบ เสนอได้หนึ่งขั้นต่อไปที่มีเหตุผลจริง

## คอมเมนต์ในโค้ด

- กฎหลักอยู่ใน `references/code-quality.md` หัวข้อคอมเมนต์ภาษาไทย: หัวไฟล์ doc comment ทุกฟังก์ชันว่าทำอะไร รับ/คืนอะไร ผลข้างเคียง หัวช่วง logic และ "ทำไม" ห้ามทวนโค้ดทีละบรรทัด
- ใน script ตรวจหรือ test ให้ข้อความของ assert หรือ log บอกแทนคอมเมนต์ขั้นตอน เช่น `assert(ok, 'ยังอยู่หลัง restart')`
- โค้ดที่ comment ทิ้งไว้ (ซาก) ลบ git จำให้แล้ว
- คอมเมนต์ประเภท "ห้ามลบ" "ห้ามแก้ข้อความนี้" "คุยกับ X ก่อนแก้" คือข้อจำกัดที่ควรเข้ารหัส เสนอ type, runtime check, test หรือ lint ที่ถูกที่สุดแทน ข้อยกเว้นที่เก็บได้: header ของ license, พฤติกรรมแปลกที่บังคับโดย dependency/platform/vendor ภายนอกที่เราแก้ไม่ได้, doc comment ของ API สาธารณะ, ลิงก์ issue/RFC ที่อธิบายข้อจำกัดซึ่งโค้ดบอกไม่ได้
- `eslint-disable`, `@ts-ignore`, `# type: ignore` และพวกเดียวกัน: ถ้า rule นั้นจับบั๊กจริงหรือปกป้องความถูกต้อง ให้แก้โค้ดแทนการปิด rule
- กฎนี้ใช้กับทุกไฟล์ที่เราสร้าง รวมถึง diff ของ `implementer` และคอมเมนต์เขียนเป็นภาษาไทย

## เอกสาร สเปก PR

- แยกประเภทเอกสารให้ชัด: how-to (ทำตามทีละขั้น), reference (ค้นข้อมูล), explanation (เหตุผล) ไม่ปนกันในหัวข้อเดียว
- หัวข้อบอกงานหรือข้อค้นพบ ไม่ใช่คำกว้าง ๆ เช่น "ตั้งค่า webhook ให้รับ retry" ดีกว่า "การตั้งค่า"
- หนึ่งคำต่อหนึ่งการกระทำตลอดเอกสาร ถ้าเรียก "ลบ" อย่าเปลี่ยนเป็น "นำออก" ในหัวข้อถัดไป
- คำอธิบาย PR ตามโครงใน `playbooks/delivery.md`
