# งานขนานและการรีวิวแบบโจมตี

agent ทุกตัวมีต้นทุน **ประลองและแตกงานใช้เมื่อผู้ใช้สั่งเท่านั้น** รีวิวแบบโจมตีใช้ `reviewer` หนึ่งตัวในระดับเต็ม blast radius หัวหน้าทำเอง

## ประลอง (arena): หลายคนทำงานเดียวกัน แล้วรวมส่วนที่ดีที่สุด

ใช้เมื่อ: ความพยายามครั้งเดียวจะล็อกรูปผิด เช่น ร่างแบบ หรือ implementation ที่ถูกได้หลายรูป ต่างจากการแตกงาน (ข้างล่าง) ที่แบ่งงานคนละส่วน

1. **ตั้งกรอบ** ทุกคนได้ prompt เดียวกัน prompt จึงเป็นสัญญา บอกผลงานที่ต้องได้ แล้วหัวหน้าเขียนเกณฑ์ให้คะแนน 3–6 ข้อที่เจาะจงกับงานนี้ (ผู้แข่งไม่เห็นเกณฑ์ เห็นแค่งาน)
2. **เลือกผู้แข่ง** อย่างน้อยสองตัว ต่างโมเดลกันเมื่อเป็นงานที่ต้องใช้วิจารณญาณ (เช่น `implementer` บน Sonnet และอีกตัวบน Opus) โมเดลเดียวกันหลายตัวได้เมื่องานเน้นการสร้างปริมาณ
3. **แยกที่เขียน** แต่ละตัวมี worktree ของตัวเอง (`isolation: worktree`) หรือโฟลเดอร์ scratch ของตัวเอง
4. **ปล่อยพร้อมกัน** ทุกตัวได้งาน path ของข้อมูลพื้นฐาน ที่เขียนของตัวเอง และคำสั่งให้ส่งผลงานพร้อมเหตุผลสั้น ๆ ว่าพิจารณาทางไหนและทิ้งอะไร ตัวไหนไม่ส่งผล ให้ไปต่อด้วย N−1 และจดไว้
5. **ให้คะแนน** หัวหน้าอ่านทุกผลงานจนจบ ให้คะแนนตามเกณฑ์ทีละข้อ ไม่ใช่ความรู้สึกรวม ถ้ามีเวลา ให้ `reviewer` (คนละโมเดลกับหัวหน้าถ้าได้) ให้คะแนนแยกอีกชุด ตรงกัน = ยืนยัน ไม่ตรง = มีคนลำเอียงหรือเกณฑ์กำกวม อ่านเหตุผลทั้งสองก่อนตัดสิน
6. **เลือกฐาน** ฐานที่คนดูแลต่อจะต่อเติมได้ง่ายที่สุดโดยไม่ทำ invariant พัง ถ้าสูสี เลือกขอบที่สะอาดกว่าหรือ API ที่เล็กกว่า
7. **graft** เดินดูตัวที่แพ้อีกรอบหาสิ่งที่ควรยกมา ปกติตัวละหนึ่งสองอย่าง ไม่ใช่ส่วนใหญ่ ใส่ด้วยมือให้เข้ากับแนวคิดเดียว ถ้าทุกตัวไปทางเดียวกันคือฉันทามติที่แรง ส่งรูปนั้นเลย ถ้าต่างกันสุดขั้ว แปลว่าโจทย์ไม่ชัด ให้ตั้งกรอบใหม่แล้วรันใหม่ อย่าเฉลี่ยความต่าง
8. **ตรวจ** ผลรวมเหมือนงานอื่น ถ้าการตรวจเจอปัญหาที่ arena พลาด แปลว่ากรอบผิด (ตั้งใหม่) หรือมีผู้แข่งจับได้แต่เราไม่ได้ยกมา (กลับไปข้อ 7)

ผลงาน: สิ่งที่สังเคราะห์แล้ว + บันทึกสั้น: ฐานที่เลือกและทำไม ความเห็นของผู้ให้คะแนนอีกคน สิ่งที่ยกมาจากแต่ละตัว สิ่งที่ทิ้ง และผลการตรวจ

## แตกงาน (swarm): หลายคนทำคนละส่วน แล้วรวมรายงาน

ใช้เมื่อ: ต้องการความครอบคลุม (audit หลาย subsystem, ตรวจหลาย scenario, ลองหลายเส้นทาง) ไม่ใช่การเปรียบเทียบ การใช้ arena เมื่อต้องการความครอบคลุม หรือใช้ swarm เมื่อต้องการเปรียบเทียบ คือความผิดพลาดที่พบบ่อย

1. บอกเงื่อนไข "เสร็จ" และรูปของรายงานที่ต้องได้ เลือกรูป: แบ่งชิ้น หรือแข่งกันบน brief เดียวกัน ถ้าแข่ง ให้ประกาศกฎเลือกก่อนปล่อย (ตัวแรกที่ผ่าน / จัดอันดับทั้งหมด / ดีที่สุด)
2. brief แต่ละชิ้นครบในตัว: เป้าหมาย ขอบเขต ชิ้นที่ได้ วิธีตรวจ สิ่งที่ต้องรายงาน ถ้าตรวจหรือวัด commit ให้ระบุ SHA และวิธีวัด (จำนวนรอบ หนึ่งตัวอย่างคืออะไร ลำดับ) ให้มันบันทึกทั้งสองอย่างในผล
3. รายงานใช้คำตัดสินชุดเดียวกับ SKILL.md: `ผ่าน`, `ไม่ผ่าน` หรือ `สรุปไม่ได้` (รวมกรณีติดขัดทำต่อไม่ได้ พร้อมเหตุผล) พร้อมหลักฐาน ตัวที่พิสูจน์ข้อบกพร่องได้ต้องรายงานทุกข้อที่พิสูจน์ได้ ไม่ใช่แค่ข้อแรก
4. รวมผล: ทิ้งผลที่ไม่บันทึก SHA และวิธีที่ brief สั่ง แล้วปล่อยตัวใหม่หนึ่งครั้ง พลาดซ้ำให้จดเป็นช่องว่าง ช่องว่างไม่ใช่ผ่าน งานครอบคลุมต้องมีผลครบทุกชิ้น
5. รายงานเดียวในแชท: ตารางผล ปัญหาบรรทัดละข้อ ช่องว่างหรือตัวที่หลุด ไม่แปะผลดิบ

## รีวิวแบบโจมตี (interrogate)

ฝ่ายโจมตีพยายามทำให้การเปลี่ยนหรือดีไซน์พัง ข้อค้นพบรอดเฉพาะที่การรันพิสูจน์ได้ รายงานข้อค้นพบ ไม่ลงมือแก้

1. **ขอบเขต:** ตามที่ผู้ใช้ระบุ ไม่งั้นคือ diff ของ branch จาก merge base รวม working tree **เจตนา:** ทวนจากข้อความผู้ใช้ commit และสเปก
2. **ปล่อยผู้โจมตี** `reviewer` หนึ่งตัว (สองตัวต่างโมเดลเมื่อผู้ใช้สั่ง) ได้ขอบเขต เจตนา และ brief นี้:
   > ทำให้การเปลี่ยนนี้พัง พิสูจน์ทุกข้อค้นพบด้วยการรันกับโค้ดจริง เช่น test ที่ fail, script ทำซ้ำ, หรือ output ของคำสั่งที่แสดงพฤติกรรมผิด ถ้าเป็นดีไซน์หรือแผน ให้ทำ prototype หรือลองกับ tree ปัจจุบัน เก็บ repro ไว้ในพื้นที่ของตัวเอง รายงานแต่ละข้อด้วย ชื่อเรื่อง คำสั่งที่รัน output ที่ได้ และ output ที่เจตนาต้องการ ตัดทุกอย่างที่ไม่ได้รันออก รวมถึงสไตล์ การตั้งชื่อ โครงสร้าง และความเสี่ยงที่ต้องมีการเปลี่ยนในอนาคตถึงจะมีผล ไม่เจออะไรก็เป็นผลที่ใช้ได้
3. **ตรวจทุกข้อ** หัวหน้ารันคำสั่งของแต่ละข้อซ้ำเอง เก็บข้อที่ output แสดงความล้มเหลวและความล้มเหลวนั้นขัดเจตนา ทิ้งที่เหลือ รวมข้อที่ต้นเหตุเดียวกัน ผู้โจมตีแต่ละตัวเจอคนละอย่าง ผลจึงเก็บทุกข้อที่ยืนยันแล้ว ไม่ใช่รายการของตัวใดตัวหนึ่ง

ผลงาน: เจตนา (ทวนแล้ว), ข้อค้นพบที่ยืนยันแล้ว (คำสั่ง output ขัดเจตนายังไง ใครเจอ) หรือ "ไม่มีข้อค้นพบที่ยืนยันได้", และจำนวนข้อที่ทิ้งของแต่ละตัวพร้อมเหตุผล

## Blast radius: การเปลี่ยนนี้จะไปพังอะไรที่อื่น

ใช้เมื่อ: "จะพังอะไรไหม" หรือ diff เล็กที่ยังไม่ไว้ใจ ระดับเต็มทำก่อนส่งเสมอ

การแค่ลิสต์ caller ไม่ใช่งานนี้ grep ทำได้ในวินาที งานคือหาการพังที่ grep มองไม่เห็น และ **อย่าเชื่อ writeup ของตัวเอง** writeup ที่ฟังดูถูกอ่านแล้วน่าเชื่อเสมอไม่ว่าจะจริงไหม ให้หาข้อเท็จจริงหนึ่งสองข้อที่ทั้งเรื่องพึ่งพา แล้วพิสูจน์ด้วยการรัน

1. **อ่านการเปลี่ยน** diff, symbol ที่เพิ่ม/เปลี่ยน/ลบ, และสิ่งที่มันทำต่างไป รวมส่วนที่ diff ไม่ได้เขียนให้เห็น
2. **หาข้อเท็จจริงเดียวที่ทำให้ปลอดภัย** การเปลี่ยนที่ดูเสี่ยงส่วนใหญ่ปลอดภัยเพราะข้อเท็จจริงข้อเดียว เช่น "การเรียกนี้ลบแค่ cache entry ที่ตายแล้วและไม่ทำอย่างอื่น" ถ้ามันจริง กรณีเสี่ยงส่วนใหญ่จบในทีเดียว ใช้เวลาตรงนี้ ไม่ใช่กับรายการ "อาจจะ" ยาว ๆ
3. **ดูตรงที่ grep หยุด** อ่าน source ของ library ที่เรียก (เช็ก version ที่ pin และ patch ในเครื่อง) ไล่จังหวะการทำงาน (microtask, unmount/teardown) ตามสิ่งที่ค้น symbol ไม่เจอ: JSON ที่ API คืน, คอลัมน์ DB, wire format, ภาษาอื่นที่อ่าน byte เดียวกัน, feature flag, โค้ดที่ห่างไปสามทอด
4. **ซื่อตรงกับทุกความเสี่ยง** ให้โอกาสเกิดและต้นทุนจริง แยกที่ยืนยันแล้วกับที่ตรวจแล้วปลอดภัย อ้าง `file:บรรทัด` จริง ค้นแล้วไม่เจอก็เป็นคำตอบ ห้ามแต่ง caller หรือ API
5. **พิสูจน์ข้อเท็จจริงนั้น** เขียน script หรือ test ที่เรียกโค้ดจริง (มักแค่ import library ตัวเดียวกับที่แอปใช้แล้วเรียกฟังก์ชันที่กังวล) รัน แล้วแปะผล ไต่ให้ถึงขั้น 4–5 ของบันไดความมั่นใจ
6. ถ้าผู้ใช้สั่ง ให้ถามคำถามเดียวกันกับสองโมเดลแล้วรวมคำตอบ โมเดลต่างกันจับบั๊กจริงได้ต่างกัน

ผลงาน: สิ่งที่การเปลี่ยนทำ (รวมส่วนที่ไม่ชัด), ข้อเท็จจริงเดียวที่ทำให้ปลอดภัยพร้อมขั้นบันไดและหลักฐาน (พิสูจน์ไม่ได้ให้เขียน "ยังไม่พิสูจน์"), ความเสี่ยงที่ยืนยันแล้ว (พังยังไง file:บรรทัด โอกาส ความรุนแรง วิธีเช็ก), สิ่งที่ตรวจแล้วปลอดภัย, และ test หรือ repro ที่ถูกที่สุดที่ควรรันก่อน merge
