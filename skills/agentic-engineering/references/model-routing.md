# แผนโมเดลและโควตา Claude Pro

ผู้ใช้ใช้แพลน Pro โควตาจำกัดและใช้ร่วมกันทั้งแชทและ Claude Code สกิลนี้ดัดแปลงจาก pstack ซึ่งผู้เขียนแทบไม่มีข้อจำกัดเรื่องโทเค็น จึงต้องปรับทุกจุดที่เผาโควตาโดยไม่ได้เพิ่มคุณภาพ **ประหยัดที่การอ่าน จำนวนรอบ และการเลือกโมเดล ห้ามประหยัดที่การตรวจหรือคำอธิบายถึงผู้ใช้**

## ทำไมไฟล์ใน repo ช่วยประหยัด

ทุก request ส่งบริบททั้งหมดซ้ำ แชทยิ่งยาวยิ่งแพงทุกรอบ ไฟล์รีไควร์เมนต์ `docs/progress.md` และคู่มือส่งมอบทำให้ **`/clear` ได้ระหว่างเฟสโดยไม่เสียความเข้าใจ** session ใหม่อ่านไฟล์สั้น ๆ แทนการแบกแชทยาวทั้งก้อน

## ตารางเฟส → โมเดล

agent เปลี่ยน `/model` ของเซสชันหลักเองไม่ได้ ให้ **บอกผู้ใช้หนึ่งบรรทัดตอนเปลี่ยนเฟส** เฉพาะเมื่อโมเดลที่แนะนำต่างจากตอนนี้

| เฟส | โมเดลเซสชันหลัก | หมายเหตุ |
| --- | --- | --- |
| เก็บรีไควร์เมนต์ งานกลาง | Sonnet | คำถามส่วนใหญ่มาจาก playbook ไม่ต้องใช้ Opus |
| เก็บรีไควร์เมนต์และออกแบบ ระดับเต็ม หรือตัดสินสถาปัตยกรรม | Opus หรือ `/model opusplan` | `opusplan` ใช้ Opus ตอนวางแผน และสลับเป็น Sonnet ตอนลงมือเอง |
| design plan ของ UI | Sonnet | ใช้ Opus เมื่อผู้ใช้ไม่พอใจทิศทางหลังจบหนึ่งรอบแล้ว |
| ลงมือเขียนโค้ดตามแผน | Sonnet | ค่าเริ่มต้นของงานส่วนใหญ่ |
| ค้นกว้างเกินราว 5 ไฟล์ หรือย่อ log ยาว | agent `scout` (Haiku) | ส่งเฉพาะเมื่อคุ้ม ส่งเองทุกครั้งไม่คุ้ม |
| แก้ 2 รอบไม่ผ่าน (โจมตีสมมติฐาน) | Sonnet ต่อ ถ้ายังติดค่อยเขียน `docs/progress.md` แล้ว `/clear` และสลับ Opus | ห้ามสลับกลางแชทยาว (ดูหัวข้อถัดไป) |
| ตรวจระดับเต็ม | agent `reviewer` (Sonnet, เงิน/auth/ข้อมูลจริงใช้ Opus) | งานกลางหัวหน้าอ่าน diff เอง |
| คู่มือส่งมอบ commit และเอกสาร | Sonnet | ประกอบจาก artifact ที่มี ไม่อ่านโค้ดใหม่ |

ใส่โมเดลที่แนะนำลงคอลัมน์ "โมเดลที่แนะนำ" ในตารางแผนของไฟล์รีไควร์เมนต์ ผู้ใช้จะได้เห็นทั้งงานในครั้งเดียว

## สลับโมเดลเฉพาะตอนเริ่มบริบทใหม่

แคชของ prompt ผูกกับโมเดล สลับ `/model` กลางแชทยาวทำให้บริบททั้งก้อนถูกประมวลผลใหม่บนโมเดลใหม่ ซึ่งเป็นจังหวะที่แพงที่สุด จึงแนะนำให้สลับคู่กับ `/clear` เสมอ ยกเว้นแชทยังสั้น

โมเดลที่แพลน Pro ใช้ใน Claude Code ได้เปลี่ยนไปตามช่วงเวลา และค่าเริ่มต้นอาจไม่ใช่ Sonnet ตอนเริ่มงานแรกของ session ให้ผู้ใช้ดู `/model` หนึ่งครั้ง ถ้าแพลนไม่มี Opus ให้ใช้ Sonnet ทุกเฟส แล้วชดเชยด้วยการแบ่งงานเล็กลงและเขียนแผนในไฟล์ให้ละเอียดขึ้น

## จุดที่ควร `/clear`

1. หลังรีไควร์เมนต์ได้รับการยืนยันและ commit แล้ว
2. ระหว่างเฟสของงานใหญ่ หลังเขียน `docs/progress.md` (`playbooks/pickup-and-pause.md`)
3. หลังส่งมอบ ก่อนเริ่มงานเรื่องใหม่

ตอนแนะนำ ให้เตรียมข้อความเริ่มใหม่ให้ผู้ใช้คัดลอกไปวางได้เลย:

```
👉 แนะนำ: /model sonnet แล้ว /clear จากนั้นพิมพ์:
"ทำงานต่อตาม docs/requirements/<ชื่อ>.md ขั้น <n> (บันทึกล่าสุดอยู่ใน docs/progress.md)"
```

แนะนำไม่เกินหนึ่งครั้งต่อการเปลี่ยนเฟส ผู้ใช้ไม่ทำตามก็ทำงานต่อได้ ห้ามหยุดรอ

## ปรับจาก pstack ให้เข้ากับ Pro

| pstack / สกิลต้นทาง (โทเค็นไม่จำกัด) | ที่นี่ (Pro) |
| --- | --- |
| ส่ง implementer agent ทุก slice | หัวหน้าเขียนเอง ส่งเฉพาะ slice ใหญ่และแยกขาด |
| ประลองหลายแบบด้วยหลาย agent | ร่างสองแบบในหัวเฉพาะระดับเต็ม (`references/design.md`) ประลองเมื่อผู้ใช้สั่ง |
| reviewer ขนานหลายตัว หรือวน review-fix หลายรอบ | reviewer หนึ่งตัวเฉพาะระดับเต็ม วนซ้ำเฉพาะข้อระดับบล็อก |
| รัน test ทั้งชุดหลายรอบหลาย seed | รัน test ที่เกี่ยวก่อน ชุดเต็มครั้งเดียวตอนท้าย รันซ้ำหลาย seed เฉพาะงาน concurrency หรือ test ที่ไม่นิ่ง |
| UI prototype 3–5 แบบ | 2–3 แบบในไฟล์เดียวหรือ route เดียว (`anti-ai-ui` references/variants.md) |
| screenshot ทุกสถานะ | screenshot สถานะหลักกับมือถือ สถานะที่เหลือ assert ผ่าน DOM/Playwright |
| อ่าน repo กว้างเพื่อทำความเข้าใจ | grep ก่อน อ่านช่วงบรรทัด ไม่อ่านไฟล์ซ้ำ |
| เอกสารแยกหลายไฟล์ (intent, spec, plan) | ไฟล์รีไควร์เมนต์ไฟล์เดียวรวมแผน + คู่มือส่งมอบหนึ่งไฟล์ |

## โควตาใกล้หมด

ผู้ใช้บอกว่าโควตาใกล้หมด หรือ `/usage` แสดงว่าใกล้เต็ม: ทำ slice ปัจจุบันให้จบที่จุดที่ commit ได้ เขียน `docs/progress.md` แล้วบอกผู้ใช้ว่าจะกลับมาทำต่อด้วยข้อความไหน ห้ามเริ่ม slice ใหม่ครึ่ง ๆ กลาง ๆ

ผู้ใช้สั่ง **"เต็มกำลัง"** ให้ยกเลิกข้อจำกัดในไฟล์นี้สำหรับงานนั้น แต่ยังต้องบอกโมเดลที่แนะนำ
