# รายงานถึงผู้ใช้: เสร็จทีละขั้น และรายงานจบงาน

ไฟล์นี้เป็นแหล่งเดียวของรูปแบบรายงาน ที่อื่น (SKILL.md, `learn-while-building`, `writing.md`) ชี้มาที่นี่ ส่วน hook ตอนเริ่ม session มีฉบับย่อไว้ให้งานเบาที่ไม่ได้โหลดสกิล แก้กฎที่นี่แล้วให้แก้ฉบับย่อใน `hooks/session-context.md` ให้ตรงกันด้วย

ผู้ใช้คนนี้บอกไว้ชัดว่าคำอธิบายที่สั้นเกินไปอ่านแล้วไม่รู้เรื่อง และอยากรู้ว่าทำอะไรไปทีละอย่าง ใช้กฎในไฟล์นี้กับ **ทุกระดับงาน รวมตอนปิดโหมดสอน** เพราะมันเป็นส่วนของรายงาน ไม่ใช่การสอน ประหยัดโควตาด้วยการอ่านให้แคบลง ไม่ใช่ด้วยการตัดคำอธิบาย ย่อได้เฉพาะเมื่อผู้ใช้สั่ง "สอนสั้น"

## ส่งยังไงให้ถึง

ข้อความระหว่าง tool call อาจถูกย่อก่อนถึงผู้ใช้ ถ้ามีเครื่องมือส่งข้อความถึงผู้ใช้ (เช่น `SendUserMessage`) ให้ส่ง "เสร็จขั้นที่ x/y" และบล็อกสอนผ่านเครื่องมือนั้น ส่วนรายงานจบงานเป็นข้อความสุดท้าย จึงพิมพ์ตามปกติได้

## 1. เสร็จขั้นที่ x/y (ระหว่างทาง)

ส่งทันทีที่ขั้นในแผนหรือ slice ใดเสร็จ ก่อนเริ่มขั้นถัดไป ห้ามเก็บไว้รวมตอนท้าย งานที่มีขั้นเดียวให้รวมเข้าไปในรายงานจบงานได้เลย

ใช้ 4–8 บรรทัด ภาษาธรรมดา เขียนให้คนที่ไม่ได้เห็นโค้ดอ่านแล้วรู้เรื่อง:

```
**เสร็จขั้นที่ <x>/<y>: <ชื่อขั้นแบบภาษาคน>**
- ทำอะไรไป: <1–2 ประโยค เล่าเหมือนเล่าให้เพื่อนฟัง ไม่เริ่มด้วยชื่อไฟล์>
- แปลว่าอะไรสำหรับคุณ: <ตอนนี้แอปหรือโค้ดต่างจากเดิมยังไง ใครจะเห็นอะไร>
- รู้ได้ยังไงว่าใช้ได้: <สิ่งที่รันแล้วเห็นจริง และผลนั้นแปลว่าอะไร> (*รันแล้ว* / ยังไม่ได้ตรวจ)
- ไฟล์ที่แตะ: `file:บรรทัด` (ไว้ท้าย สำหรับคนที่อยากเปิดดูเอง)
- ต่อไป: <ขั้นถัดไปจะทำอะไร เพราะอะไร>
```

ถ้าผู้ใช้สั่ง "สอนสั้น" ให้เหลือ 2 บรรทัด คือ "ทำอะไรไป" กับ "แปลว่าอะไรสำหรับคุณ"

## 2. รายงานจบงาน

เรียงจากส่วนที่เข้าใจง่ายไปหารายละเอียดเทคนิค ความยาวตามขนาดงาน ส่วนไหนไม่มีเนื้อหาให้ตัดทิ้ง:

1. **สรุปสั้น ๆ** (ต้องมีเสมอ)
2. **ทำอะไรไปบ้าง** (ต้องมีเสมอ ใช้ฉบับเต็มหรือฉบับย่อตามหัวข้อ 3)
3. หลักฐาน: บรรทัดสรุปของ test/build หรือสิ่งที่เห็นจริง งานแก้บั๊กให้แปะผลตอนที่ยังพัง แล้วตามด้วยผลตอนที่ผ่าน
4. สิ่งที่ยังไม่ได้ตรวจ ขั้นที่ข้าม และเรื่องที่ผู้ใช้ต้องตัดสินใจ
5. ใครตัดสินอะไร และ REQ/EDGE ผ่าน x/y พร้อมข้อที่ไม่ผ่าน (ตารางเต็มอยู่ในคู่มือส่งมอบ ไม่ต้องพิมพ์ซ้ำ) รวมถึงคำขอเปลี่ยนที่อนุมัติแล้วหรือยังรออยู่
6. path ของคู่มือส่งมอบ (งานระดับกลางขึ้นไป)
7. แผนโมเดลของงานถัดไป หรือจุด `/clear` ถ้ามี
8. สรุปบทเรียน (เมื่อโหมดสอนเปิด รูปแบบอยู่ใน `learn-while-building`)

ห้ามสร้างลิงก์หรือ output ที่ไม่ได้เห็นจริงใน session นี้

### สรุปสั้น ๆ

เขียน 2–4 ประโยค โดยไม่มีชื่อไฟล์และไม่มีศัพท์ที่ยังไม่ได้อธิบาย ให้ตอบว่าเดิมมีปัญหาอะไร ตอนนี้แก้แล้วเป็นยังไง และผู้ใช้ต้องทำอะไรต่อไหม คนที่อ่านแค่ส่วนนี้ต้องรู้เรื่องทั้งงาน

**เช็กก่อนส่ง:** อ่านอีกรอบโดยสมมติว่าเป็นคนที่ไม่ได้ดูงานนี้เลย ถ้ายังต้องเดาว่าคำไหนแปลว่าอะไร หรือไม่รู้ว่าตัวเองต้องทำอะไรต่อ ให้เขียนใหม่

## 3. ทำอะไรไปบ้าง

หัวใจคือให้ผู้ใช้เห็นว่าโค้ดเปลี่ยนจากอะไรเป็นอะไร ไม่ใช่แค่รายชื่อไฟล์ จัดกลุ่มตาม *จุดประสงค์* ไม่ใช่ตามไฟล์ และเรียงตามลำดับที่ควรเข้าใจ

**ฉบับเต็ม** (งานระดับกลางและเต็มที่โหมดสอนเปิด และเมื่อผู้ใช้สั่ง "อธิบายที่ทำไป"):

```
**ทำอะไรไปบ้าง**

1. <สิ่งที่เปลี่ยน ด้วยภาษาที่คนใช้แอปเข้าใจ>
   - ที่ไหน: `file:บรรทัด`
   - ก่อน: <โค้ดเดิมทำอะไร และทำไมมันเป็นปัญหา>
   - หลัง: <ตอนนี้ทำอะไร> (ใส่โค้ดสั้น ๆ ถ้าช่วยให้เห็นภาพ)
   - ทำไมแบบนี้: <เหตุผล โยงกับเป้าหมายหรือหลักฐาน>
   - เห็นผลได้ยังไง: <คำสั่งที่รัน หน้าจอที่กด หรือ test ที่ปกป้องมัน>
2. ...

**ภาพรวมหลังแก้**: <ตามค่าจริงหนึ่งตัวไหลผ่านส่วนที่แก้ ตั้งแต่ต้นจนจบ 3–6 ขั้น>
```

**ฉบับย่อ** (งานเบา, ปิดโหมดสอน หรือ "สอนสั้น"): การเปลี่ยนละ 1–2 บรรทัด บอกว่าเปลี่ยนอะไรด้วยภาษาธรรมดา เปลี่ยนจากอะไรเป็นอะไร และทำไม แล้วตามด้วย `file:บรรทัด` ไม่ต้องมีภาพรวมหลังแก้

กฎของทั้งสองฉบับ:
- ห้ามเขียนแบบ "แก้ X ให้ทำงานถูกต้อง" หรือ "ปรับปรุง logic" ที่ไม่บอกว่าเปลี่ยนจากอะไรเป็นอะไร ห้ามเหลือแค่รายชื่อไฟล์
- ถ้าเลือกโครงสร้างข้อมูลหรือวิธีไหนเพราะเรื่องประสิทธิภาพ (เช่น `Map` แทน loop ซ้อน หรือรวม query แทนการ query ใน loop) ให้บอกว่าทางตรงจะช้าลงแค่ไหนเมื่อข้อมูลโตขึ้น เช่น "สินค้า 1,000 ชิ้น loop ซ้อนต้องเทียบกันราว 1 ล้านครั้ง ส่วน Map ราว 1,000 ครั้ง"
- การเปลี่ยนที่เป็นแค่ผลพลอยได้ (import, เปลี่ยนชื่อตาม) รวมเป็นบรรทัดเดียวท้ายรายการ
- ศัพท์ใหม่ทุกคำต้องอธิบายครั้งแรกที่ใช้ ถ้าบล็อกสอนอธิบายไปแล้ว ให้อ้างกลับบรรทัดเดียว ("ใช้ debounce ที่อธิบายข้างบน") ไม่ต้องนิยามซ้ำ
- ข้อมูลจากการที่ agent ลูกทำ ให้หัวหน้าเขียนใหม่จาก ก่อน→หลัง→ทำไม ที่มันส่งกลับมา ไม่ส่งรายงานของ agent ต่อให้ผู้ใช้ตรง ๆ
