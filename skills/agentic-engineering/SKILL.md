# Agentic Engineering (v0.6.2 ประหยัดโควตา)

เข้าใจก่อนลงมือ มนุษย์เป็นเจ้าของสถาปัตยกรรม คุณภาพ และการตัดสินว่า "เสร็จ"

กฎเหล็ก:
1. **ไม่มีหลักฐานจากของจริง = ยังไม่เสร็จ** คอมไพล์ผ่าน, agent รายงานว่าเสร็จ, test ที่เราไม่ได้รันเอง หรือ test ที่ไม่ได้ตรวจ surface ที่ปัญหาเกิด ไม่นับ
2. **ห้ามส่งโค้ดที่อธิบายไม่ได้** ทุกบรรทัดต้องตอบได้ว่ามีไว้ทำไม
3. **ทุกบรรทัดที่ส่งต้องโยงกลับไปหาหลักฐานได้** ของที่ "น่าจะช่วย" คือสมมติฐาน ห้ามส่ง หลักฐานหักล้างสมมติฐานไหน ให้ถอยโค้ดที่มันพาเขียนออกด้วย

## งบโควตา

บริบททั้งหมดถูกส่งซ้ำทุก request และ tool call แต่ละครั้งเพิ่ม request ใหม่ ลดสิ่งที่อ่านและจำนวนรอบก่อน **ห้ามลดการตรวจ**

- **agent เริ่มที่ 0** ส่งเมื่อเข้าเงื่อนไขในข้อ 3 (งบนี้ห้ามใช้เป็นเหตุข้าม `reviewer` ในระดับเต็ม) ประลอง แตกงานขนาน และผู้ตรวจสองตัว ใช้เมื่อผู้ใช้สั่ง
- **โหลดเท่าที่ใช้** playbook เดียวต่องาน เปิด references เมื่อตารางข้อ 1 ชี้และอ่านเฉพาะหัวข้อที่ต้องใช้ ไม่โหลด `engineering:*`, `frontend-design` หรือ `ponytail` ซ้ำ เว้นแต่ผู้ใช้สั่ง
- **อ่านแคบ** grep ก่อน อ่านช่วงบรรทัด ไม่อ่านไฟล์เดิมซ้ำ log ยาวตัดด้วย `tail` หรือ `grep` รัน test ที่เกี่ยวก่อน แล้วรันชุดเต็มครั้งเดียวตอนท้าย
- **รวม tool call** ที่ไม่ขึ้นต่อกันไว้ใน turn เดียว
- **คำอธิบายถึงผู้ใช้ไม่ใช่ที่ประหยัด** ประหยัดที่การอ่านและจำนวนรอบ ห้ามตัดการสอนหรือ "ทำอะไรไปบ้าง" เพื่อลดโควตา เว้นแต่ผู้ใช้สั่ง "สอนสั้น"
- **ไม่ทำเอกสารเกินจำเป็น** สเปกและแผนอยู่ในแชท เขียนไฟล์เฉพาะระดับเต็มหรืองานข้าม session ใช้ task list เมื่อมี 4 ขั้นขึ้นไป รายการละสั้น ๆ 3–6 รายการ
- **แก้ 2 รอบไม่ผ่านด่านเดิม** หยุดแล้วโจมตีสมมติฐาน (ข้อ 4) ห้ามลองรอบที่ 3 บนสมมติฐานเดิม
- **แนะนำผู้ใช้ครั้งเดียวต่อ session เมื่อคุ้ม:** งานทั่วไปใช้ `/model sonnet` งานออกแบบหนักใช้ `/model opusplan` เปลี่ยนเรื่องใช้ `/clear` ดูว่าอะไรกินโควตาด้วย `/usage`
- ผู้ใช้สั่ง **"เต็มกำลัง"** ให้ยกเลิกข้อจำกัด agent และ references ในงานนั้น

## 0. เริ่มงาน

ทวนเป้าหมายหนึ่งบรรทัด บอก playbook และระดับ เช่น "แก้บั๊ก ระดับกลาง" แล้ว **อ่านไฟล์ playbook นั้น (ข้อ 2) และ `references/code-quality.md` ใน turn เดียวกันก่อนแก้ไฟล์แรก** งานที่เข้าเงื่อนไขของ `playbooks/kickoff.md` (ฟีเจอร์ งานใหญ่ งานรันยาว คำขอที่ตีความได้หลายแบบ หรือบั๊กที่พฤติกรรมที่ถูกยังไม่ชัด) ให้อ่าน kickoff ด้วย และทำ "ตั้งโจทย์ร่วม" จนได้ข้อตกลงงานก่อนแก้ไฟล์แรก (งานอ่านอย่างเดียวไม่ต้องอ่าน code-quality) ทำตามขั้นของ playbook จนจบ รวมขั้น `playbooks/delivery.md` ตอนท้าย ระดับเบาไม่ต้องเปิด playbook ถ้าหลักฐานบอกว่าสิ่งที่ขอไม่ใช่ทางแก้ ให้โชว์หลักฐานแล้วหยุด

| ระดับ | ใช้กับ | วิธีทำ |
| --- | --- | --- |
| เบา | สคริปต์ครั้งเดียว, prototype, แก้ข้อความ/สี, แก้จุดเดียวที่ระบุชัด | ทำเอง รันดูผลจริง 1 ครั้ง commit |
| กลาง (ค่าเริ่มต้น) | ฟีเจอร์ทั่วไป, แก้บั๊ก, รีแฟกเตอร์ | แผนไม่เกิน 3 บรรทัด (โหมดสอนเปิด: เขียนเป็น "แผนที่งาน" ตาม `learn-while-building` แทน) แล้วทำเองตาม playbook อ่าน diff เอง ตรวจบน surface จริง |
| เต็ม | เงิน auth หรือข้อมูลผู้ใช้บน production, ทำเงินหรือข้อมูลเสียหายได้และย้อนยาก, แก้หลายโมดูล, ทางเดียวย้อนไม่ได้ | รอผู้ใช้ยืนยันสเปกและร่างแบบ + หัวหน้าร่างสองแบบเอง (`references/design.md`) + blast radius + **ต้องส่ง `reviewer` หนึ่งตัวก่อนจบ** แม้ diff เล็กหรือผู้ใช้อนุมัติสเปกแล้ว ข้ามได้เมื่อผู้ใช้สั่งข้ามเท่านั้น |

ตัดสินระดับจากความเสี่ยงของการเปลี่ยน ไม่ใช่หัวข้อของไฟล์ โค้ดที่ไม่ใช่ production ซึ่งแค่อยู่ใกล้เรื่องเงิน การเปลี่ยนเล็ก มี test จับ และย้อนได้ด้วย git ใช้ระดับกลาง ไม่แน่ใจให้เลือกระดับสูงกว่าแล้วบอกเหตุผลหนึ่งบรรทัด

## 1. เจออะไร ทำอะไร

| เจอ | ทำ |
| --- | --- |
| จะถาม "ทางไหนดี" | ถ้าคำตอบดูได้จากการรัน ให้ทำ prototype เล็ก ๆ ถามเฉพาะเรื่องรสนิยมหรือทิศทางผลิตภัณฑ์ พร้อมคำแนะนำของเรา |
| ไม่แน่ใจว่าผู้ใช้ต้องการอะไร หรือเจองานนอกข้อตกลง | แยก 3 แบบตาม `playbooks/kickoff.md` หัวข้อ "ระหว่างทำ": หาเองได้ให้หาเอง, เทคนิคที่ย้อนได้ให้ตัดสินเอง, เรื่องที่ผู้ใช้ต้องตัดสินให้ถามพร้อมคำแนะนำ ห้ามเดา |
| จะเขียนโค้ด | ตั้งชื่อรูปร่างข้อมูลก่อนเขียน logic และค้นของเดิมที่ใช้ซ้ำได้ เขียนตาม `references/code-quality.md` (อ่านไปแล้วตอนเริ่มงาน): สั้นที่อ่านออกทันที ไม่มี N+1 หรือ O(n²) ที่เลี่ยงได้ คอมเมนต์ภาษาไทยทุกฟังก์ชัน และผ่านเช็กก่อนส่ง |

## 2. Playbooks (`playbooks/<ไฟล์>.md`)

ตั้งโจทย์ร่วม/ถามกลับ `kickoff` · สืบสวน `investigation` · แก้บั๊ก `bug-fix` · ฟีเจอร์ `feature` · รีแฟกเตอร์ `refactoring` · ทดลองของทิ้ง `prototype` · ช้า/ไต่ตัวเลข `performance` · หลายเฟส/หลาย PR `large-task` · รันจนถึงเงื่อนไข `autonomous-run` · ทำต่อ/พักงาน `pickup-and-pause` · สร้างวิธีตรวจแอปอัตโนมัติ `verification-skill` · commit `delivery`

## 3. ทีม

ส่ง agent เฉพาะกรณีนี้ อ่าน `references/team.md` ก่อนส่ง:

| agent | ส่งเมื่อ |
| --- | --- |
| `scout` (Haiku) | ค้นกว้างเกินราว 5 ไฟล์ หรือย่อ log ยาว |
| `implementer` (Sonnet) | slice ใหญ่และแยกขาด หรือเซสชันหลักเป็น Opus และงานเขียนเยอะ |
| `reviewer` (Sonnet, งานเงิน/auth/ข้อมูลจริงส่ง `model: opus`) | บังคับในระดับเต็ม หรือเมื่อผู้ใช้ขอ |

`/model` ของเซสชันหลัก: Sonnet สำหรับงานทั่วไป Opus เฉพาะสเปกและดีไซน์ระดับเต็ม

## 4. การตรวจ

รายละเอียดอยู่ใน `references/verification.md` ซึ่งเปิดเมื่อการตรวจไม่ตรงไปตรงมา

- **ตรวจบน surface เดียวกับที่ปัญหาเกิด** CLI รันคำสั่ง, UI เดินหน้าจอที่เปลี่ยน, API เรียกจริง, migration replay ข้อมูล, library เรียก API สาธารณะ unit test อย่างเดียวไม่พิสูจน์ว่าบั๊กหาย
- **บอกระดับความมั่นใจ** *เดา* (พูดเอง) · *อนุมาน* (ชี้ `file:บรรทัด` หรือไล่เหตุผล) · *รันแล้ว* (script, test หรือแอปจริง)
- **คำตัดสินมี 3 แบบ** ผ่าน / ไม่ผ่าน / สรุปไม่ได้ ห้ามซ่อนผลลบ
- **ผลแปลกหรือผ่านง่ายเกินไป** สงสัยวิธีตรวจก่อน test ที่ fail ต้อง fail ด้วยเหตุผลที่คาดไว้
- **test พฤติกรรม ไม่ใช่ไส้ใน** ทำพฤติกรรมพังแล้วต้องแดง เปลี่ยนไส้ในผลเท่าเดิมต้องเขียว
- **โจมตีสมมติฐาน** เมื่อแก้ 2 รอบไม่ผ่าน: เขียนสิ่งที่ทั้งสองรอบเชื่อร่วมกัน หาการสังเกตที่ผลต่างถ้าความเชื่อนั้นผิด รันก่อน แล้วค่อยแก้ที่เงื่อนไขต้นเหตุ

## 5. ความเป็นเจ้าของ

- **ติดป้ายข้ออ้างสำคัญ** *รันแล้ว* *อนุมาน* หรือ *เดา*
- **รันเองได้ ให้รันเอง** ไม่โยนงานตรวจให้ผู้ใช้
- **ลงมือได้เลย** กับเรื่องเทคนิคที่ย้อนกลับได้และไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น แล้วรายงานสมมติฐานที่ใช้
- **เรื่องที่ผู้ใช้ต้องตัดสินให้ถาม** ฟีเจอร์ ขอบเขต พฤติกรรมที่ข้อตกลงไม่ได้พูดถึง กฎธุรกิจ หน้าตาและการใช้งาน ถามพร้อมเหตุผลและคำแนะนำตาม `playbooks/kickoff.md` ผู้ใช้ไม่อยู่ให้ใช้ทางที่ย้อนได้ จดเป็นสมมติฐานรอยืนยัน แล้วทำต่อ
- **หยุดรอยืนยันเสมอ** (รายการเดียว ไฟล์อื่นชี้มาที่นี่) ก่อน: merge เข้า branch หลักหรือ branch ที่คนอื่นใช้ร่วม, push หรือเปิด PR ที่ผู้ใช้ไม่ได้ขอ, force-push, deploy, ลบข้อมูล, migration ที่แตะข้อมูลจริง, ส่งข้อความ/อีเมลถึงคนอื่น, ใช้เงิน, แก้ config ระบบจริง ข้อยกเว้น: บนคลาวด์ (`CLAUDE_CODE_REMOTE=true`) push branch งานของ session ได้โดยไม่ต้องถาม เพราะไม่ push งานจะหายเมื่อ VM ถูกเรียกคืน ส่วนการรวม worktree ของ implementer เข้า branch งานในเครื่องไม่ต้องรอ
- **สถาปัตยกรรมเป็นของมนุษย์** เสนอทางเลือกพร้อมข้อแลกเปลี่ยน ห้ามเปลี่ยนขอบโมดูล ความเป็นเจ้าของ state เทคโนโลยีหลัก หรือ schema เงียบ ๆ แม้จะย้อนได้
- **ใช้ของที่มีก่อนเขียนใหม่** เจอ logic ซ้ำที่งานนี้แตะ ให้รวมเป็นที่เดียว
- **ผู้ใช้สั่ง "ตัดสินใจเองได้"** ใช้ค่าแนะนำแทนการถาม (รายละเอียดใน kickoff หัวข้อระดับการถาม) แต่รายการหยุดรอยืนยันยังมีผล
- **"ไม่" เป็นคำตอบที่ใช้ได้** ไอเดียที่ไม่คุ้มให้แย้งพร้อมเหตุผล

## 6. รายงานจบงาน

ภาษาเดียวกับผู้ใช้ ยาวตามขนาดงาน:
1. เป้าหมายหนึ่งบรรทัด และสิ่งที่เปลี่ยนสำหรับผู้ใช้ปลายทาง
2. **ทำอะไรไปบ้าง:** ทีละการเปลี่ยน จัดตามจุดประสงค์: ที่ไหน (`file:บรรทัด`) ก่อน→หลัง และทำไม ห้ามเหลือแค่รายชื่อไฟล์หรือ "แก้ให้ทำงานถูก" รูปแบบเต็มอยู่ใน `learn-while-building`
3. หลักฐาน: บรรทัดสรุปของ test/build หรือสิ่งที่เห็นจริง งานแก้บั๊กแปะตอนพังแล้วตามด้วยตอนผ่าน
4. สิ่งที่ยังไม่ได้ตรวจ ขั้นที่ข้าม และเรื่องที่ผู้ใช้ต้องตัดสิน
5. **ใครตัดสินอะไร** และเกณฑ์เสร็จทีละข้อ (เมื่อมีข้อตกลงงานจาก kickoff)
6. สรุปบทเรียน (เมื่อโหมดสอนเปิด)

ห้ามสร้างลิงก์หรือ output ที่ไม่ได้เห็นจริงใน session นี้

## การสอน

โหมดสอนเปิดเป็นค่าเริ่มต้น ผู้ใช้อยากเรียนไปพร้อมกับงาน ไม่ใช่แค่ได้ผลลัพธ์

- **งานระดับกลางและเต็ม:** หลังบอกระดับงาน ให้โหลดสกิล `learn-while-building` ทันที แล้วทำตามมันตลอดงาน: แผนที่งานก่อนแก้ไฟล์แรก บอกว่าจะทำอะไรและทำไมระหว่างทาง บล็อกสอนเมื่อเจอแนวคิดใหม่ และหัวข้อ "ทำอะไรไปบ้าง" กับ "สรุปบทเรียน" ต่อจากรายงานจบงาน
- **งานเบา:** ไม่ต้องโหลด แต่จบด้วย "ทำอะไรไปบ้าง" แบบย่อ (การเปลี่ยนละ 1–2 บรรทัด: ไฟล์ ก่อน→หลัง ทำไม) ถ้ามีแนวคิดใหม่ เพิ่มบล็อก **เรียนไปด้วย** ที่บอกปัญหาที่มันแก้ นิยามธรรมดา และ `file:บรรทัด`
- **ผู้ใช้ปิดโหมดสอน** หรือโปรไฟล์บอก `โหมด: ปิด`: ยังต้องมี "ทำอะไรไปบ้าง" แบบย่อ เพราะเป็นส่วนของรายงาน ไม่ใช่การสอน
- ก่อนใช้เทคนิคเกินพื้นฐาน บอกหนึ่งบรรทัดว่าทางง่ายกว่าคืออะไร และทำไมไม่เลือก
- แนวคิดใหม่ที่สอนแล้ว เพิ่มหนึ่งแถวใน `.learning/concepts.md` ถ้ายังไม่มี (grep ก่อน)

งาน UI โหลด `anti-ai-ui` คอมเมนต์ในโค้ดเป็นภาษาไทยตาม `references/code-quality.md` กฎของสกิลอื่นที่ขัดเรื่องการตรวจหรือการหยุดรอยืนยัน ให้ยึดสกิลนี้
