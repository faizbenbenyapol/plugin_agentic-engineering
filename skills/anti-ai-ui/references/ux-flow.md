# UX ก่อนหน้าตา: flow, สถานะ และคำบนหน้าจอ

หน้าที่สวยแต่ใช้ยากคือหน้าที่ล้มเหลว นักออกแบบตัวจริงเริ่มจาก "ผู้ใช้จะทำงานอะไรให้สำเร็จ" ก่อนเลือกสี ทำขั้นนี้เป็นข้อความหรือ ASCII ล้วน ไม่ต้องเขียนโค้ด (ถูกกว่าแก้หน้าจอที่สร้างไปแล้วมาก) แล้วเก็บผลไว้ในหัวข้อ 8 ของไฟล์รีไควร์เมนต์

## 1. งานหลักและ flow

1. **งานหลักไม่เกิน 3 อย่าง** ที่ผู้ใช้มาหน้าจอนี้เพื่อทำ เรียงตามความถี่ งานอันดับ 1 ต้องทำได้เร็วที่สุด
2. **เขียน flow ของงานอันดับ 1** จากจุดเข้า (ลิงก์ แจ้งเตือน หน้าแรก) จนสำเร็จ ทีละขั้น: ผู้ใช้เห็นอะไร → ทำอะไร → ระบบตอบอะไร นับจำนวนขั้นและจำนวนครั้งที่ต้องพิมพ์ แล้วถามว่าขั้นไหนตัดหรือรวมได้
3. **หาทางแยก** ที่ flow พัง: ยังไม่ล็อกอิน ไม่มีสิทธิ์ ข้อมูลไม่ครบ ยกเลิกกลางทาง เน็ตหลุด กดย้อน
4. **หนึ่งหน้าจอ หนึ่งการกระทำหลัก** ปุ่มหลักมีปุ่มเดียว ที่เหลือเป็นรอง ถ้าเลือกไม่ได้ แปลว่าหน้าจอทำหลายงานเกินไป

```
ตัวอย่าง flow: จองคิวตัดผม (มือถือ)
[ลิงก์ LINE] → เลือกสาขา (จำสาขาล่าสุด) → เลือกช่าง/ใครก็ได้ → เลือกเวลาว่าง
→ กรอกชื่อ+เบอร์ (จำจากครั้งก่อน) → ยืนยัน → หน้าสำเร็จ + เพิ่มลงปฏิทิน
ขั้น: 5 · พิมพ์: 0 ครั้งถ้าเคยจอง · ทางแยก: เวลาถูกจองไปก่อนกดยืนยัน → เสนอเวลาใกล้สุด
```

## 2. ตารางสถานะ (state matrix)

ทุกหน้าจอหรือ component ที่โหลดข้อมูล ให้ระบุว่าแต่ละสถานะแสดงอะไร ช่องที่ตอบไม่ได้คือคำถามสำหรับผู้ใช้ ไม่ใช่สิ่งที่เดาเอง

| หน้าจอ | ปกติ | ว่าง (ครั้งแรก / ค้นไม่เจอ) | กำลังโหลด | error | บางส่วน | ไม่มีสิทธิ์ | ข้อมูลยาว/มาก |
| --- | --- | --- | --- | --- | --- | --- | --- |

"ว่างครั้งแรก" กับ "ค้นไม่เจอ" ต่างกัน ครั้งแรกชวนเริ่มใช้ ค้นไม่เจอบอกวิธีปรับคำค้น

## 3. เช็กลิสต์การใช้งาน (ย่อจาก heuristics ของ Nielsen)

ใช้ตรวจทั้งตอนวางแผนและตอนดูหน้าจอจริง รายงานเฉพาะข้อที่ไม่ผ่าน พร้อมจุดที่เห็น

1. **เห็นสถานะระบบ** กดแล้วรู้ทันทีว่ารับคำสั่งแล้ว งานที่นานเกิน 1 วินาทีมีสิ่งบอกความคืบหน้า
2. **ภาษาของผู้ใช้** เรียกสิ่งต่าง ๆ ด้วยคำที่ผู้ใช้ใช้ ไม่ใช่คำของระบบ ("การแจ้งเตือน" ไม่ใช่ "webhook")
3. **ย้อนและยกเลิกได้** การกระทำที่ทำลายข้อมูล ทำ "เลิกทำ" ได้ดีกว่ากล่องยืนยัน ถ้าต้องยืนยัน ให้ระบุชื่อสิ่งที่จะลบ
4. **สม่ำเสมอ** สิ่งเดียวกันชื่อเดียวกัน หน้าตาเดียวกัน อยู่ที่เดียวกันทุกหน้า
5. **กันผิดก่อนแก้ผิด** ปิดตัวเลือกที่ใช้ไม่ได้พร้อมบอกเหตุผล ใช้ input ที่ถูกชนิด
6. **เห็นดีกว่าจำ** ไม่บังคับให้ผู้ใช้จำค่าจากหน้าก่อน แสดงตัวเลือกให้เห็น
7. **เร็วสำหรับคนใช้บ่อย** จำค่าล่าสุด ค่าเริ่มต้นที่ฉลาด ทางลัดคีย์บอร์ดในงานจอใหญ่
8. **เรียบ** ทุกองค์ประกอบต้องช่วยงานหลัก ไม่งั้นตัด
9. **error ช่วยแก้** บอกว่าเกิดอะไร ที่ช่องไหน และแก้ยังไง เก็บค่าที่ผู้ใช้กรอกไว้
10. **ช่วยเหลือตรงจุด** คำอธิบายสั้นข้างช่องที่งง ดีกว่าหน้าคู่มือแยก

## 4. ฟอร์ม และรูปแบบข้อมูลไทย

- label อยู่เหนือช่อง ไม่ใช้ placeholder แทน label ช่องไม่บังคับเขียนว่า "(ไม่บังคับ)" แทนการติดดอกจันทุกช่อง
- ตรวจค่าตอนออกจากช่อง ไม่ใช่ทุกตัวอักษร แสดง error ใต้ช่องนั้น ห้ามล้างค่าที่กรอกเมื่อส่งไม่ผ่าน
- ใช้ `inputmode`/`type` ให้ตรง: เบอร์โทร `tel`, ตัวเลข `numeric`, อีเมล `email` มือถือจะขึ้นแป้นที่ถูก
- **เบอร์มือถือไทย** 10 หลัก รับทั้งแบบมีขีดและไม่มี เก็บแบบไม่มีขีด แสดง `081-234-5678`
- **เลขบัตรประชาชน** 13 หลัก ตรวจ checksum แสดง `1-2345-67890-12-3`
- **ที่อยู่** เรียงแบบไทย: บ้านเลขที่ ถนน ตำบล/แขวง อำเภอ/เขต จังหวัด รหัสไปรษณีย์ กรอกรหัสไปรษณีย์แล้วเสนอตำบล/อำเภอให้เลือก ประหยัดการพิมพ์มาก
- **วันที่** ตกลงในรีไควร์เมนต์ว่าแสดง พ.ศ. หรือ ค.ศ. เก็บในระบบเป็น ค.ศ./ISO เสมอ เขตเวลา Asia/Bangkok
- **เงินบาท** `฿1,250.00` หรือ `1,250 บาท` เลือกแบบเดียวทั้งแอป ตัวเลขในตารางชิดขวาและใช้ตัวเลขความกว้างเท่ากัน (`font-variant-numeric: tabular-nums`)
- **ชื่อ** ถ้าต้องมีคำนำหน้า ให้เป็นตัวเลือก ไม่บังคับ ช่องชื่อยาวพอสำหรับชื่อไทยที่ยาว

## 5. คำบนหน้าจอ (microcopy)

- คำมีไว้ทำให้ใช้ง่ายขึ้น ไม่ใช่ตกแต่ง แต่ละข้อความทำหน้าที่เดียว
- **ปุ่มบอกสิ่งที่จะเกิด** "บันทึกการแก้ไข" ไม่ใช่ "ตกลง" หรือ "Submit" "ส่งใบเสนอราคา" ไม่ใช่ "ดำเนินการต่อ"
- **ชื่อการกระทำเดียวกันตลอด flow** ปุ่ม "เผยแพร่" → แจ้งเตือน "เผยแพร่แล้ว" → ตัวกรอง "ที่เผยแพร่"
- **error** ไม่ขอโทษ ไม่กำกวม: "เบอร์โทรต้องมี 10 หลัก" ไม่ใช่ "ขออภัย เกิดข้อผิดพลาด"
- **empty state** คือคำชวนให้ทำ พร้อมปุ่มทำได้เลย ไม่ใช่การบรรยายความว่างเปล่า
- น้ำเสียงสุภาพเป็นกลาง ไม่ใส่ "ค่ะ/ครับ" ในข้อความระบบ เว้นแต่แบรนด์ต้องการ ไม่ใช้คำอังกฤษปนเมื่อมีคำไทยที่คนใช้จริง

## 6. ตรวจบนหน้าจอจริง

- เดิน flow งานอันดับ 1 บนหน้าจอจริงตั้งแต่จุดเข้าจนสำเร็จ (Playwright หรือ browser) นับขั้นเทียบกับที่วางไว้
- ผู้ใช้อนุมัติ mock หรือภาพอ้างอิงแล้ว: screenshot หน้าจริงเทียบกับภาพนั้นทุกรอบที่แก้ จนต่างเฉพาะจุดที่ตั้งใจ
- เดินเช็กลิสต์หัวข้อ 3 แล้วรายงานเฉพาะข้อที่ไม่ผ่าน
