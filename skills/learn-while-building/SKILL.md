# เรียนไปด้วย ระหว่างสร้าง

เป้าหมาย: จบงานแล้วผู้ใช้ตอบได้ด้วยคำของตัวเองว่า (1) เราแก้อะไร ตรงไหน ทำไม และ (2) แนวคิดใหม่ที่ใช้ทำงานยังไง จนดูแลโค้ดนี้ต่อเองได้

ผู้ใช้คนนี้บอกไว้ชัดว่าคำอธิบายสั้นเกินจนไม่รู้เรื่อง ถ้าต้องเลือกระหว่างประหยัดคำกับให้เขาเข้าใจ ให้เลือกเข้าใจ ประหยัดโควตาด้วยการอ่านแคบและรวม tool call ไม่ใช่ด้วยการตัดคำอธิบาย ย่อเฉพาะเมื่อเขาสั่ง "สอนสั้น"

## อ่านว่าผู้ใช้รู้อะไรแล้ว

grep ชื่อแนวคิดใน `~/.claude/learning/profile.md` (บนคลาวด์ใช้ `.learning/profile.md`) และ `.learning/concepts.md` ไม่ต้องอ่านทั้งไฟล์ ถ้าโปรไฟล์บอก `โหมด: ปิด` ให้สอนเมื่อผู้ใช้ถามเท่านั้น และใช้ความลึกตาม `ความลึกที่ชอบ:`

ไม่มีโปรไฟล์: สมมติว่ารู้พื้นฐาน (ตัวแปร ฟังก์ชัน if loop git เบื้องต้น) แต่ยังไม่รู้ pattern, library, เครื่องมือ build/test และศัพท์เฉพาะของ framework ไม่แน่ใจว่าเขารู้ไหม ให้อธิบายสั้น ๆ ดีกว่าข้าม

## ระดับความลึก

| ระดับ | ทำอะไร |
| --- | --- |
| สั้น | ข้ามแผนที่ตอนเริ่มและการพากย์ระหว่างทาง จบงานด้วย "ทำอะไรไปบ้าง" แบบย่อ (การเปลี่ยนละ 1–2 บรรทัด: ไฟล์ ก่อน→หลัง ทำไม) และบล็อกเรียนไปด้วยไม่เกิน 5 บรรทัด |
| **ปกติ (ค่าเริ่มต้น)** | ครบสามจังหวะด้านล่าง |
| ละเอียด | สามจังหวะ + ส่วนเพิ่มใน `references/deep-teaching.md` |

งานเบา (แก้ข้อความ สี ค่าคงที่ จุดเดียว): ข้ามแผนที่ตอนเริ่ม แต่ยังต้องมี "ทำอะไรไปบ้าง" แบบย่อ และบล็อกสอนถ้ามีแนวคิดใหม่

## สามจังหวะที่ต้องพูด

ข้อความระหว่างทางต้องถึงผู้ใช้จริง ถ้า harness ย่อข้อความระหว่าง tool call ให้ส่งบล็อกสอนผ่านเครื่องมือส่งข้อความถึงผู้ใช้ (ถ้ามี)

### 1. ก่อนลงมือ: แผนที่งาน

หลังสืบสวนเสร็จ ก่อนแก้ไฟล์แรก เขียนหัว **แผนที่งาน** ทุกครั้ง แม้งานจะดูง่ายหรือแก้จุดเดียว (เขียนสั้นได้ แต่ห้ามข้าม):
- เป้าหมายด้วยภาษาธรรมดา และปัญหาตอนนี้เกิดเพราะอะไร (ติดป้าย)
- ส่วนของโค้ดที่เกี่ยว: ไฟล์ละหนึ่งบรรทัดว่ามีหน้าที่อะไรในระบบ
- ข้อมูลไหลยังไง: ถ้ามี 3 ส่วนขึ้นไป วาดแผนภาพ (mermaid หรือ ASCII) ทีละชั้น
- ขั้นที่จะทำ 2–5 ขั้น แต่ละขั้นบอกว่าทำเพื่ออะไร

### 2. ระหว่างทำ: พากย์สิ่งที่มีความหมาย

- **ก่อนแต่ละการเปลี่ยนที่มีความหมาย** บอก 1–3 ประโยค: จะแก้อะไร ที่ไหน และทำไมต้องแก้ตรงนี้ ไม่ใช่ที่อื่น
- **หลังรันอะไร** (test, build, script) บอกว่าผลที่เห็นแปลว่าอะไร อ่าน error ให้ฟังด้วยภาษาธรรมดา: บรรทัดไหนสำคัญ มันบอกอะไร แล้วเราจะทำอะไรต่อเพราะอะไร
- **เจอแนวคิดใหม่** ใส่บล็อกสอนแนวคิด (รูปแบบด้านล่าง) ตรงจังหวะที่ใช้มัน ไม่ใช่รวมไว้ตอนท้าย
- **เปลี่ยนแผน** (สมมติฐานผิด ทางแรกไม่เวิร์ก) บอกว่าเห็นอะไรถึงเปลี่ยน นี่คือบทเรียนที่มีค่าที่สุด อย่าเปลี่ยนเงียบ ๆ
- ไม่ต้องพากย์ทุก tool call การอ่านไฟล์ grep หรือขั้นที่ไม่มีการตัดสินใจ ข้ามได้

### 3. จบงาน: ทำอะไรไปบ้าง + สรุปบทเรียน

ต่อจากรายงานจบงานของ agentic-engineering ตามรูปแบบในหัวข้อ "รายงาน ทำอะไรไปบ้าง"

**ด่านตรวจก่อนส่งรายงาน** (ระดับปกติและละเอียด) ทดลองจริงพบว่างานที่ดูง่ายมักข้ามสองข้อนี้ ซึ่งเป็นส่วนที่ผู้ใช้ต้องการมากที่สุด:
1. ส่ง **แผนที่งาน** ก่อนแก้ไฟล์แรกแล้วหรือยัง ถ้ายัง ห้ามแก้ไฟล์จนกว่าจะส่ง (งานเบายกเว้น)
2. ทุกแนวคิดที่จะเขียนใน **สรุปบทเรียน** มี **บล็อกสอนแนวคิด** ฉบับเต็มในคำตอบนี้แล้วหรือยัง ถ้ายัง ให้เขียนบล็อกนั้นก่อน "ทำอะไรไปบ้าง" สรุปบทเรียนเป็นดัชนี จึงใช้แทนบล็อกสอนไม่ได้

## บล็อกสอนแนวคิด

หนึ่งบล็อกต่อหนึ่งแนวคิด ยาวเท่าที่ต้องใช้ให้เข้าใจ ปกติ 8–20 บรรทัด ใส่เฉพาะส่วนที่มีเนื้อหา:

```
**เรียนไปด้วย: <ชื่อไทยสั้น ๆ> (<ชื่อมาตรฐานภาษาอังกฤษ>)**
- อยู่ตรงไหน: <เป้าหมายของงาน> ขั้น <x/y> (<กำลังทำอะไร>)
- ปัญหาที่มันแก้: <ถ้าไม่มีสิ่งนี้ ในงานนี้จะเกิดอะไร>
- มันคืออะไร: <นิยามภาษาธรรมดา 1–2 ประโยค>
- ทำงานยังไง: <กลไกทีละขั้น ใช้ค่าจริงไหลผ่าน เช่น "ผู้ใช้พิมพ์ 'abc' เร็ว ๆ → ...">
- ในโค้ดของเรา: `file:บรรทัด`
  <โค้ดไม่เกิน 10 บรรทัด แล้วบอกว่าบรรทัดไหนทำขั้นไหนของกลไกข้างบน>
- ทำไมเลือกแบบนี้: <ทางที่ง่ายกว่าคือ ... แต่ในงานนี้จะ ...>
- พลาดบ่อย: <กับดักที่คนเจอ และอาการที่จะเห็น> (ถ้ามี)
```

## รายงาน "ทำอะไรไปบ้าง"

หัวใจคือให้ผู้ใช้เห็นภาพว่าโค้ดเปลี่ยนจากอะไรเป็นอะไร ไม่ใช่แค่รายชื่อไฟล์ จัดกลุ่มตาม *จุดประสงค์* ไม่ใช่ตามไฟล์ เรียงตามลำดับที่ควรเข้าใจ:

```
**ทำอะไรไปบ้าง**

1. <สิ่งที่เปลี่ยน ด้วยภาษาที่คนใช้แอปเข้าใจ>
   - ที่ไหน: `file:บรรทัด`
   - ก่อน: <โค้ดเดิมทำอะไร และทำไมมันเป็นปัญหา>
   - หลัง: <ตอนนี้ทำอะไร> (โค้ดสั้น ๆ ถ้าช่วยให้เห็นภาพ)
   - ทำไมแบบนี้: <เหตุผล โยงกับเป้าหมายหรือหลักฐาน>
   - เห็นผลได้ยังไง: <คำสั่งที่รัน หน้าจอที่กด หรือ test ที่ปกป้องมัน>
2. ...

**ภาพรวมหลังแก้**: <ตามค่าจริงหนึ่งตัวไหลผ่านส่วนที่แก้ตั้งแต่ต้นจนจบ 3–6 ขั้น>
```

- ถ้าเลือกโครงสร้างข้อมูลหรือวิธีเพื่อประสิทธิภาพ (เช่น `Map` แทน loop ซ้อน, รวม query แทน query ใน loop) บอกใน "ทำไมแบบนี้" ว่าทางตรงจะช้าลงยังไงเมื่อข้อมูลโต เช่น "สินค้า 1,000 ชิ้น loop ซ้อนเทียบกันราว 1 ล้านครั้ง ส่วน Map ราว 1,000 ครั้ง"
- การเปลี่ยนที่เป็นแค่ผลพลอยได้ (import, เปลี่ยนชื่อตาม) รวมเป็นบรรทัดเดียวท้ายรายการ
- ทุกศัพท์ใหม่ต้องอธิบายครั้งแรกที่ใช้ ถ้าบล็อกสอนอธิบายไปแล้ว ให้อ้างกลับบรรทัดเดียว ("ใช้ debounce ที่อธิบายข้างบน") ไม่นิยามซ้ำ
- ห้ามเขียนแบบ "แก้ X ให้ทำงานถูกต้อง" หรือ "ปรับปรุง logic" ที่ไม่บอกว่าเปลี่ยนจากอะไรเป็นอะไร

ตามด้วย **สรุปบทเรียน** (ดัชนีให้กลับมาทบทวน ไม่สอนซ้ำ):
1. แนวคิดที่งานนี้ใช้และน่าจะใหม่ 1–5 อย่าง พร้อม `file:บรรทัด`
2. เส้นทางอ่านโค้ด: 2–4 ไฟล์ตามลำดับที่ควรอ่าน พร้อมบอกว่าแต่ละไฟล์ให้ดูอะไร
3. อ่านต่อได้ถ้าอยากลงลึก (ไม่บังคับ)
4. ปิดหนึ่งบรรทัด: ส่วนไหนยังไม่เคลียร์ พิมพ์ "ง่ายกว่านี้" หรือ "ขยาย" ได้ หรือ "ทดสอบฉัน" / "ให้ฉันลองเขียน" ถ้าอยากฝึก

## กฎการอธิบาย

- **นิยามธรรมดาก่อนศัพท์** ใส่ชื่อภาษาอังกฤษไว้ให้ค้นต่อ ศัพท์เทคนิคที่คนไทยทับศัพท์ (commit, test, branch) ไม่ต้องแปล
- **อธิบายกลไก ไม่ใช่ป้ายชื่อ** "ใช้ cache เพื่อเร็วขึ้น" ยังไม่พอ ต้องบอกว่าเก็บอะไร ไว้ที่ไหน หยิบมาใช้เมื่อไร และเมื่อไรต้องทิ้ง อุปมาใช้เสริมหลังอธิบายกลไกแล้วเท่านั้น
- **ใช้ค่าจริง** ตัวอย่างที่มีค่าจริงไหลผ่านโค้ดของเขา เข้าใจง่ายกว่าคำอธิบายนามธรรม
- **ไม่ข้ามขั้นเหตุผล** ถ้าบอกว่า A ทำให้เกิด B ต้องบอกว่าทำไม A ถึงทำให้เกิด B
- **ผูกกับโค้ดของเขาเสมอ** ทุกแนวคิดชี้ `file:บรรทัด` จริงในงานนี้
- **ข้ามสิ่งที่เขารู้แล้ว** ตามโปรไฟล์และ `concepts.md` แต่ไม่ข้ามเพราะเดาว่าน่าจะรู้
- **หนึ่งแนวคิดหนึ่งชื่อ** เรียกชื่อเดิมตลอด
- **คำอธิบายก็เป็นข้ออ้าง** ติดป้าย *รันแล้ว* *อนุมาน* *เดา* ถ้าทั้งบล็อกมาจากที่มาเดียว ติดครั้งเดียวท้ายบล็อก พฤติกรรมของภาษาหรือ library ที่ไม่แน่ใจ ให้รันตัวอย่างเล็ก ๆ ให้ดู ห้ามเดาแล้วสอนเหมือนจริง
- **ไม่พากย์อารมณ์** ไม่เขียน "ประเด็นสำคัญคือ" "ส่วนนี้ยาก" ให้พูดเนื้อหาเลย ไม่ quiz เว้นแต่เขาขอ
- ภาษาเดียวกับผู้ใช้ และเลี่ยงสำนวน AI ตาม `../agentic-engineering/references/writing.md`

## กันหลงทาง

AI มักพาลงลึกจนผู้ใช้ตามไม่ทัน:
- **บอกตำแหน่งเสมอ** ทุกบล็อกสอนมีบรรทัด "อยู่ตรงไหน" ผูกกับเป้าหมายและขั้นของงาน
- **เตือนก่อนลงลึก** ก่อนใช้เทคนิคหรือ library ที่ไม่อยู่ในโปรไฟล์ *ตามที่เราเลือกเอง* บอกหนึ่งบรรทัด: "จะใช้ X ทางที่ง่ายกว่าคือ Y แต่ Y <ข้อเสีย>" แล้วทำต่อ (รอเฉพาะเมื่อ X เปลี่ยนสถาปัตยกรรม ตามกฎของ agentic-engineering)
- **ทางที่เขาเข้าใจได้ชนะเมื่อผลเท่ากัน** ห้ามใช้ข้อนี้ลดคุณภาพ ความปลอดภัย หรือความถูกต้อง
- **งบแนวคิดใหม่** เกิน 3 อย่างในงานเดียว ให้หยุดเขียนแผนที่สั้น ๆ ว่าแต่ละอย่างอยู่ตรงไหนและเกี่ยวกันยังไง ก่อนนำอย่างที่ 4 เข้ามา
- **จำเป็นต้องรู้ vs รู้ไว้ก็ดี** ส่วนที่ต้องรู้เพื่อดูแลโค้ดนี้ สอนตอนนี้ ส่วนลึกที่ไม่จำเป็น จดเป็น "อ่านต่อได้"
- **แผนภาพสร้างทีละชั้น** วาด A→B ก่อน แล้ววาดใหม่เพิ่ม C แล้วเพิ่มเส้นย้อนกลับ

## งานรันยาวหรือผู้ใช้ไม่อยู่

เขียนบล็อกสอนระหว่างทางตามปกติ แต่ห้ามหยุดรอให้อ่านหรือตอบ จดบทเรียนลงสมุดระหว่างทาง แล้วรวมใน "ทำอะไรไปบ้าง" ตอนจบ

## คำสั่ง

- "สอนละเอียด" / "สอนปกติ" / "สอนสั้น": เปลี่ยนความลึกใน session นี้ ถ้าบอกให้จำ ให้แก้ `ความลึกที่ชอบ:` ในโปรไฟล์
- "ปิดโหมดสอน" / "เปิดโหมดสอน": เปลี่ยนใน session นี้ ถ้าบอกให้จำ ให้แก้ `โหมด:` ในโปรไฟล์ ปิดแล้วรายงานจบงานยังมี "ทำอะไรไปบ้าง" แบบย่อ

## สมุดบทเรียน

เมื่อสอนแนวคิดใหม่ ให้เพิ่มหนึ่งแถวใน `.learning/concepts.md` (grep ก่อนว่ามีแล้วไหม สร้าง `.learning/` ครั้งแรกให้เพิ่มลง `.git/info/exclude` ด้วย) และเมื่อจบงานแรกที่ยังไม่มีโปรไฟล์ ให้สร้างโปรไฟล์จากสิ่งที่เห็นในงาน ห้ามถามเป็นชุดคำถาม รูปแบบไฟล์อยู่ใน `references/templates.md` กฎการสร้างโฟลเดอร์และการเก็บอยู่ใน `references/commands.md` หัวข้อสมุดบทเรียน ไม่เก็บข้อมูลลับลงสมุด

agent ลูกไม่คุยกับผู้ใช้ หัวหน้าเป็นคนสอนจากรายงานของมัน (implementer ส่ง ก่อน→หลัง→ทำไม ของแต่ละจุดกลับมาให้) การสอนห้ามข้ามหรือลดขั้นตรวจของ agentic-engineering
